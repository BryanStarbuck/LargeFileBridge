# LargeFileBridge — Perceptual Content Fingerprint

## About Large File Bridge

Large File Bridge is a local-first web app (TypeScript on Node; UI at http://localhost:2222/, REST backend
at http://localhost:8787/) that keeps the **big, git-ignored files** in a person's repos and folders —
videos, large images, audio and other large binaries — **in sync across their own computers by pinning them
on IPFS**, while git carries the small text files and the record of what exists. It scans repos and
directories for large files, nudges the ones that should be git-ignored (never ignoring anything on its
own), tracks each file with a content hash and per-file metadata, and pins and fetches those files so every
computer holds the same copy; a 15-minute `launchd` job keeps that going in the background. Around that
core it helps people take care of the media itself: it finds files that are needlessly uncompressed and
compresses them only when asked, writes transcripts, AI visual descriptions and OCR text beside them, and
— the subject of this spec family — **recognizes when two files are the same content** even after a
resize, re-compression, re-encode or format change. Everything runs on the user's own machine: sign-in is
Google through OpenAuthFederated for allow-listed accounts only, the computer never acts as a public IPFS
gateway or relay, and the fingerprint features never touch the network.

LargeFileBridge needs to know when two files are **fundamentally the same file** even after they have
been **reduced in pixel resolution, compressed, re-encoded to a different codec, changed in frame rate,
or converted between formats** (e.g. a PNG re-saved as a heavily-compressed JPEG). An exact content hash
(SHA of the bytes) cannot do this — change one pixel and it changes completely. A **perceptual
fingerprint** can: it hashes what the media *looks like*, not the exact bytes, so a shrunk-and-recompressed
copy still matches its original.

This is the capability **PhotoDNA** is known for. We want that capability under one **non-negotiable
constraint from the [charter](../CLAUDE.md)**:

> **Hard requirement: no external networking.** Whatever we choose must run **entirely locally**. It must
> **NOT** phone home, call an external service, or otherwise send file data or fingerprints over the
> network. LargeFileBridge is **not a reporting service** and must not behave like one.

The file opens with the two **ranked comparisons** (images, then video), because that is what a reader
comes here for, followed at once by the **final decision** ([§FD](#fd-final-decision--what-ships-images--video)):
**PDQ via ajdnik/imghash for images, and PDQ per frame on our own ffmpeg sampler for video**. The **goal** and the **scoring math** that produced every number in those tables follow
immediately after. The LOCKED design sections (§1–§7) keep their numbers so the many cross-references
into this spec from other specs and code comments stay valid.

This spec builds on the siblings and does not repeat them:

* [compression.mdx](./compression.mdx) — captures the fingerprint **before and after** every compress /
  convert so the result is provably the same content (its `fingerprint_before` / `fingerprint_after`).
* [repo_tracking_scheme.mdx](./repo_tracking_scheme.mdx) — the per-file `<name>.yaml` sidecar where the
  fingerprint is stored (`file.fingerprint`), and the `compress`/`convert` events that carry the pair.
* [files.mdx](./files.mdx) — per-file identity and the exact content hash this fingerprint **complements**.
* [special_files.mdx](./special_files.mdx) — only **video/image/audio** (and other media) get a
  perceptual fingerprint; ordinary large binaries get the exact hash only.
* [duplicates.mdx](./duplicates.mdx) and [subsets.mdx](./subsets.mdx) — the de-dup and "clip inside a
  longer video" features that consume these fingerprints.
* [external_tools_policy.mdx](./external_tools_policy.mdx) — why ffmpeg stays user-installed (§4.2),
  which is also what keeps the GPL-only MPEG-7 filter legally at arm's length (§D.2 below).

## The three fingerprint specs, and how they work together

Perceptual fingerprints are specified in three files. Each one owns one layer, and each layer talks only to
the layer below it. **You are reading perceptual_fingerprint.mdx, the engine layer.**

```
  Claude Code (chat)              Web app (browser)                Terminal
        │ stdio, JSON-RPC               │ signed-in session              │
        ▼                               │                                ▼
  lfb MCP server ── mcp.mdx             │                     lfb CLI ── cli.mdx
        │ X-LFB-Api-Key, loopback only  │                                │ X-LFB-Api-Key
        └───────────────────┬───────────┴────────────────────────────────┘
                            ▼
  REST API  /api/fingerprints/*  ── apis.mdx
  local API key · hybrid 200/202 jobs · lookup · compare · CSV export
                            │
                            ▼
  Fingerprint engine  ── perceptual_fingerprint.mdx §FD
  fingerprint.service → lfb-pdq Go sidecar (PDQ) + the user's own ffmpeg for video frames
                            │
                            ▼
  Postgres lfb.perceptual_fp + memory tier · CSVs in ~/T/_large_files_bridge/fingerprints/exports/
```

The CLI shares the same key and base URL, but today it calls `/api/files/list`, not the fingerprint routes.

| Spec | The question it answers | What it owns | What it leaves to the others |
| --- | --- | --- | --- |
| [perceptual_fingerprint.mdx](./perceptual_fingerprint.mdx) ◀ **this spec** | *What is a fingerprint, and what computes it?* | The research and the algorithm choice (PDQ for images, PDQ per frame for video); the match thresholds, quality floor and the video duplicate / subset rule; storage and the validity rule; the no-network guarantee. | How programs reach it (apis.mdx) and how Claude Code presents it (mcp.mdx). |
| [apis.mdx](./apis.mdx) | *How does any program ask for one?* | The local API key and machine-channel security; the endpoints; the hybrid sync/async job contract and its wait budgets; the error codes; the measured timings that justify the contract. | What a fingerprint means and when two match (perceptual_fingerprint.mdx); the Claude Code tools (mcp.mdx). |
| [mcp.mdx](./mcp.mdx) | *How does Claude Code ask for one?* | The eleven `lfb_` tools; the stdio transport; reply shaping (summaries, byte cap, pointer to the CSV); the playbook `ai/lfb_mcp.md`; registration with Claude Code. | Every answer (computed by the backend, apis.mdx) and creating the key (apis.mdx §3.2). |

**One request, end to end.** The user asks Claude Code: *"is clip.mp4 part of long.mp4?"*

1. Claude calls `lfb_fingerprint_compare` (mcp.mdx §5).
2. The MCP server re-reads the key from `~/.credentials/large_files_bridge.json` and sends
   `POST /api/fingerprints/compare` to `127.0.0.1:8787` (mcp.mdx §4).
3. The backend honors the key only from a loopback peer with a loopback Host header (apis.mdx §3.5).
4. For each file it reuses the stored fingerprint if the size, modification time and engine version are
   unchanged, or computes a new one through the `lfb-pdq` sidecar (perceptual_fingerprint.mdx §FD.3–§FD.4).
5. It compares the two frame lists. A shared fraction ≥ 0.8 is a **duplicate**; otherwise a longest matching
   run covering ≥ 0.7 of the shorter video is a **subset**, returned with its time range
   (perceptual_fingerprint.mdx §4, apis.mdx §7.8).
6. The MCP server wraps the answer in its JSON envelope (mcp.mdx §6), and Claude reports it as a
   **signal**. Nothing is deleted or moved because of a match.

**Where a change starts.**

* **A different algorithm, threshold or storage rule** → perceptual_fingerprint.mdx first. The API and the
  MCP server only carry the new values through.
* **A new capability for callers** → a backend endpoint in apis.mdx first, then an MCP tool that wraps it.
  The MCP server holds wrapper code only (mcp.mdx §1), so a tool can never be the first place something is
  computed.
* **How Claude Code behaves** (tool wording, reply size, what to do on an error) → mcp.mdx and
  `ai/lfb_mcp.md` only.

**A number used in more than one spec has one owner.** The others cite it; if they ever disagree, the
owner wins and the others are corrected.

| Number | Value | Owner |
| --- | --- | --- |
| Image match threshold (normal / strict) | Hamming ≤ 32 / ≤ 24 of 256 bits | perceptual_fingerprint.mdx §4 |
| PDQ quality floor | 50 (of 100) | perceptual_fingerprint.mdx §4 |
| Video duplicate / subset | shared fraction ≥ 0.8 / longest-run coverage ≥ 0.7 | perceptual_fingerprint.mdx §4 |
| When a stored value is still valid | same size, modification time and engine version | perceptual_fingerprint.mdx §FD.4 |
| Server wait budget (`wait_ms`) | default 20 s, maximum 55 s | apis.mdx §6.2 |
| MCP wait cap / MCP HTTP timeout | 50 s / 75 s | mcp.mdx §6 |
| MCP reply byte cap | 200 KB (up to 2 MB) | mcp.mdx §6 |

The shared threshold constants, in code:
`~/repos/LargeFileBridge/code/packages/shared/src/fingerprints.ts` — `PDQ_MATCH_THRESHOLD`, `PDQ_MATCH_THRESHOLD_STRICT`, `PDQ_QUALITY_FLOOR`.

(1–10, 10 best) computed by the equation in §D.4. Every proprietary, phone-home, or

monorepos, the commit count is for the **relevant sub-directory only**: `pdq/` in ThreatExchange and

**What the ranking says:**
* **PDQ holds the top six places.** It is delivered six different ways, which confirms the LOCKED image

## B. Best options for video — ranked comparison

**39 open-source options** that pass every hard gate (§D.1), sorted best first by the priority score.
This list mixes **visual** fingerprints, **audio** fingerprints (a video's soundtrack is a cheap, strong
second signal that finds a clip inside a longer video along with its offset), and **temporal aligners**
(VCSL: the algorithms that turn matched frames into a time range). Column **T** in the sub-scores
rewards the **subset / partial-match** capability. Proprietary and cloud options are in
[§Z](#z-excluded-options--proprietary-phones-home-or-copyleft-that-would-reach-our-code). Comparison-side
indexes (USearch, Faiss, hnswlib) are not fingerprints, so they are listed separately at the end of this
section.

**What the ranking says:**
* **PDQ per frame (vPDQ-style) is #1–#3**, which confirms the LOCKED video choice in §3. The frame list
  is exactly what [duplicates.mdx](./duplicates.mdx) and [subsets.mdx](./subsets.mdx) already store.
* **#4 VCSL's aligners** are the missing piece for an exact **"clip A is 00:41–01:12 of video B"** answer.
  They are MIT-licensed, small, and portable to TypeScript on top of the frame hashes we already keep.
* **Audio fingerprints** (#5 SoundFingerprinting, #6 Chromaprint) are the best **companion** signal:
  hundreds of times faster than realtime, with a built-in offset. They fail only when the audio has been
  stripped or replaced.
* **The MPEG-7 `signature` filter that powers subsets today ranks #10.** It is strong at finding
  subsets, but it is **GPL-only**, and it cannot compare *stored* signatures, only two inputs fed to the
  same ffmpeg run. Our use of it is lawful only at arm's length (§D.2). **Never port its matcher into our
  code, and never bundle an ffmpeg that includes it.**
* **The VSC2022 winners** (#17, #20, #21) are the state of the art on quality, but they are GPU ensembles
  of research code. They rank as they do because criteria 7–8 (speed, and running well alongside our
  stack) matter to us.

## FD. Final decision — what ships (images + video)

**Decided 2026-09-24.** One engine for both media types: **PDQ**, computed by the MIT-licensed
[ajdnik/imghash](https://github.com/ajdnik/imghash) Go v2 library inside our own single static Go binary
(`lfb-pdq`). This section **supersedes the "fallback ships today" line of §3** for the fingerprint service
described here. §3's LOCKED choice of PDQ for images and per-frame PDQ for video is unchanged; this section
now names the exact implementation of each.

| --- | --- | --- | --- |
| **Images** | [PDQ via ajdnik/imghash (Go v2)](https://github.com/ajdnik/imghash) | §A **#1**, **8.3** | The top-ranked option. A single static MIT Go binary with no C dependencies, and a very active codebase. |
| **Video** | [PDQ per frame on our own ffmpeg sampler](https://github.com/facebook/ThreatExchange/tree/main/pdq) (the same `lfb-pdq` binary, video mode) | §B **#1**, **7.5** | Chosen **on speed** from the three options scoring ≥ 7.4 (#1, #2, #3). **Measured fastest by 11–16×** on 4K (§FD.2). |

### FD.1 Images — PDQ via ajdnik/imghash

* **Pipeline.**
  * `sharp` decodes the file, applies the EXIF orientation, and resamples it to **128×128** with the aspect
    squashed. PDQ squashes every input to 64×64 itself, so squashing earlier loses nothing.
  * The pixels are composited over **white**, and, for an image with ≥ 0.5% see-through pixels, **also over
    black**.
  * The long-lived `lfb-pdq` sidecar returns the 256-bit PDQ hash as **64 hex**, plus the PDQ reference
    **quality** score (0–100). A transparent image gets a second hash, `value_alt`.
  * Formats `sharp` cannot read (for example HEIC on a build without the codec) fall back to an ffmpeg
    decode at the same 128×128.
* **Why 128×128 "fill" (measured).** 60 camera photos and 30 screenshots, each run through 7 transforms,
  under four pipelines:

  | Pipeline | Survives the transforms | ms/file | Sent to sidecar |
  | --- | --- | ---: | ---: |
  | old: ≤ 512 px "inside" | same as below | 65 | 545 KB |
  | **128×128 fill (chosen)** | as good or better on every transform | **53** | **48 KB** |
  | 64×64 fill, lanczos or cubic | slightly worse (p95 up to 18) | 50 | 12 KB |

  Measured on the chosen pipeline:
  * Survives resize to 50% + JPEG q75, resize to 25% + q40, JPEG q15, 320 px WebP q30, 160 px JPEG, and
    +10% brightness: median distance 2–4 bits, p95 ≤ 16 bits.
  * **No false matches:** of 4,005 pairs of *different* files, the only pairs ≤ 32 bits apart were real
    duplicate copies (0 bits).
  * A **3% crop breaks PDQ** (median 36 bits). That is inherent to global hashes; see §1.
  * The same frame size is used by the video path, so an image and a video frame showing it are hashed from
    comparable inputs.
* **Transparent images carry two hashes (measured).** A PNG with see-through pixels has no single look:
  one tool exports it to JPEG on white, another on black. On 5 screenshots with transparent window shadows:

  | Hash kept | vs a black-flattened JPEG copy | vs a white-flattened JPEG copy |
  | --- | --- | --- |
  | White only | missed **every** copy (median 64 bits) | matched |
  | Black only | matched | missed every copy |
  | Mid-gray | missed 3 of 5 | missed 1 of 5 |
  | **Both (chosen)**, nearer one wins | **matched** (median 2, max 10) | **matched** (median 4, max 6) |

  `value` is the white-background hash, and `value_alt` the black one. It is null for opaque images and all
  videos. Compare and the CSV use both.
* **Measured speed, 12-way:**
  * 229 PNG screenshots: **16 ms per image** (61/s);
  * 230 JPEG camera photos: **7.7 ms per image** (130/s), because JPEG is shrunk on load;
  * PDQ itself: 1–3 ms.

### FD.2 Video — the speed shoot-out between the three options scoring ≥ 7.4

The instruction was: pick whichever of the three top video options (score ≥ 7.4) **gets the work done
fastest**. All three were installed and run on this machine (24-core Apple Silicon, `ffmpeg` 9 from
Homebrew) against the same files, sampling **one frame per second**:

| Video | vPDQ (Meta) — #3 | Thorn `perception` — #2 | **Ours: PDQ per frame on our ffmpeg sampler — #1** |
| --- | ---: | ---: | ---: |
| 39 s, 1080p **HEVC 10-bit** (Dolby Vision), 48 MB | 4.9 s | 3.1 s | **0.5–0.6 s** |
| 205 s, **4K H.264**, 165 MB | 42.7 s | 28.2 s | **2.6 s** |
| 11 s clip, 2.7 MB | — | — | **0.7 s** |

**Result: #1 wins.** It is **16× faster than vPDQ and 11× faster than `perception` on 4K**, which is
**~78× realtime**, and **~5–8× faster on 10-bit 1080p HEVC** (~70× realtime). vPDQ and `perception` decode every frame at full
resolution and then throw most of them away. Ours avoids that work:

1. **Keyframes first.** `-skip_frame nokey` decodes only the intra frames. Most real encodes place one
   every 1–2 s, which already is our one-frame-per-second grid, so the ~97% of decode work spent on P/B
   frames is skipped.
2. **Hardware decode when it works.** On macOS the keyframe pass tries VideoToolbox first and scales on the
   GPU (`scale_vt`), so only a 128×128 frame is copied back.
   * This was 2.3× faster than software on the 4K file.
   * The frame is downloaded in the stream's own bit depth: **P010 for 10-bit**, NV12 for 8-bit. Asking for
     NV12 on the 10-bit Dolby Vision HEVC made VideoToolbox write nothing. With P010 that file decodes in
     hardware in 0.47 s instead of 1.1 s in software.
   * A codec/pixel-format pair that VideoToolbox still refuses falls back to software automatically. The
     pair is remembered for the life of the process, so a folder of such files pays for the failed attempt
     once. Every abandoned plan is listed in the result's `tried`.
3. **Tiny frames, no files.** ffmpeg pipes 128×128 raw RGB straight into the sidecar. There are no JPEG or
   PNG files per frame, no temp directory, and no second decode (PDQ reduces every frame to 64×64 anyway).
4. **Parallel hashing** across all cores while ffmpeg keeps decoding.

**Sparse keyframes** (a long-GOP encode, where any gap between samples is over max(5 s, 4 × interval))
trigger one **full-decode** pass instead. It is still fast: loop filtering is skipped and the frames stay
tiny.

**Hardware and software agree.** Frames decoded both ways differ by a median of **8 bits**, inside the
32-bit threshold, so a fingerprint's value does not depend on which decode path produced it:
* 4K H.264 (193 frames): p90 12, max 16.
* 10-bit HEVC through P010 (40 frames): p90 14, max 20.

**Timestamps start at 0.** Each frame's time is measured from the container's `start_time`. Many MPEG-TS
captures do not start at 0, and without this correction a subset's reported offset would be wrong by that
much, and the coverage check would see a phantom gap at the start.

The decode-plan ladder and the sparse-keyframe fallback, in code:
`~/repos/LargeFileBridge/code/sidecars/pdq/video.go` — `hashVideo()` (plans), `runPlan()` (ffmpeg → frames → PDQ), `coverageGap()` (the sparse test).

### FD.3 How the engine runs

* **One Go binary, both media.** Source: `code/sidecars/pdq/` (`main.go`: image mode and the NDJSON
  server; `video.go`: video mode). The `just build-pdq` recipe builds it into `code/sidecars/pdq/bin/lfb-pdq`,
  and `just build` / `just run` include that step. The binary is git-ignored build output. When it is
  missing, the backend runs one background `go build` itself.
* **One long-lived process.** The backend keeps a single `lfb-pdq --serve` child and matches replies to
  requests by id. The process:
  * is restarted on the next request if it dies, and every in-flight request is rejected with the exit
    reason and logged to `error.err`;
  * is stopped with the backend.
* **Version-stamped values.** Every stored fingerprint carries `algo_version`: the sidecar's
  `--version` plus the sampling knobs. A change to either makes every older row stale automatically.
* **Local only (§6 holds).**
  * The sidecar imports no network package.
  * ffmpeg runs with `-protocol_whitelist file,pipe` and a `file:` input, so even a playlist that
    references URLs cannot make it open a socket.
  * `fingerprints.no-network.spec.ts` enforces both on the source.

Spawning, the request/reply protocol, crash handling and the lazy `go build`, in code:
`~/repos/LargeFileBridge/code/packages/backend/src/modules/fingerprints/pdq-sidecar.ts` — `ensureChild()`, `pdqFromRgb()`, `pdqFromVideo()`, `buildPdqSidecar()`.

### FD.4 Storage and validity (Postgres)

* **Where.** Postgres table `lfb.perceptual_fp` (migrations `0018_perceptual_fp.sql` and
  `0019_perceptual_fp_value_alt.sql`), one row per file path. It holds `kind`, `algo` (`pdq` |
  `pdq-frames`), `algo_version`, `size_bytes`, `mtime_ms`, `value` (64 hex), `value_alt` (the
  black-background hash of a transparent image), `quality`, and for video: `frame_count`, `frames` (in the `.vpdq` line format
  `n,hex,quality,ts`), `duration_s` and `strategy`. It also records `compute_ms` and `computed_at`.
* **Validity rule.** A stored fingerprint answers for a file **only while the file still has the size and
  modification time it had when the fingerprint was computed, and the engine version still matches**. A
  file modified after its fingerprint was computed therefore reads as stale, and is recomputed and
  overwritten. A file that changes **during** its own fingerprinting is returned but **not stored** (a torn
  read never becomes a cached truth).
* **Single flight.** Two callers asking for the same unchanged file at the same moment (a directory job and
  an MCP call) share one computation.
* **Two tiers.**
  * **Memory tier.** A bounded in-process cache: 20,000 entries and 64 MB of frame lists. It makes repeat
    MCP and API calls instant.
  * **Postgres tier.** The durable store; it survives restarts and the web app reads it back.
* **No Postgres is not an error.** On a machine without Postgres (the app's documented `LFB_DB_MODE=auto`
  fallback) values are still computed and cached in memory, and each result says `stored: false`.
  Postgres failures go through `tryDb()`, which logs them (throttled) to `error.err` and never fails a
  request.
* **Why not `file_fingerprint` (0009).** That table is keyed by **content hash** and holds a single
  `bit(256)`. It is the sidecar-render plane's twin of the YAML `file.fingerprint`. This cache needs
  path-keyed validity without hashing a 4 GB video first, and it needs per-frame lists.

The validity test and both tiers, in code:
`~/repos/LargeFileBridge/code/packages/backend/src/modules/fingerprints/fingerprint.store.ts` — `isValid()`, `getStored()`, `putStored()`, `listStoredUnder()`.

### FD.5 Performance and the sync-vs-async question

These numbers decide whether an API call can simply wait for the answer: an image takes 10–40 ms, and a
video takes about 1–3 s per minute of 1080p and ~2.6 s for 3.5 minutes of 4K. So **one file, or a few
dozen, is answered synchronously**. A directory of thousands is not. The API therefore uses **one hybrid
contract**:

* **Every request becomes a job, and the call waits up to `wait_ms`** (default 20 s, maximum 55 s).
* **If the job finishes in time,** the caller gets every result in the same response (`200`).
* **If it does not,** the caller gets the job id and the results so far (`202`). The work continues in the
  background, and the caller long-polls the job.

This keeps a Claude Code MCP call inside its tool timeout and never cuts work off. The full reasoning and
the measured table are in [apis.mdx §6 and §8](./apis.mdx).

### FD.8 The bulk directory scan — in-process, on ~80% of the cores

**Added 2026-09-24.** The ask: *give it a directory, get back a CSV with one row per file, holding the full
path and the fingerprint, and be a lot faster.* The per-file path (§FD.3) answers one file per request, and
its gates allow 12 images and **3 videos** at a time. On the Charlie Kirk media sync (6,888 files, about
70 GB) it ran at about **5 files a second**: 5,000 files took 1,026 s. The videos set the pace.

**The design.** The fingerprint library (ajdnik/imghash) is Go, so the code that drives it is Go too, in the
same binary and the same process:

1. **One process per scan.** The backend starts `lfb-pdq --scan` and writes one JSON request to its stdin:
   the directory, recursive or not, the extension filter, which directories to skip, the worker count, and
   the stored values it already holds.
2. **The walk comes first.** Go walks the directory before it hashes anything. It never follows a symlink.
   It skips hidden folders, macOS bundles, and the skip lists the backend passes (the same `HARD_SKIP` every
   other walk uses, or a smaller set when the caller asks). It keeps only files whose extension passes the
   filter. A 2,000-file tree walks in about 0.1 s, so the total is exact from the start.
3. **The longest work goes first.** Before hashing, Go probes every video's duration with ffprobe, in
   parallel, at a few ms each. Videos then run **longest first**, followed by images, largest first. It is
   duration, not bytes: ordered by size, an 80-minute talk of only 0.38 GB started late and was the whole
   tail of the run (430 s against 375 s ordered by duration).
4. **The worker count is a share of the cores.** The default is **80% of the logical cores**: 19 on the
   24-core tower. A caller can set `cpu_percent` or an exact `workers` count instead. Each worker takes the
   next file and calls the PDQ library in-process on its own goroutine.
   * **Images** are decoded in the same process (`image_native.go`), with the same steps as the per-file
     path: a 128×128 fill resample using premultiplied area averaging, EXIF orientation, then flattening
     on white (`value`) and, for a transparent image, on black (`value_alt`). The Go decoders read jpeg,
     png, gif, still webp, bmp and tiff.
   * **HEIC, AVIF, animated WebP**, and anything else the Go decoders reject are **deferred**. The backend
     sends them through the per-file sharp path after the scan, in the same job, so no file loses its
     fingerprint.
   * **Videos** use the same ffmpeg keyframes-first sampler as the per-file path (`video.go`). Only
     ffmpeg's thread count changes. Each video gets threads in proportion to its share of all the video
     duration, never fewer than `cores / workers`. A full decode (keyframes too sparse) gets **half the
     cores**, because it is always the tail. Giving it every core measured worse (446 s against 375 s for
     the mirror), because the extra threads only add contention.
5. **The bytes decide the pipeline.** The same 16-byte sniff as `media-sniff.ts` runs on every file, so a
   JPEG named `.mp4` is hashed as an image.
6. **Results stream back.** Each file produces one NDJSON line. The backend turns each line into an ordinary
   result, stores it in L1 and Postgres (§FD.4), and writes the job's CSV when the scan ends.
7. **Stored values are reused.** Files whose stored value is still valid (same size, modification time and
   engine version) are listed in the request. Go answers them from that list without opening them.
8. **Online-only cloud files are left alone.** A Dropbox or iCloud placeholder (macOS `SF_DATALESS`) is
   reported as `not_downloaded` and never opened, because reading it would force a download. A caller can
   opt in to reading them.
9. **One scan at a time.** Each scan already uses about 80% of the machine, so a second scan waits for
   the first to finish (`waiting_for_slot`). Callers should scan several directories one after another,
   never in parallel.

**Same values, not merely similar ones** (measured 2026-09-24 on the Charlie Kirk mirror):

* **Videos: identical.** 324 of 324 videos gave the same representative value and the same frame
  count as the per-file path. Both paths run the same Go sampler, and ffmpeg's thread count never changes
  the decoded pixels. The 100-video benchmark set matched frame for frame at 2 and at 12 threads.
* **Images: the same family, a few bits apart.** Across 1,672 JPEG, PNG, WebP and GIF files the Go decoder
  was a median of **2 bits** from sharp's value (p90 6, p99 10, max 16, out of 256). 422 were exactly
  equal, and **none** was farther than the strict 24-bit threshold. Both decoders gave `value_alt` to exactly the
  same images. So both carry the **same** `algo_version` (`… image:fill128+alpha2`), and either one's stored
  value is valid for the other. A value's `strategy` tells them apart: `go-area` for the Go decoder, blank
  for sharp.

**Measured speed** (the 24-core tower, while other sessions were also using it):

| Work | Per-file path (before) | Bulk scan (after) |
| --- | ---: | ---: |
| 1,672 mirror images | 6.5 s (259/s) | 6.4 s (262/s) |
| 100 mirror videos, 2.6 GB (90 keyframe passes, 10 full decodes) | 116.8 s | **62.9 s** (1.9×) |
| The whole mirror, 1,997 files, 22 GB | 550.1 s | **375.5 s (1.47×)** |

What the numbers say:

* **Images were never the bottleneck.** sharp's shrink-on-load keeps the per-file path at about 260
  images a second, and the Go decoder matches it.
* **The gain is in videos:** 19 at a time instead of 3, the largest first, and more ffmpeg threads for the
  tail.
* **The hardware decoder does not limit it.** On the 100-video set, VideoToolbox-first took 69.8 s and
  software-only took 73.1 s at 19 workers.
* **Fewer workers is not better.** 8 workers took 72.1 s.
* **Past 80% of the cores, workers only fight.** 24 software workers took 92.2 s.
* **The floor is the slowest single video.** On the mirror, the four slowest were long 1080p AV1 files with
  sparse keyframes, from 32 to 80 minutes. The M2 has no AV1 hardware decoder, so each needs a full
  software decode of every frame. The slowest was a 70-minute file at about 374 s. The old path decoded
  it in 164 s, because it had the machine nearly to itself; the bulk scan finishes everything else in
  the same window. A 14-minute AV1 talk alone took 28 s at 12 threads, 45 s at 4, and 37 s at 24.
* **Next speedup, not done:** fewer frames to decode for sparse-keyframe AV1. That would change which
  frames are sampled, so it needs an engine version bump and a recompute. It is not a scheduling change.

## C. Goal

**Produce, for every image and video, a small persistable text value** (a hex string, a line-oriented
frame list, or a small JSON blob) that **recognizes the same content across damage**. Two files that are
*fundamentally the same image* or *the same footage* must match even when one of them has been
downscaled to a lower pixel resolution, recompressed (even heavily), converted between formats or
codecs, re-timed, or lightly damaged. Two different images or clips must not match.

Concretely, the fingerprint must be:

1. **Persistable as text.** It is stored in the per-file YAML sidecar and in `duplicates.csv` as a
   string. The compare step must never need the original media bytes again
   ([duplicates.mdx](./duplicates.mdx), requirement 3).
2. **Resilient.** It survives the transforms in §1: resize, recompress, format and codec change, and
   frame-rate change.
3. **Subset-aware for video.** It can tell *"B is the same video as A"* apart from *"B is a shorter piece
   cut out of A"*. Ideally it also says **which time range**.
4. **Fast to compare at scale.** One query against **100,000** stored fingerprints must return quickly.
   The compare function should ideally be **plain TypeScript** (Hamming distance / popcount over hex, or
   cosine over a small float vector). Needing the library's own matcher is acceptable but scores lower.
5. **Fast and high-quality to generate.** Generation may run in **any language** (Rust, Go, C++, Python)
   as a sidecar, CLI, native addon, or WASM, provided it runs well alongside our Node app.
6. **Entirely local, legally clean, and open-source.** These are the hard gates in §D.1.

## D. Assessment criteria and the priority-score math

Every option is first put through the **hard gates** (§D.1). An option that fails any gate is
**excluded** and moved to [§Z](#z-excluded-options--proprietary-phones-home-or-copyleft-that-would-reach-our-code),
with no score. Every surviving option then gets a **1–10 sub-score on each criterion**, calibrated by the
anchor tables in §D.3, and the equation in §D.4 folds those sub-scores into one **1–10 priority score**.

| Gate | Rule | Fails, for example |

| **G1 — Open source only** | The code **and any model weights** must be under an OSI-approved license. ### D.2 The legal assessment of copyleft (criterion 1)

> This is an engineering reading of the licenses and the FSF's published interpretation, written to
> decide *which integrations are safe to build*. It is not legal advice; if we ever want to ship a copyleft
> component **inside** our distribution, get counsel first.

The question for every copyleft license is: **does our use create a single "combined work" with it, or
are they two separate programs?** Only a combined work spreads the license to our code.

| Integration mode | Permissive (MIT / BSD / Apache / ISC) | Weak copyleft (LGPL / MPL-2.0) | Strong copyleft (GPL-2/3) | Network copyleft (AGPL-3) |
| --- | --- | --- | --- | --- |
| **Linked into our process**: npm package, napi/Node native addon, WASM compiled into our bundle, Rust crate compiled in | ✅ keep the notice | ⚠️ LGPL: OK **only** if dynamically linked and the user can swap the library (WASM/static embedding is the risky case). MPL: OK, file-level only | ⛔ **combined work → our code becomes GPL.** Gate G3 fails | ⛔ same, plus §13 |
| **Separate program**: CLI / sidecar we `spawn`, talking over argv, stdin/stdout, or files | ✅ | ✅ | ✅ *"mere aggregation"*, as long as it is a genuinely separate program. **Our code stays ours.** Obligations apply only to the GPL binary itself, and only if **we distribute it** | ✅ as for GPL, if we run it **unmodified**. §13 only triggers when a **modified** AGPL program serves users over a network, which matters for the future hosted Large File Bridge |
| **User-installed** (e.g. `brew install`, never shipped by us) | ✅ | ✅ | ✅ We distribute **nothing**, so we have **no obligations at all**. This is ffmpeg's posture ([external_tools_policy.mdx §4.2](./external_tools_policy.mdx)) | ✅ same |
| **Porting / translating its code into TypeScript** | ✅ keep the notice | ⚠️ the port is LGPL/MPL-covered | ⛔ **a translation is a derivative work → GPL** | ⛔ |

How this is applied:

* **The FSF's own line** ([GPL FAQ — "mere aggregation"](https://www.gnu.org/licenses/gpl-faq.html#MereAggregation)):
  pipes, sockets and command-line arguments are normally communication between two separate programs.
  Exchanging complex internal data structures, or loading into the same address space, makes them one
  program. **A napi addon or a WASM module is the same address space. A `spawn`ed CLI is not.**
* **Distribution is what triggers GPL obligations.** Large File Bridge's repo is public, so vendoring a
  GPL binary in it would be distribution. Letting the user install it (Homebrew) is not.
* **The ffmpeg MPEG-7 `signature` filter is GPL-2.0-or-later.** It only exists in ffmpeg builds
  configured with `--enable-gpl`. The user-installed Homebrew ffmpeg we call as a separate process is one
  of those builds.
  * **This is lawful as used today:** it is a separate program that the user installed, and we
    distribute nothing.
  * **Two things would break that:** (a) bundling a GPL ffmpeg in our distribution, or (b) porting
    `signature_lookup.c` into TypeScript so we can compare stored signatures. **Both are forbidden.**
  * A permissive aligner (VCSL, MIT) over PDQ frame hashes is the clean route to the same capability.
* **Mixed-license repos are judged per component.** czkawka's `czkawka_core` / `czkawka_cli` are MIT,
  but the Krokiet and similario GUIs are GPL (through the Slint UI library): use only the MIT crates.
  Chromaprint's own code is MIT, but the library as a whole is LGPL-2.1 (it bundles FFmpeg code), so
  use it as the `fpcalc` CLI.
* **Model weights are licensed separately from code.** SSCD, DINOv2 and CLIP weights are MIT/Apache and
  pass. ISC2021 and LAMV are CC-BY-NC and fail G1. For OpenCLIP, check each weight set.
* **Patents.** Apache-2.0 grants an express patent licence; MIT/BSD are silent. This is scored as a
  small plus inside criterion L. It is not a gate.
* **Surviving copyleft still costs points.** A GPL/AGPL tool that passes G3 only because we would run it
  as a separate program scores **L = 2–3**. That reflects the permanent discipline it imposes (never
  vendor it, never port it, never modify it for a hosted deployment).

### D.4 The equation

For each option, over the criteria its medium uses (images: Q R P H C L M A S Y I; video adds T):

```
H = min(Q, P)                                   # quality×speed synergy — high only when BOTH are
S = clamp(1, 10, round(2 · log10(stars + 2·forks)))
A = step(commits_last_12_months)                # table in §D.3
Y = step(years_since_first_release)             # table in §D.3

weighted_mean = Σ ( w_c · s_c ) / Σ w_c          # Σ w = 88 (image) or 92 (video)
quality_factor = 0.70 + 0.03 · Q                 # Q=10 → 1.00 · Q=9 → 0.97 · Q=7 → 0.91 · Q=5 → 0.85

PRIORITY SCORE = round( weighted_mean · quality_factor , 1 )      # 1–10, 10 best
Any failed hard gate (§D.1) → excluded (listed in §Z), no score.
```

**Why a quality multiplier on top of the weighted mean?** Without it, a very popular, very active
project running an *old* algorithm (a dHash tool with 10k stars) could out-rank a best-in-class
algorithm with a smaller community, because maintenance, stars, age and install ease add up. You were
explicit that we want *"the best algorithms, not an old one that's not considered the best."* The
multiplier caps what community signals can buy: an otherwise-perfect Q = 5 option tops out at 8.5.

## 1. What "fundamentally the same content" must survive (LOCKED requirements)

The fingerprint is judged against the transforms the product actually performs and encounters:

| Transform | Must still match? | Why it happens in LFB |
| --- | --- | --- |
| **Resize / lower resolution** | ✅ yes | A 4K master and a 1080p export of the same clip/still. |
| **Re-compression** (same format, lower quality) | ✅ yes | Our own compress pass ([compression.mdx](./compression.mdx)); re-exports. |
| **Codec re-encode** (ProRes→H.264, etc.) | ✅ yes (video) | Our compress pass targets a smaller codec. |
| **Frame-rate change** (video) | ✅ yes (video) | Re-timed exports. |
| **Format conversion** (PNG→JPEG, HEIC→JPEG) | ✅ yes (image) | The PNG→compressible and HEIC→JPEG conversions ([compression.mdx](./compression.mdx), [charter](../CLAUDE.md)). |
| **Heavy crop / large arbitrary rotation** | ⚠️ best-effort | Degrades for *every* global perceptual hash; we do not rely on it (the learned descriptors in §A/§B — SSCD, DINOv2 — are the future answer). |

**"Resize" here does not contradict compression.mdx's "we never downscale."** They govern different
things, and the two specs say so on purpose ([to_fix.mdx §3.4](./to_fix.mdx)):

* **"Never downscale"** ([compression.mdx §1](./compression.mdx)) governs the **compressed output file** —
  a **user's file** must never lose resolution.
* The row above is the opposite direction: it is the **input variety** the fingerprint must **survive** —
  someone *else's* 1080p export of our 4K master must still match.
* The fingerprint's **own** downscale is **internal to its decode** — in the older blockhash path,
  `sharp.resize(512, 512, { fit: "inside" })`; in the PDQ fingerprint service, a 128×128 fill (§FD.1).
  Either way it shrinks a throwaway pixel buffer purely to bound what we hash. It **writes no file**,
  **touches no output**, and is **invisible to the user**; resize-invariance (the row above) is precisely
  what makes hashing the shrunken copy legitimate.

The internal, output-free downscale is in code:
`~/repos/LargeFileBridge/code/packages/backend/src/modules/media/perceptual.service.ts` — `decodeForHash()`

**Do not "fix" this into agreement with compression.mdx.** A reader who mistakes `decodeForHash()`'s
resize for a violation of "never downscale" will delete it — which decodes every image at **full
resolution** and restores a **~105 MB-per-file memory bomb** on a path that runs many files at once.

The fingerprint's job is to let LFB say *"the compressed `trees.mov` is the same content as the original
`trees.mov`"* and *"this 1080p JPEG is the same image as that 4K PNG,"* so a compress/convert is verified,
duplicates across variants are recognized, and a decision made about one variant can be **matched to the
same content across a rename or a compress/convert** ([decisions.mdx §3.2](./decisions.mdx)).

## 3. The choice (LOCKED)

* **Images → PDQ (256-bit).** The open, permissively-licensed heir to PhotoDNA: transform-robust
  (resize/recompress/format-convert, plus free flip/90°-rotate variants), ships a **quality score** to
  skip flat/junk images, is a compact **32 bytes** for our per-file YAML, and matches on a single integer
  **Hamming distance**. Run locally via the **Rust `pdqhash` crate** wrapped in a **napi-rs** native
  addon, or compiled to **WASM** to avoid a native build in CI; decode pixels with **`sharp`** first.
* **Video → vPDQ (per-frame PDQ).** Reuse the *same* PDQ primitive on **frames sampled by the user-installed
  `ffmpeg`** (start ~1 fps or scene-change keyframes). Two videos are "the same content" when a high
  fraction of frames match within the image threshold. One hashing primitive covers both media types.
* **Fallback with zero native build → blockhash-core + sharp-phash.** To ship before the napi/WASM PDQ
  binding exists, use **blockhash-core at `bits:16`** (256-bit, MIT, pure JS/WASM) with `sharp` for
  decoding, optionally cross-checked by **sharp-phash** (64-bit DCT, MIT, built-in Hamming helper). The
  sidecar can hold **both** a `pdq` and a `blockhash` value during the transition; matching migrates to
  PDQ once the binding lands.
* **Audio.** Audio has no PDQ; a perceptual **audio** fingerprint is out of scope for v1 — audio files
  carry only the exact content hash plus (optionally) a transcript ([Transcribe.mdx](./Transcribe.mdx)).
  Reserve an `audio` fingerprint slot for later.

**The §A / §B ranking confirms this choice.** PDQ holds image ranks #1–#6, and per-frame PDQ holds
video ranks #1–#3. It also dates two follow-ups, neither of which changes this LOCKED decision:
* The fallback that ships today (blockhash-core, image #29) should give way to PDQ via the Go sidecar
  (image #1) or the napi-rs Rust crate (image #4).
* A TypeScript port of a VCSL aligner (video #4) would give subsets an exact time range without the
  GPL-only MPEG-7 filter (§D.2).

**Update (2026-09-24): the final implementation is decided in [§FD](#fd-final-decision--what-ships-images--video).**
The fingerprint service, the REST API and the MCP server all run PDQ through the `lfb-pdq` Go sidecar
(ajdnik/imghash). The blockhash fallback below remains only in the older consumers listed in §FD.7.

The algorithm choice and matcher are isolated behind one module so the fallback→PDQ swap is a one-file change, in code:
`~/repos/LargeFileBridge/code/packages/backend/src/modules/media/perceptual.service.ts` — `fingerprintImage(buf)` / `fingerprintVideo(path)` (ffmpeg-sampled) / `hammingDistance(a, b)` / `sameContent(a, b, opts)`.

## 4. Matching — Hamming distance + thresholds (LOCKED)

* **Compare by Hamming distance** over the 256-bit fingerprints (count of differing bits). Smaller =
  more similar; identical content → 0.
* **Image threshold:** treat Hamming **≤ 32 / 256** as "same content"; expose a stricter **≤ 24** for
  high-precision de-dup. Always gate on the PDQ **quality** score — the floor is **50 of 100**; flat or
  low-quality images below it are dropped from automatic matching to avoid false hits.
* **Video threshold:** a video pair is "the same content" when the **fraction of frames** whose PDQ
  matches within the image threshold exceeds a high bar (vPDQ's shared-frame logic), which naturally
  survives codec/fps/resize changes. The shipped values:
  * **Duplicate:** the shared-frame fraction, measured in both directions, is **≥ 0.8**.
  * **Subset:** not a duplicate, but the longest run of matching frames covers **≥ 0.7** of the shorter
    video. The run gives the time range: where it starts in each video and where it ends in the longer one.
* **This section owns these numbers.** The API ([apis.mdx §7.1, §7.8](./apis.mdx)) and the MCP playbook
  report them; they do not set them.

The thresholds and quality floor, in code:
`~/repos/LargeFileBridge/code/packages/shared/src/fingerprints.ts` — `PDQ_MATCH_THRESHOLD`, `PDQ_MATCH_THRESHOLD_STRICT`, `PDQ_QUALITY_FLOOR`.

The duplicate / subset decision for two videos, in code:
`~/repos/LargeFileBridge/code/packages/backend/src/modules/fingerprints/fingerprint.router.ts` — `POST /compare`, using `symmetricSharedFraction()` and `longestSharedRun()` from `modules/videos/vpdq.service.ts`.
* **Never auto-act on a perceptual match.** Consistent with the charter, a fingerprint match is a
  **signal** LFB surfaces (e.g. "this looks like the same content as X"); it never deletes, replaces, or
  alters a file on its own.

## 5. Storage — per file, in the sidecar (LOCKED)

**Two stores, two jobs.** This section is the **tracked, per-file record** that travels with a repo's
tracking state. The PDQ fingerprint service's **Postgres cache** (§FD.4) is a different thing: a path-keyed
cache that answers API and MCP calls quickly and never travels. Moving the older consumers onto PDQ (§FD.7)
is also when the sidecar's `fingerprint` field switches from `blockhash` to `pdq` values.

The fingerprint is stored per file in the `<name>.yaml` sidecar
([repo_tracking_scheme.mdx §3](./repo_tracking_scheme.mdx)) and referenced from `files.yaml`. Both the
sidecar and the fingerprint are **Category-B tracking state** ([artifact_placement_policy.mdx](./artifact_placement_policy.mdx)):
they live in **Local Storage** at `~/T/_large_files_bridge/repos/<repoKey>/files/<path>.yaml` — always,
**never** the working repo's `.lfbridge/` — and are additionally mirrored to the company/Personal **sync
repo** when it is enabled:

```yaml
# ~/T/_large_files_bridge/repos/<repoKey>/files/videos/trees.mov.yaml
file:
  # …identity…
  fingerprint:
    algo: pdq                 # pdq (image) | vpdq (video) | blockhash (fallback)
    value: a1b2c3…            # 64-hex (32 bytes) for pdq/blockhash
    quality: 96               # PDQ quality score (image); low quality → excluded from auto-match
  # video variant instead carries a frame list (kept in a sidecar file when large):
  # fingerprint: { algo: vpdq, frames_ref: ~/T/_large_files_bridge/repos/<repoKey>/files/videos/trees.mov.vpdq }
```

* **Complements, never replaces, the exact hash.** The exact content `hash` proves *byte identity*; the
  perceptual `fingerprint` proves *content identity across transforms*. Both live on the file. The
  before/after pair captured around a compress/convert ([compression.mdx](./compression.mdx)) uses this
  same field: `fingerprint_before` should match `fingerprint_after` within threshold, which is how LFB
  **verifies a compression preserved the content**.
* **Size.** A PDQ/blockhash fingerprint is **32 bytes** — trivial inline in YAML. A per-frame vPDQ list
  can be large; when it is, store it in a small **`.vpdq` sidecar file** beside the `<name>.yaml` in Local
  Storage (`~/T/_large_files_bridge/repos/<repoKey>/files/…`, never the working repo) and keep only a
  reference inline.

## 6. Wiring it with zero network access (LOCKED)

* **All hashing is pure local computation** on decoded pixel/frame buffers (Rust/WASM or JS). None of the

* **The only external process is the user-installed `ffmpeg` binary** ([external_tools_policy.mdx §4.2](./external_tools_policy.mdx))

* This is enforceable and must be **verified**: the perceptual module has **no HTTP client, no fetch, no
  socket** and is covered by a test that fails if it gains one — the same "nothing phones home" guarantee
  the charter demands of the IPFS posture and the AI-provider boundary.

Guaranteeing the perceptual path never performs network I/O (no client imported; ffmpeg invoked with local paths only) is asserted in code:
`~/repos/LargeFileBridge/code/packages/backend/src/modules/media/perceptual.service.ts` — plus the guard test `perceptual.no-network.spec.ts`.

## 7. Acceptance criteria

1. LFB computes a **transform-robust perceptual fingerprint** for **image and video** files that survives
   resize, re-compression, codec re-encode, frame-rate change, and format conversion (§1).
2. The chosen algorithm is **PDQ (256-bit) for images** and **vPDQ (per-frame PDQ) for video**, with a
   **blockhash-core + sharp-phash** no-native-build fallback that remains only in the older consumers
   (§FD.7); **Microsoft PhotoDNA is explicitly not used** for the reasons in §2.
3. Everything runs **entirely locally with no network access** — no phone-home, no external service, no
   sending bytes or fingerprints anywhere; the only external process is the **user-installed ffmpeg** for frame
   sampling (§6). A guard test enforces this.
4. Matching is by **Hamming distance** with the **≤ 32 / 256** image threshold (stricter ≤ 24 available)
   plus a **quality gate**, and a **shared-frame fraction** for video (§4). A match is a **signal only** —
   LFB never auto-acts on it.
5. The fingerprint is stored **per file** in the `<name>.yaml` sidecar (32 bytes for pdq/blockhash; a
   `.vpdq` sidecar reference for large frame lists) — Category-B tracking state in **Local Storage** at
   `~/T/_large_files_bridge/repos/<repoKey>/files/…` (never the working repo; mirrored to the sync repo when
   enabled — [artifact_placement_policy.mdx](./artifact_placement_policy.mdx)) — **complements** the exact
   content hash, and is the field the compress/convert **before/after** pair uses to verify content was
   preserved (§5).
6. The candidate rankings in §A (images, ≥ 30 options) and §B (video, ≥ 30 options) are **sorted by the
   §D.4 priority score**, every input sub-score is published in the sub-score tables, and every option
   that fails a hard gate (§D.1) is listed **only** in §Z, never in a ranked table.
7. No integration may **link, embed, port, or vendor** a GPL/AGPL component (§D.2). A copyleft tool is
   usable only as a separate, user-installed, unmodified program.
8. The final engines are the ones in §FD: **PDQ via ajdnik/imghash** for images, and **PDQ per frame on
   our own ffmpeg sampler** for video (the fastest of the ≥ 7.4 options, by measurement).
   * Results are stored in Postgres `perceptual_fp` and are valid only while the file's size and mtime
     and the engine version are unchanged.
   * They are reachable from the web app (the directory and file menus), the REST API
     ([apis.mdx](./apis.mdx)) and the MCP server ([mcp.mdx](./mcp.mdx)).

These are **out of the ranked lists on purpose** and carry **no score**. Each fails at least one hard
gate from §D.1. They are recorded here so nobody re-proposes them without seeing why.
