# LargeFileBridge — The Git Backbone Engine

A storage's small, travelling text — its descriptor, its device registry, its mapped-directory list, its
IPFS manifest, and its expensive-to-generate derived artifacts — has to get **between the user's
computers**. For most storages the vehicle for that text is a **Git repository**: the
[Syncable Data Location](./syncable_data_location.mdx) *is* a little Git repo, and Git is exactly the
tool for versioning small text and reconciling edits made on two machines at once.

This spec is the **authoritative** description of how LFB drives that Git repo. When the user turns the
**Git backbone** on for a storage ([storage_settings.mdx §4.1](./storage_settings.mdx#41-dedicated-git-repo-preferred-when-available)),
they are **granting LFB permission** to run the real Git commands on that repo — **`git fetch`,
`git merge` (with automatic merge), `git add` / `git commit`, and `git push`** — on **every pin pass**.
Nothing else in the product moves the SDL's YAML between computers; this engine does.

Read the shared model first; this spec does not restate it:

* [storage_settings.mdx §4.1](./storage_settings.mdx#41-dedicated-git-repo-preferred-when-available) —
  the per-storage setting that **turns this backbone on** and holds the remote (a local path or a URL).
* [storage_personal.mdx](./storage_personal.mdx) — the **canonical use case**: one user, two computers,
  one Personal Git repo, the same repo configured on both. That spec drives every requirement here.
* [syncable_data_location.mdx](./syncable_data_location.mdx) — **what** travels (the SDL's YAML
  inventory, §2) and the **trust/reconcile** rule this engine obeys when two devices edit at once.
* [devices.mdx](./devices.mdx) — the **self-owned** `devices/<device>.yaml` files that are the main
  thing this engine commits and pushes; self-ownership is what makes auto-merge safe (§4).
* [pin_process.mdx](./pin_process.mdx) — the **full pass** this pull/merge/push cycle runs inside,
  once per storage that has a Git backbone.

## 1. What LFB is permitted to do — the granted Git operations (LOCKED)

Turning on the Git backbone for a storage is an **explicit, user-confirmed grant**. Until the user
enables it and supplies a remote, LFB runs **no** Git command against that storage beyond the
already-existing `git init` of a brand-new dedicated repo. Once enabled, LFB has permission to run — and
**only** — this closed set of operations against **that one configured repo**:

| Operation | Command | When | Why |
| --- | --- | --- | --- |
| **Fetch** | `git fetch <remote>` | start of every pass | pull down what the user's *other* computers pushed |
| **Merge** | `git merge --no-edit` (ort strategy) | after fetch, if the remote advanced | fold the other computers' SDL edits into this working copy, **automatically** |
| **Stage** | `git add <this device's own files>` | after local changes | queue only **this** device's self-owned files (§4) |
| **Commit** | `git commit --no-edit` | if anything is staged | record this device's SDL edits |
| **Push** | `git push <remote> <branch>` | after commit | send this device's edits to the user's other computers |

Two hard boundaries the charter imposes (§7):

* **Only the user's own configured repos.** LFB fetches/merges/pushes **exactly** the repo the user
  pointed a storage's Git backbone at — never a repo it merely *discovered*, never a third party's repo,
  never a public one. This is the Git analogue of the charter's *no-public-relay* posture: we move
  **our own** content between **our own** machines, nothing else.
* **Never destructive without cause.** LFB never runs `push --force`, never `reset --hard` a user's
  work, never `clean` their tree. The only writes it makes are the additive commit of its own files and
  a fast-forwardable push; anything it cannot reconcile it **surfaces**, it does not overwrite (§3.3).

The granted operation set, gated behind the per-storage "Git backbone enabled" flag, is implemented in code:
`~/repos/LargeFileBridge/code/packages/backend/src/modules/git/git.service.ts` — `GitBackbone` class (`fetch()`, `merge()`, `commitSelf()`, `push()`); the enable gate is read from the per-storage settings by `~/repos/LargeFileBridge/code/packages/backend/src/modules/storage/storage-settings.service.ts` — `readStorageSettings()` (`backing.dedicated_repo`).

## 2. The library — `simple-git` over the system git binary (LOCKED)

LFB does **not** re-implement Git. It shells out to the **system `git` binary** through
[`simple-git`](https://www.npmjs.com/package/simple-git) — a thin, pure-JavaScript, promise-based
wrapper with **no native bindings**. This is a locked decision; the alternatives were evaluated and
rejected:

| Library | Verdict | Reason |
| --- | --- | --- |
| **`simple-git`** ✅ | **chosen** | Wraps the installed `git` CLI, so **real Git does the merge** — the modern **ort** recursive strategy with rename detection, exactly what "handle automatic merge" requires. ~8M weekly downloads, actively maintained, pure JS (no build step), and it reuses the same `git` LFB already calls for `git init`. |
| `isomorphic-git` | rejected | A pure-JS re-implementation. Its merge is **limited** — fast-forward and simple 3-way only, weak on renames, and it **throws** on cases real git would resolve. We must not hand the user's history to a partial merge engine. |
| `nodegit` | rejected | Native **libgit2** bindings — painful, fragile installs across macOS/Linux and Node versions. Heavy for what we need, and still not the canonical git merge. |

Because the merge is performed by the **real `git`** the user already has, LFB inherits git's full,
battle-tested conflict resolution, its `.gitattributes` merge drivers (§4.2), and its credential
handling (§5) for free. The requirement — *"find the right library … and let it handle all the Git
commands, including automatic merge"* — is met by delegating to git itself and orchestrating it with
`simple-git`.

The `simple-git` dependency (added to the backend workspace) and the single wrapper that all Git operations flow through are in code:
`~/repos/LargeFileBridge/code/packages/backend/src/modules/git/git.service.ts` — `openRepo(workingDir)` returns a configured `SimpleGit` instance (system-git, non-interactive env). Declared in `~/repos/LargeFileBridge/code/packages/backend/package.json` — `dependencies.simple-git`.

## 3. The two remote shapes — a local path vs. an HTTP(S) URL (LOCKED)

When the user turns the Git backbone on for a storage they supply a **remote**. LFB accepts **two
shapes**, and the difference is the whole reason this section exists — one is already a working tree on
this computer, the other is not.

### 3.1 A local file path — a checked-out working tree on this box

The common case in the [Personal use case](./storage_personal.mdx): the user has **already cloned/created**
the Git repo on this computer (e.g. `~/BGit/Bryan_git/personal_large_files_bridge/`) and points the
storage's Git backbone at **that local path**.

* LFB treats that directory **as the working copy** — it reads and writes the SDL YAML there directly,
  and runs `fetch` / `merge` / `commit` / `push` **in place** against whatever `origin` the user's clone
  already has.
* This is the preferred, simplest shape: the user manages the clone; LFB just keeps it pinned. Because
  the repo is a real checkout, the user can also inspect it with their own Git tools.

### 3.2 An HTTP(S) URL — a Git server not mapped to the local filesystem

The user may instead give a **URL** — `https://github.com/BryanStarbuck/personal_large_files_bridge.git`
or any Git server — **without** a corresponding local checkout. *"Sometimes people will add an HTTP URL,
and we have to go talk to that Git server without it being mapped to the local file system."* LFB then
owns the working copy:

* On first use LFB **clones the URL into a machine-local working-copy cache** under the state root —
  `~/T/_large_files_bridge/pin/s/<storage_id>/git/` — a hidden checkout LFB manages, **not** a place
  the user browses. (This cache is machine-local scaffolding, exactly like the rest of
  [storage_local.mdx](./storage_local.mdx); wipe it and the next pass re-clones.)
* Every pass thereafter runs `fetch` / `merge` / `commit` / `push` inside that cached checkout, against
  the configured URL as `origin`.
* The SDL YAML that other parts of LFB read is resolved to **that cache path** for a URL-backed storage,
  vs. the user's own checkout for a local-path storage. Everything downstream (devices, manifest,
  analysis) is indifferent to which shape produced the working copy.

### 3.3 Both shapes converge on one working copy

After resolution, both shapes yield a single **working directory** the rest of the engine operates on: a
user-managed checkout (local path) or an LFB-managed cache clone (URL). §4–§6 are written against that
working directory and do not care which shape it came from.

Resolving the configured remote to a working directory — using the local path in place, or clone-on-first-use / open-thereafter for a URL — is handled in code:
`~/repos/LargeFileBridge/code/packages/backend/src/modules/git/git.service.ts` — `resolveWorkingCopy(storageId, remote)` (returns `{ dir, origin }`; clones a URL remote into `pin/s/<id>/git/` via `resolveStateDir()`, opens a local path directly). The remote itself (kind + value) is persisted per-storage by `~/repos/LargeFileBridge/code/packages/backend/src/modules/storage/storage-settings.service.ts` — `writeStorageSettings()`.

## 4. Automatic merge — why conflicts are rare, and how git resolves them (LOCKED)

The load-bearing requirement: *"deal with any merge."* Two of the user's computers can edit the same SDL
repo before either has pulled the other's push. LFB must **fetch, merge automatically, and push** without
the user ever hand-resolving a conflict in the normal case. Three things make that true.

### 4.1 Self-owned files rarely collide

The SDL is deliberately structured so that concurrent edits land in **different files** (the trust rule
of [sync_list.mdx §5](./sync_list.mdx#5-trust--reconciliation--the-load-bearing-rule),
[devices.mdx §2.1](./devices.mdx#21-a-device-file-is-self-owned-trust)):

* A computer **writes only its own** `devices/<device>.yaml`. Two computers editing the registry at the
  same time touch **two different files** — git merges them with **no conflict at all** (a clean union of
  two added/modified paths).
* `pinned_by` claims, schedules, and grafts are all **per-device**, so the same rule holds for them.

This is why *"we're making a unique device … then it won't conflict with other devices"* is true at the
Git level, not just conceptually: self-ownership maps directly onto per-file, non-overlapping commits.

### 4.2 Append-mostly shared lists merge by union

A few files are genuinely **shared** — the per-repo **`manifest.yaml`** (large-file → CID + pin state) and
the per-file **`decisions.yaml`** ledger. These are **Category-B** tracking state
([artifact_placement_policy.mdx](./artifact_placement_policy.mdx)): they live in **Local Storage** always and
travel through this backbone as the additive **sync-repo mirror** at `<syncRepo>/repos/<repoKey>/` — **never**
committed into a working code repo. For them, LFB installs a **`.gitattributes`** in the sync repo that marks
them `merge=union`, so git **keeps both sides' lines** instead of conflicting when two computers — or two
**teammates** — append different entries. LFB then folds the merged file on the next read (the manifest is a
set keyed by path/CID; the decision ledger is an **append log folded to
latest-`decided_at`-per-`(sid,path)`** — [decisions.mdx §5](./decisions.mdx)), so a union followed by the
fold is always correct and a **ten-person team never resolves a decision conflict by hand**.

```gitattributes
# <syncRepo root>/.gitattributes  (written by LFB when it enables the Git backbone)
repos/*/manifest.yaml   merge=union
repos/*/decisions.yaml  merge=union
```

**The union is the transport, not the reconciliation.** Git's `merge=union` keeps both computers' lines so
the *file* never conflicts; what LFB then believes is decided by the **per-entry merge** that reads the
result — union by `path`, union `pinned_by`, newer `modified_at` wins a CID conflict, absence never a
delete, this computer's own pin claim re-derived from its real pinset
([storage_company.mdx §8.4.3](./storage_company.mdx#843-receiving-is-a-merge-never-a-copy-locked),
[sync_list.mdx §5.7](./sync_list.mdx#57-the-sync-repo-mirror--keyed-by-remote-merged-on-every-pull-locked)).
A union-merged file that is then **copied** wholesale into Local Storage throws that away — which is exactly
what happened. The fold belongs in step 4 of the cycle, immediately after the merge (§6).

**The union patterns are matched by filename, so the mirror's rekey is free.** The subtree a repo's tracking
mirrors to is now keyed by the repo's **normalized git remote** — `repos/<repoUid>/`, not the machine-local
`repos/<repoKey>/` ([storage_company.mdx §8.4.1](./storage_company.mdx#841-a-repos-shared-identity-is-its-remote-never-its-path-locked)).
The attribute lines LFB writes are bare filenames (`manifest.yaml`, `decisions.yaml`), which git applies at
**any depth**, so the rekey needs **no** `.gitattributes` change — but a future pattern that anchors a path
segment would silently stop union-merging the mirror, and that is a defect to hunt for.

The union-merge patterns (bare filenames, matched at any depth, so both `repos/<repoKey>/` and `repos/<repoUid>/` are covered) are in code:
`~/repos/LargeFileBridge/code/packages/backend/src/modules/git/git.service.ts` — `UNION_MERGE_PATHS` written by `GitBackbone.ensureMergeAttributes()`.

### 4.2.1 The sync repo's committed tracking payload must never be git-ignored (LOCKED, learned from a defect)

This backbone drives a **sync repo** — a dedicated `*_large_files_bridge` company/Personal tracking repo
whose *whole reason to exist* is to carry LFB's **Category-B** tracking state
([artifact_placement_policy.mdx](./artifact_placement_policy.mdx)). Because a sync repo **is an SDL** — a
dedicated LFB file repo — it has **no `.lfbridge/` directory at all**; its root *is* the `.lfbridge` area
([artifact_placement_policy.mdx §0](./artifact_placement_policy.mdx)). So its committed payload sits at the
**repo root**: the `repos/<repoKey>/` subtrees (manifest, decisions, sidecars, history, `repo_storage.yaml`)
plus the SDL's own **root metadata** — the **device registry** (`<sdl>/devices/<device>.yaml`,
[devices.mdx](./devices.mdx)), `storage.yaml`, `mapped_dirs.yaml`, `files.yaml`, `manifest.yaml`,
`bookmarks.yaml`, and `analysis/`. That payload must be committable — the invariant below exists because it
was **violated in production** and it broke the entire two-computer story:

> **The defect (provenance — do not lose this).** The generic storages rule *"keep `.lfbridge/`
> git-ignored"* ([storages.mdx §4](./storages.mdx#4-where-a-storages-state-lives--the-kind-split-then-category-a-vs-category-b-locked)) was
> applied to **every** git-backed storage root, so LFB wrote a bare `.lfbridge/` line into the **sync
> repo's** `.gitignore`. That silently made `git add -A` stage **nothing** under `.lfbridge/`: each computer
> wrote its `devices/<self>.yaml` to disk, committed only `.gitattributes`, and **pushed no device file at
> all**. Two computers each pushed nothing about themselves, so **neither ever saw the other** — the symptom
> "I'm not seeing my other computer."
>
> **What changed, and what did not.** Under [§0](./artifact_placement_policy.mdx) the sync repo no longer has
> a `.lfbridge/` for that line to hit — but **the hazard did not go away, it moved**: an ignore rule that
> swallows the SDL's **root metadata** or its **`devices/` directory** reproduces the exact same silent
> failure. The lesson is unchanged; only the path it applies to is.

The rule this locks in: **for a Git backbone, the sync repo's tracking text is the payload that must
travel** ([storage_personal.mdx §1](./storage_personal.mdx#1-anatomy-of-the-personal-storage)) — only the
big-file **bytes** are ignored, and those never live in the sync repo. So **before every commit** the
backbone **strips any ignore line that would swallow the SDL's committed tracking text** — its root metadata
(`devices/`, `storage.yaml`, `mapped_dirs.yaml`, `files.yaml`, `manifest.yaml`, `bookmarks.yaml`,
`analysis/`), its `repos/<repoKey>/` subtrees, and a **legacy bare `.lfbridge/` line** (still stripped: a
not-yet-migrated SDL may hold content there until `migrateSdlLfbridge()` runs, §0.3). This heals a sync repo
that a prior build (or the user) wrongly ignored. It is a **design smell to hunt for**: any code path that
git-ignores the very tracking text a Git backbone exists to carry.

> **A plain working code repo is the opposite case — and it never git-ignores `.lfbridge/`.** A `repo`-type
> code repo is the one kind that **does** keep a `.lfbridge/` (§0: LFB is a guest there, so it quarantines
> its files in one hidden corner). It is **never** a Git backbone for tracking state: its Category-B state
> goes to Local Storage (+ the sync repo), **never** committed into the code repo. Its committed
> `.lfbridge/` holds only the **Category-A** content — transcripts + AI descriptions — that is *meant* to
> travel with the repo ([artifact_placement_policy.mdx §1.1](./artifact_placement_policy.mdx)), so it must
> never be git-ignored either. Both kinds keep their tracking text **committed**; they simply put it in
> different places (code repo → `.lfbridge/`; SDL → the root) and carry different payloads.

Ensuring the tracking text is committable on every backbone commit (strip any ignore over the SDL's root metadata / `devices/` / `repos/`, plus a legacy bare `.lfbridge/` line) is handled in code:
`~/repos/LargeFileBridge/code/packages/backend/src/modules/git/git.service.ts` — `GitBackbone.ensureSdlCommittable()` (called from `commitAndPush()` alongside `ensureMergeAttributes()`). The complementary fix — LFB no longer **adds** an ignore over its own tracking text for **any** storage: a company/Personal **sync repo** must commit its root payload, and a `repo`-type **code repo** commits its Category-A `.lfbridge/` content while its Category-B tracking state is written to Local Storage instead of the repo — is `~/repos/LargeFileBridge/code/packages/backend/src/modules/storage/storage.service.ts` — `reconcileLfbridgeIgnore(root, type)` (now `unignoreLfbridge` for every type; Category-B never lands in a working repo), called from `ensureStorage()` and `ensureBackingLocations()`. Which base directory a root's tracking text hangs off — and therefore what must stay committable — is resolved by storage **kind** in `~/repos/LargeFileBridge/code/packages/backend/src/modules/storage/storage-type.service.ts` — `trackingBaseDir(root, type?)` / `usesLfbridgeDir(type)`.

> **The user-facing Git Ignore action honors this too (LOCKED).** The **Git Ignore dialog**
> ([git_ignore.mdx](./git_ignore.mdx)) — the deliberate, user-driven way to git-ignore big files so they
> pin over IPFS instead of committing — writes **anchored, repo-root-relative** lines and **refuses to emit
> any line that would ignore LFB's own committed tracking text**: a `.lfbridge/` path in a **working repo**,
> or the **SDL root metadata** (`devices/`, `storage.yaml`, `mapped_dirs.yaml`, `files.yaml`,
> `manifest.yaml`, `bookmarks.yaml`, `analysis/`, `repos/`) in a **sync repo**. That is defense-in-depth
> against re-introducing this defect from the UI. It only ever **adds** big-file ignore lines; LFB's
> committed text it never touches ([git_ignore.mdx §5.3–§5.4](./git_ignore.mdx)).

### 4.3 The strategy, and the fallback when git truly cannot resolve

* LFB merges with git's default **ort** recursive strategy (`git merge --no-edit`), which resolves the
  overwhelming majority of real-world cases (including renames) on its own.
* ~~If — despite §4.1/§4.2 — git reports a **genuine conflict** it cannot auto-resolve, LFB does **not**
  guess and does **not** clobber. It **aborts the merge** (`git merge --abort`, leaving the working copy
  clean), records the conflicted paths, and **surfaces them in the UI** as a backbone problem on that
  storage, so the user can resolve it with their own Git tools.~~ **SUPERSEDED by §4.3.1** — abort-and-surface
  is now the **last resort**, reached only after the per-file resolution ladder has been applied to every
  conflicted path and something is genuinely left over. It is no longer the *first* thing that happens to a
  conflicted merge, and it is no longer allowed to freeze the whole storage.
* Reconciliation of *content* claims (a stale `pinned_by`, a superseded revision) still follows the SDL
  trust rules ([sync_list.mdx §5.3](./sync_list.mdx#53-conflicts-resolve-by-revision-then-content-then-time)); the textual fallback below is
  only for a conflict git itself declines **and** LFB has no rule for.

#### 4.3.1 The per-file resolution ladder — a conflict is always resolved (LOCKED)

The authority for **why** is [storage_company.mdx §11.1](./storage_company.mdx#111-a-conflict-is-always-resolved-never-surfaced-as-homework-locked)
— *waiting for the customer to resolve a conflict means it never gets resolved.* A tracking repo stuck
pending a human has stopped syncing. This section is the **engine's** half: what this backbone does with a
conflicted merge, file by file.

> **What the old behavior cost.** One unresolvable path aborted the merge, and `commitAndPush()` then
> refused to run, so a **single** conflicted file froze that storage's **entire** backbone — nothing
> merged, nothing committed, nothing pushed, every cycle repeating the same abort until a human ran git by
> hand. Worse, the only auto-resolution that existed applied **only when every conflicted path was a
> `repo_storage.yaml`**, so a lone sidecar in the same merge took the resolvable files down with it. The
> mirrored `repos/<repoUid>/` payload (§4.2) made mixed conflicts the common case rather than the rare one.

**Every path is resolved by what the file *is*, never by what else is in the same merge.** The four
resolutions, matching [storage_company.mdx §11.1](./storage_company.mdx#111-a-conflict-is-always-resolved-never-surfaced-as-homework-locked)'s
table one-for-one:

| Resolution | Applies to | What LFB does |
| --- | --- | --- |
| **`regenerate`** | `repo_storage.yaml` (any depth), `files.yaml` | Machine-generated caches whose authoritative copy is Local Storage — **drop the path from the merge**; the next pass rebuilds it. |
| **`ours`** | `devices/<device>.yaml`, `debug/<device>/…` | Self-owned (§4.1) — **keep this computer's copy**; other devices' files are different paths and are never touched. A debug export is self-owned the same way and is a disposable snapshot the user can retake, so "ours" loses nothing (the other side stays in git history). |
| **`union`** | `manifest.yaml`, `decisions.yaml`, `owner_map.yaml`, `LargeFilesBridge_SyncList.yaml`, `files/<rel>.yaml` sidecars, `history/<device>.txt` | Append-only lists. Reaching a conflict at all means the `merge=union` attribute was **not** in the tree when the merge ran (a fresh clone, a mid-migration repo), so LFB does the union **by hand** — strip the markers, keep **both** bodies, dedupe identical lines. A superset is always safe; losing a line never is. |
| **`null`** | anything with no rule | **Quarantined**, named, and surfaced — never a reason to stop the backbone. |

> **A missing rule is a stuck storage, not a cosmetic gap (proven live 2026-07-29).** `debug/<device>/…`
> had no rule. An add/add conflict on one debug export therefore hit the `null` row, and — because a
> quarantined path still aborts the merge — the company tracking repo aborted **every cycle**, logging
> *"1 conflicted path(s) have no automatic resolution"* and syncing nothing at all. The lesson is that
> **any LFB-owned path added later must be added to this ladder in the same change**; the ladder is only as
> complete as the last file someone introduced.

* **Per file, not per merge.** A mixed conflict resolves the files it can and escalates only the ones it
  genuinely cannot. Resolving nine of ten paths and finishing the merge is strictly better than abandoning
  all ten.
* **Finish the merge when nothing is left over.** With every conflicted path resolved, LFB commits the
  merge itself (`LFB: auto-resolved N merge conflict(s)`) and the cycle continues into commit + push. Only
  a **non-empty** unresolved list falls through to `merge --abort` + surface (§4.3), and even then every
  *other* file in the repo keeps syncing on the next cycle.
* **Never destructive.** Resolution only unions, regenerates, or picks a side and records it. No
  `reset --hard`, no `clean`, no force-push (§1) — the one thing ever discarded is a cache this computer
  can rebuild from Local Storage.

Classifying a conflicted path and applying its resolution is handled in code:
`~/repos/LargeFileBridge/code/packages/backend/src/modules/git/git.service.ts` — `resolutionFor(path)` (the `regenerate` / `ours` / `union` / `null` classifier) and `GitBackbone.resolveConflicts()` (per-path application, returning `{ resolved, unresolved }`), with the by-hand union in `GitBackbone.unionMergeFile()`; the attribute patterns that make most of this unnecessary in the first place are `UNION_MERGE_PATHS` (§4.2).

#### 4.3.2 A repo with no `origin` is a loud, standing fault (LOCKED)

The counterpart to "never fail silent". When a Git-backed storage has **no `origin`** — the normal state of
a freshly `git init`ed company storage ([storage_company.mdx §10.3](./storage_company.mdx#103-proposing-and-creating-the-company-storages-locked))
— the cycle used to commit, return with **no problem set and nothing logged**, and look **exactly like a
healthy repo with nothing to do**. The repo then accumulated local commits forever while the user believed
their computers were in sync.

* **Committed-but-unpushed is a first-class reported state**, not an absence. The cycle sets a problem and
  writes a WARN line naming the storage.
* **The user-facing wording is plain:** *"Large File Bridge is tracking this company locally, but it has no
  remote — nothing is reaching your other computers."* The fix is one click: add a remote (§3).
* **It is standing, not one-shot.** The fault persists on the storage's row until a remote exists; once one
  does, the always-push-when-ahead rule (§6.1) delivers everything that piled up.

### 4.9 Finding the git binary — and handing it to `simple-git` in a form it accepts (LOCKED)

Every git spawn resolves the binary to an **absolute path** once, up front, rather than relying on a bare
`git` and the caller's PATH. A background context — a launchd worker with no `EnvironmentVariables` block,
a Windows scheduled task, any supervisor that starts the backend with a minimal environment — can have a
PATH that omits the directory git lives in, and then every spawn fails with `spawnSync git ENOENT`.

**The Windows trap (performance.mdx §6.3, fixed 2026-08-06).** `simple-git` validates the custom `binary`
it is handed against `/^([a-z]:)?([a-z0-9/.\\_~-]+)$/i` and **throws out of its factory** when the value
does not match — no spaces, no parentheses. Git for Windows installs at `C:\Program Files\Git\cmd\git.exe`.
So `openRepo()` threw **before running a single command**, and with it every pull, commit, push, device
registration and mirrored-manifest reconcile on the platform, logged every ten minutes for weeks as

```
[pin] device registration for storage <id> failed: Invalid value supplied for custom binary,
restricted characters must be removed or supply the unsafe.allowUnsafeCustomBinary option
```

Nothing was wrong with the path. The direct `execFileSync(stableGitBin(), …)` callers had been using it
all along without complaint — which is exactly why only the `simple-git` paths broke, and why the failure
read as a storage problem rather than a path problem.

The rule: **where the resolved path is not one `simple-git` will accept, hand it the bare name and put the
resolved directory at the FRONT of the child's PATH instead.** Same binary, the same immunity to a thin
background PATH, through a door `simple-git` will open. `unsafe.allowUnsafeCustomBinary` — what the message
suggests — is *not* used: it only downgrades the throw to a `console.warn` on every construction and buys
nothing. The PATH write updates whichever key is already present (**Windows spells it `Path`**, and
spreading `process.env` keeps that spelling) rather than adding a second one the child would have to choose
between.

Binary resolution and the `simple-git` hand-off are in code:
`~/repos/LargeFileBridge/code/packages/backend/src/modules/git/git-bin.ts` — `stableGitBin()`, `isSimpleGitSafeBinary()`, `withGitOnPath()`; applied by `~/repos/LargeFileBridge/code/packages/backend/src/modules/git/git.service.ts` — `openRepo()`

## 5. Credentials for a URL remote — the OS git credential helper, never a prompt (LOCKED)

A local-path remote needs no credentials — it is a local checkout whose `origin` the user already
authenticated. A **URL** remote (§3.2) needs to authenticate to the Git server. LFB **never** invents
its own password prompt and **never** stores a plaintext password in its own config:

* LFB runs git **non-interactively** (`GIT_TERMINAL_PROMPT=0`) and lets git use the **OS credential
  helper** (macOS Keychain via `osxkeychain`) or an **already-configured token** in the URL/helper, the
  same way the user's own `git push` authenticates. If the user can `git push` that URL from a terminal,
  LFB can.
* If authentication **fails** (no cached credential, expired token), LFB **surfaces a clear "connect /
  re-authenticate this Git remote" problem** on the storage rather than hanging or retrying blindly —
  and simply keeps pinning over IPFS in the meantime (the Git backbone is an *additional* path, never
  the only one).
* This honors the charter's security posture: no secrets in LFB's own files, no phone-home, and the
  user stays in control of what LFB can reach.

Running git with a non-interactive, credential-helper-backed environment and turning an auth failure into a surfaced storage problem (not a hang) is handled in code:
`~/repos/LargeFileBridge/code/packages/backend/src/modules/git/git.service.ts` — `openRepo()` sets `GIT_TERMINAL_PROMPT=0` and inherits the OS credential helper; `push()` / `fetch()` classify an auth error into a `GitAuthProblem` surfaced by `pinStorageUnit(id)`.

### 5.2 An inherited ASKPASS variable must never reach a git child (LOCKED, learned from a defect)

"Non-interactive" is a property of the **environment we hand the child**, not only of the flags we pass —
and the environment we inherit is not ours. Every git child therefore has `GIT_ASKPASS`, `SSH_ASKPASS` and
the `VSCODE_GIT_ASKPASS_*` companions **deleted**, alongside the editor variables stripped for the same
reason (`NON_INTERACTIVE_ENV_STRIP`).

Two independent reasons, either sufficient:

* An askpass helper **is** a prompt, by another name. `GIT_TERMINAL_PROMPT=0` declares that this process
  must never block on one; leaving a helper wired up contradicts that declaration.
* `simple-git` treats either variable as an unsafe-config vector and **refuses to run git at all** unless
  `allowUnsafeAskPass` is opted in. We do not opt in — the point is to have no prompt, not to permit one.

**The defect (2026-08-12).** VS Code exports both variables into every integrated terminal and every child
of one, so a backend started from a terminal — the ordinary way this app is run in development — inherited
them, and every commit failed with `Use of "GIT_ASKPASS" is not permitted without enabling
allowUnsafeAskPass`. The affected machine had every service installed, enabled and firing on schedule, the
Scans page showed all of them green, and it had not committed once since setup: half a day of passes, its
own device file still untracked, `company discovery: 0 repo(s) with your commits`. The failure appeared only
in `log.log`. **A job that fails every cycle must not render as a healthy job**
(see `background_processing.mdx`) — the green check that outlived total failure is what cost the day.

## 6. The backbone cycle — where Git runs inside the pass (LOCKED order)

Every storage that has the Git backbone enabled runs **one Git cycle per pin pass**
([pin_process.mdx §2](./pin_process.mdx#2-every-pin-pass-is-a-full-pass-locked)), in this fixed
order, wrapped around the storage's normal reconcile + IPFS byte work:

1. **Resolve the working copy** (§3) — local path in place, or clone/open the URL cache.
2. **`git fetch`** — bring down what the user's other computers pushed.
3. **`git merge` (auto)** — fold their SDL edits into this working copy (§4); on an unresolvable
   conflict, abort + surface and continue with IPFS-only for this pass.
4. **Reconcile against the merged SDL** — now that the incoming devices/manifest/analysis are merged in,
   run the storage's normal reconcile ([pin_process.mdx §5](./pin_process.mdx#5-what-a-pass-does-per-unit--and-what-the-opt-in-gates)):
   fetch/pin the marked CIDs to their **grafted** local paths ([devices.mdx §4](./devices.mdx#4-the-graft--machine-independent-hierarchy--local-paths-locked)),
   inherit derived artifacts, write this device's own `devices/<device>.yaml`, update `manifest.yaml`.
   **This is also where a pulled `repos/<repoUid>/` mirror is folded into Local Storage by per-entry merge**
   ([§4.2](#42-append-mostly-shared-lists-merge-by-union),
   [storage_company.mdx §8.4.3](./storage_company.mdx#843-receiving-is-a-merge-never-a-copy-locked)) — on
   **every** pull, not on demand.
5. **`git add` (self-owned only) → `git commit`** — stage **only this device's** files (§4.1) plus any
   shared list this device appended to, and commit if anything changed. Nothing to commit → no empty
   commit.
6. **`git push`** — send this device's commit up. On a **non-fast-forward reject** (another computer
   pushed between our fetch and our push), LFB **re-fetches, re-merges (§4), and re-pushes** — the
   standard pull-then-push retry — rather than force-pushing. ~~once~~ **SUPERSEDED by §6.3: the budget is
   three attempts with backoff.**

The cycle is **idempotent** and safe to run every 15 minutes: with nothing changed on either side it
fetches, finds nothing to merge, stages nothing, and pushes nothing.

**The device-registration worker reuses this exact cycle on its own 10-minute cadence.** The dedicated
every-10-minute device write-back ([devices.mdx §11](./devices.mdx#11-the-device-registration-write-back--every-10-minutes-locked))
runs a **narrowed** version of steps 1–3 + 5–6 — resolve → **fetch → auto-merge** → write **only** this
device's own `devices/<self>.yaml` → commit → push — for every Git-backed storage, **whether or not** the
storage is opted into IPFS pinning. Its step 2 fetch+merge runs **every 10 minutes even when this computer
has nothing to change**, so device edits made on another computer are pulled down. Because it and the
15-minute pass share one process, both take a **per-storage lock** so they never run git on the same
working copy at once (`~/repos/LargeFileBridge/code/packages/backend/src/modules/pin/pin.service.ts`
— `ensureDeviceRegistered(id)` under `withStorageGitLock`).

Driving this ordered cycle for each Git-backed storage inside the full pass — fetch/merge before reconcile, commit/push after, with the non-fast-forward retry — is handled in code:
`~/repos/LargeFileBridge/code/packages/backend/src/modules/pin/pin.service.ts` — `pinStorageUnit(id)` calls `GitBackbone.pull()` (fetch+merge) before `runUnitPin(...)` and `GitBackbone.commitAndPush()` after, both from `~/repos/LargeFileBridge/code/packages/backend/src/modules/git/git.service.ts` (`pull()`, `commitAndPush()` with the fetch-merge-push retry). Only storages whose `backing.dedicated_repo.enabled` is true run the cycle; the rest pin over IPFS alone.

### 6.0 The cycle must SAY which step it is on (added 2026-08-06)

A `git fetch` or `git push` over a slow link is minutes of complete silence: nothing is written locally and
no log line lands until it returns. The pin pass waiting on it showed a spinner, so "pulling your other
computers' changes" and "wedged" looked identical from the user's chair — the 2026-08-06 report.

Each step of the cycle therefore reports a **phase line** ([webapp.mdx §12a](./webapp.mdx)) onto whichever
progress card is driving it: `git: fetching your other computers' changes` → `git: merging them in` →
`git: resolving 3 conflicts` → `git: staging this computer's changes` → `git: pushing (attempt 2 of 3)`.
The §6.3 backoff **waits** are named too (`git: waiting 4s before push attempt 2 of 3`) — a deliberate
pause the user can see is not a hang. A cycle **queued behind another on the same storage's lock** says so
rather than spinning.

The hook is **optional at every call site**: a caller with no card passes nothing and the cycle behaves
exactly as before — no cycle ever depends on being watched.

*Reported in:* `~/repos/LargeFileBridge/code/packages/backend/src/modules/git/git.service.ts` —
the `GitPhaseNote` callback threaded through `GitBackbone.pull()` / `pullInner()` / `pullReadOnly()` /
`commitAndPush()` / `commitAndPushInner()`; *supplied by:*
`~/repos/LargeFileBridge/code/packages/backend/src/modules/pin/pin.service.ts` —
`pinStorageUnit(id, onPhase)` / `syncStorageText(id, onPhase)`, whose `onPhase` writes into that storage's
per-unit detail on the pass card (`pinAll()`), with `storageGitLockBusy(id)` in
`~/repos/LargeFileBridge/code/packages/backend/src/modules/git/git-lock.ts` supplying the
"waiting for the git cycle already running on this storage" line.

### 6.1 Always push when the branch is ahead — deliver stranded / foreign commits (LOCKED, learned from a defect)

Step 6's push must fire whenever the local branch is **ahead of the remote — for ANY reason** — not only
when *this* pass produced its own commit. This is a locked correctness rule because its absence stranded a
commit in production (the [2026-07-07 incident](./backbone_resilience.mdx#8-the-incident-that-motivated-this-spec-2026-07-07)):

> **The defect.** `commitAndPush()` staged the tree and, **if nothing new was staged, returned before it
> ever called `git push`.** So a branch that was *already* ahead of the remote — because something OTHER
> than LFB had committed into the repo (a machine-wide `git add -A && git commit` auto-commit), or a
> prior push had failed and left the commit local — was pushed **only if this pass also happened to make
> its own commit.** A stranded commit sat unpushed while the other computer advanced the remote; the two
> diverged and never reconverged.

The rule: after the (possibly empty) stage-and-commit, LFB computes the **ahead-count**
`origin/<branch>..HEAD`; if it is **greater than zero it pushes**, regardless of whether this pass
committed anything itself — delivering LFB's own commit, a foreign committer's commit, a merge commit, or
a commit left behind by an earlier failed push. The non-fast-forward retry (step 6) still applies. LFB
must **not** rely on the device write-back's `updated_at` churn to force a push (it usually does, which is
what *accidentally* masked the bug); a pass that legitimately writes nothing must still deliver a branch
that is ahead. This is the Git-layer half of the broader resilience contract in
[backbone_resilience.mdx §6](./backbone_resilience.mdx#6-always-push-when-the-branch-is-ahead-locked-learned-from-a-defect)
(and its §4 foreign-committer coexistence rule).

Attempting the push whenever the branch is ahead of the remote — not only after a fresh local commit — via an ahead-count check is handled in code:
`~/repos/LargeFileBridge/code/packages/backend/src/modules/git/git.service.ts` — `GitBackbone.commitAndPush()` (pushes when `result.committed` OR `aheadCount(branch) > 0`) and its helper `GitBackbone.aheadCount(branch)` (`git rev-list --count origin/<branch>..HEAD`, treating a missing upstream ref as "push to establish it").

### 6.2 A mirror write nudges its SDL's backbone — debounced (LOCKED)

Steps 5–6 fire on a **timer**. A tracking mirror written *between* ticks therefore sits in the sync repo's
working tree, uncommitted, until the next 15-minute pass or 10-minute device write-back happens to run —
so a decision the user just made can take ten minutes to leave the machine. **The write is the trigger:**
after LFB mirrors a repo's tracking state into `<syncRepo>/repos/<repoUid>/`, it **announces that write to
the SDL it wrote into**, which schedules a **debounced** commit + push of that storage — the same mechanism
durable artifacts already use. Rule owned by
[storage_company.mdx §8.7](./storage_company.mdx#87-four-smaller-defects-this-use-case-also-closes):

* **Debounced, never per-write.** A pin pass mirrors many files; each announcement coalesces into **one**
  commit + push per storage, so the SDL does not get a commit per file.
* **The nudge is additive, not a replacement.** The timer cycle (§6) still runs, and a missed nudge is
  covered by the next tick — this only removes the *latency*, never the guarantee.
* **The debounced push is the ordinary §6 cycle** — fetch → auto-merge → commit → push, with the
  always-push-when-ahead rule (§6.1) and the non-fast-forward retry. It is **not** a second, weaker path.
* **It announces the destination it wrote into — a path inside the SDL.** `noteArtifactWritten()` resolves
  the owning storage by **root prefix**, so announcing the *working repo's* root would find nothing
  (`charlie-kirk` is not inside `act3_large_files_bridge`) and the nudge would silently no-op. The mirror
  step therefore announces **`dst`**, the mirror destination under `<syncRepo>/repos/<repoUid>/`, which it
  already knows — and the prefix lookup lands on the right SDL. This trap is **avoided**, not removed:
  prefix resolution stays fragile precisely because its failure mode is a silent no-op, so never hand
  `noteArtifactWritten()` a path outside the storage you mean.

Announcing a mirror write to its SDL so the backbone commits + pushes it on a debounce is handled in code:
`~/repos/LargeFileBridge/code/packages/backend/src/modules/pin/sync-trigger.service.ts` — `noteArtifactWritten()` (resolves the storage by root prefix via `storageIdForPath()`, which is why it is handed the SDL-side destination), invoked from `~/repos/LargeFileBridge/code/packages/backend/src/modules/storage/tracking-sync.service.ts` — `mirrorToSyncRepo()` (passes `dst`, not the repo root).

### 6.3 The push retry budget — three attempts with backoff (LOCKED)

Step 6's retry is **three attempts, not one**. A single retry loses to any peer that pushes twice while we
are working — and on a **shared company repo with several members** that is an ordinary Tuesday, not an
edge case ([storage_company.mdx §11.4](./storage_company.mdx#114-push-retries)). It is also exactly what
[storage_personal.mdx §17.4](./storage_personal.mdx#174-stage-4--push-changed) already asked for; that rule
is now **built**, and this section is where the engine states it.

* **Backoff `0s / ~2s / ~8s`, JITTERED.** The first attempt is immediate; a peer's push usually lands
  within seconds, so a short then longer wait costs nothing when it works and buys the race when it does
  not. Each wait carries **±40% randomness**, because a *fixed* ladder is the same ladder on **every one of
  the user's computers**: two machines that collide once then retry in lockstep and collide again. Jitter is
  the only thing that can break that phase lock — no local lock can exclude another **computer's** push.
* **Every retry re-pulls first**, so we are always pushing on top of the newest remote state — running the
  full §4 merge including §4.3.1's per-file resolution. If that re-pull leaves something genuinely
  unresolvable, LFB **stops and surfaces** rather than pushing blindly.
* **Never a force-push**, at any attempt (§1).
* **Log the cause of every rejection.** The error was previously captured and never read, so an **auth
  failure** and a routine **non-fast-forward race** were indistinguishable in the log — and if a later
  retry succeeded, the fact that anything went wrong vanished entirely. Each attempt now logs its
  classification and its attempt number; a later success **clears** the earlier attempt's problem.
* **An authentication rejection is not retried at all.** Re-pulling cannot produce a credential, so the
  remaining attempts only widen the window in which other cycles queue behind this storage's lock. It is
  recorded and surfaced immediately (§6.4).
* **Exhausting the budget is not data loss.** The commit stays local, the fault is reported, and the
  always-push-when-ahead rule (§6.1) sends it on the next cycle — plus the re-arm and the user-visible
  record in §6.4.

The three-attempt push budget with backoff, its per-attempt re-pull, and its per-attempt logging are handled in code:
`~/repos/LargeFileBridge/code/packages/backend/src/modules/git/git.service.ts` — `GitBackbone.commitAndPush()` (the `ATTEMPTS` loop, each iteration calling `GitBackbone.pull()` before the next attempt); the jittered wait itself is `pushRetryDelayMs()` in the same file.

### 6.4 "Giving up this cycle" must never mean giving up (LOCKED)

A cycle that exhausts its budget has left this computer's tracking state **committed but unshared**: the
user's other computers do not learn about the new or changed large files, and every screen still looks
healthy. **A machine that has silently stopped sharing is the worst outcome this product has** — it is the
exact drift LFBridge exists to prevent. So exhaustion is a **fact**, not a log line:

* **It is recorded durably** in the state root (`~/T/_large_files_bridge/backbone-push-health.json`) with
  the storage, the backbone folder, the last push that *did* land, the consecutive-failure count, how many
  commits are waiting, and the remote's own complaint. Machine-local; it never travels.
* **The push is re-armed** on a jittered exponential backoff (≈1 min, doubling, capped at 15 min) for that
  one storage, so the queued commits leave minutes later instead of waiting on the 10–15-minute workers or
  on a page load.
* **A single successful push erases the record** and cancels the re-arm, so the warning self-clears the
  moment the machine is sharing again — the same rule as a missed worker cycle.
* **The user sees it.** The Scans page leads with *"This computer hasn't shared its file list with your
  other computers"*, names the backbone, says how long it has been, and says plainly that nothing is lost
  and Large File Bridge is still retrying.

The durable record, the jittered re-arm and the self-clearing rule are handled in code:
`~/repos/LargeFileBridge/code/packages/backend/src/modules/git/push-health.service.ts` — `recordPushFailure()`, `armUnpushedRetry()` / `unpushedRetryDelayMs()`, and `recordPushSuccess()`; the git cycle calls them from `GitBackbone.noteUnpushed()` in `git.service.ts`.

Surfacing it to the user is handled in code:
`~/repos/LargeFileBridge/code/packages/backend/src/modules/schedule/schedule.service.ts` — `jobsPageData()` (the `backbonePush` field), rendered by
`~/repos/LargeFileBridge/code/packages/frontend/src/pages/scans/ScansPage.tsx` — `BackbonePushCard` / `unsharedNote()`.

**Why there is no cross-process file lock for the git cycle.** Only one Large File Bridge backend can run
per computer (`shared/single-instance.ts`, `backend.lock`), and the launchd worker does no git of its own —
it POSTs a kick and the work runs inside that one backend
(`code/deploy/launchd/run-worker.mjs`). The in-process per-storage lock (`git-lock.ts`) and the working-tree
gate (`worktree-gate.ts`) therefore already serialize every git cycle on this machine. The pushes we lose
to come from the user's **other computers**, which no local lock can exclude.

### 6.5 A cycle must never manufacture its own conflicts (LOCKED, learned from a defect)

The retry, re-arm and reporting machinery above (§6.3, §6.4) exists for pushes lost to **another
computer's legitimate work**. It is not a licence to generate churn and then survive it. Every conflict the
app creates for itself costs a cycle its push, and the user experiences that as *"sometimes it just doesn't
pull and push."* Three rules, each learned from a live failure on 2026-07-29:

1. **A timestamp is not a change.** `writeYaml` stamps `updated_at: now` on every call, so re-writing an
   identical document still yields a byte-different file. `writeSelfDevice` runs on every device pass
   (10 min), every pin pass (15 min) **and** every artifact sync, for **every** storage — so each cycle
   committed a diff that was exactly one line, `-updated_at:` / `+updated_at:`. Self-owned state is
   therefore written **only when something other than the timestamp moved** — and the comparison that
   decides "moved" must be **canonical**, or the guard silently does nothing (§6.6.2). §6.6 generalizes
   this rule from the timestamp to **every** self-moving field, and enforces it at the commit itself.
2. **A machine-local fact never goes in a shared file.** Two computers can pin identical bytes under
   different CIDs (a legacy `Qm…` dag-pb add vs. a raw-leaves `bafk…`); those are different multihashes,
   so `canonicalCid()` cannot bridge them. Foreign-profile **adoption** used to write the local CID into
   the **shared** `manifest.yaml`, so two machines with different add profiles overwrote each other's
   entry on every pass, forever. The adoption is now recorded in a **machine-local** equivalence map and
   the manifest's CID is left exactly as the fleet recorded it.
3. **Two storages must not share one backbone.** Two clones of the same remote on one computer both write
   the same `devices/<self>.yaml` and both push to the same branch, so they reject each other every cycle.
   LFB does **not** silently disable one — which clone is real is the user's call — but it **names the
   collision every pass** so it appears in the fault trail and in a debug export.

Not re-writing an unchanged document is implemented in code:
`~/repos/LargeFileBridge/code/packages/backend/src/shared/store/yaml-store.ts` — `writeYamlIfChanged()`, used by `~/repos/LargeFileBridge/code/packages/backend/src/modules/storage/devices.service.ts` — `writeSelfDevice()`.

Keeping the adopted CID out of the shared manifest is implemented in code:
`~/repos/LargeFileBridge/code/packages/backend/src/modules/pin/cid-equivalence.service.ts` — `noteCidEquivalence()` / `pinsetHasContent()`, called from `~/repos/LargeFileBridge/code/packages/backend/src/modules/pin/pin.service.ts` — `runUnitPin()`.

Naming two storages that share one backbone is implemented in code:
`~/repos/LargeFileBridge/code/packages/backend/src/modules/pin/pin.service.ts` — `warnOnDuplicateBackbones()`, called at the top of `pushDeviceBackbone()`.

### 6.6 QUIET BY DEFAULT — the substantive-change gate (LOCKED, learned from a defect)

**The invariant.** *When the user did nothing we track, this computer adds nothing.* A machine that sat
idle — no file added, nothing compressed, no transcript, no AI description, no OCR, no decision changed —
must produce **zero commits and zero pushes**, indefinitely. It still **pulls** every cycle, so another
computer's work arrives normally; it simply has nothing of its own to say. Silence is the normal, expected,
healthy state of an idle computer, and this applies identically to the **personal** and the **company**
tracking repos.

**Why this is a correctness rule and not a tidiness preference.** Every needless commit costs something
real:

* On a **shared company remote** it is a chance to lose a push race. Two computers that both commit every
  cycle collide, re-pull, retry, and eventually log *"attempt 3/3; giving up this cycle"* — the user
  experiences that as *"sometimes it just doesn't pull and push"* (§6.3, §6.5).
* It makes `git log` **unreadable and unauditable**. A history in which 95% of commits mean nothing cannot
  answer *"when did this file arrive?"* — the question the history exists for.
* It burns bandwidth, remote storage, and battery on every one of the user's computers, forever.

**What was actually happening (measured live on the personal tracking repo, 2026-07-29):**

```
2,437 commits in 7 days  (~348/day)
  2,322  touches of devices/*.yaml     ← 95%
      3  debug exports                 ← user-initiated, legitimate
      1  merge commit
     ~1  each .ocr / .transcription     ← the actual work
and of the last 60 device commits, 58 had a ONE-LINE diff:
  -updated_at: 2026-07-29T16:19:36.456Z
  +updated_at: 2026-07-29T16:36:05.339Z
```

The remaining 2 were a 25-line rewrite of `ip_addresses` — the laptop's `fe80::` link-local addresses
coming and going. **Not one of those 2,320 commits carried a single thing the user did.**

#### 6.6.1 The transaction taxonomy — what may create a commit

A commit is justified by a **transaction of a kind this product tracks**, and by nothing else.

**SUBSTANTIVE — these, and only these, may create a commit:**

1. A file becomes **tracked / pinned to IPFS**, or stops being (a `sync` decision changes).
2. A file's **git-ignore decision** changes.
3. An **artifact is produced**: `.transcription`, `.ai_description`, `.ai_description_rejected`, `.ocr`.
4. A file is **compressed / converted**, or a compression is **declined** (the never-recompress record).
5. A tracked file's **content fingerprint** changes — a genuinely new, changed, renamed, or deleted file.
6. A **manifest CID** changes because content actually moved.
7. **Device identity** changes: the nice name, the minted id, the owner, the IPFS PeerID, the hardware
   model, the pin schedule, the graft.
8. A **user-initiated action** that is by definition a deliberate event — a debug export, an owner mapping
   accepted, a storage's settings changed.

**NEVER SUBSTANTIVE — these must never, on their own, create a commit:**

* `updated_at` and every other write-stamp or heartbeat. **A timestamp is not a change** (§6.5 rule 1).
* **Network addresses** — `primary_ip`, `ip_addresses`. A DHCP lease rotates and a laptop grows and drops
  `fe80::` link-local addresses as interfaces, VPNs and AirDrop come and go, all with no user involved.
* A file's **mtime/atime moving with its content unchanged** — reading, scanning, copying, and cloud-sync
  clients all touch timestamps. LFB tracks **content**, not stat metadata.
* A **scan/pass counter**, a "last checked" marker, or a re-derived cache written back identically.
* **Key reordering or schema-default fill-in** — a document that means the same thing.
* A **pull that brought another computer's work down.** Receiving is not authoring. The merge lands, the
  working tree changes, and this computer still has nothing of its own to commit.

#### 6.6.2 Two layers enforce it, and the second is the one that must hold

**Layer 1 — at the writer.** Self-owned state is written only when something other than a volatile field
moved. The comparison must be **canonical**: both sides normalized the same way, keys deep-sorted, volatile
paths removed, `undefined` treated as absent.

> **The trap that made the first fix a no-op.** The original guard compared
> `YAML.stringify(rawDiskDoc)` against `YAML.stringify(schemaParsedValue)`. Those are **never** textually
> equal even when they mean the same thing: a zod-parsed object carries the *schema's* key order and the
> schema's injected defaults (`home_user: ""`, `ip_addresses: []`), while the disk file carries the order it
> was last written in and none of the defaults it predates. The guard shipped, looked right, and changed
> nothing — the churn continued at exactly its old rate. **A change-detection comparison must normalize both
> sides through the same pipeline, and the test for it must prove CONVERGENCE**, i.e. that a repeated
> identical write goes quiet and *stays* quiet, not merely that one comparison returned false.

**Layer 2 — at the commit choke point.** Layer 1 is a per-writer discipline, and a discipline is only as
good as the next writer to be added. The backbone therefore refuses the commit itself: after staging, any
staged **modification** of an LFB-owned YAML whose canonical content equals `HEAD`'s — volatile paths
removed — is **reverted**, not merely un-staged (leaving it would re-stage it next pass). If nothing
substantive remains, **no commit is made and no push is attempted**.

This layer is what makes the invariant structural. A future writer that stamps a heartbeat costs a
redundant local write and **nothing more** — no commit, no push, no merge race.

**THE CHOKE POINT HAS TWO DOORS, AND BOTH ARE GATED (LOCKED, learned from a defect).** `commitAndPush` is
not the only path to a commit: the **pre-merge checkpoint** reaches one too. Before a merge, the cycle
stages and commits every dirty LFB-generated path so the merge is always legal (§4, the "your local changes
would be overwritten by merge" abort) — and that path originally had no semantic opinion about what it was
committing. So any volatile-only write that happened to be dirty *at pull time* became a commit, and then a
push, **before layer 2 ever looked at it**. That is not a narrow window: `repo_storage.last_scan` is
rewritten into the sync repo by the **scan** path (`mirrorToSyncRepo`), at moments with no relationship to
the git cycle, so the tree is routinely dirty with pure churn exactly when the checkpoint runs. A choke
point with a second door in it is not a choke point. The checkpoint therefore runs the same gate, and
commits only what survives it — while still leaving the tree clean, so the merge can always proceed.

Applies the gate to the pre-merge checkpoint, and commits only the paths that survive it, in code:
`~/repos/LargeFileBridge/code/packages/backend/src/modules/git/git.service.ts`, class
`GitBackbone`, methods `checkpointOwnWrites()` → `dropVolatileOnlyChanges()` → `stagedOwnPaths()`.
Regression test: `code/packages/backend/src/modules/git/checkpoint-quiet-gate.spec.ts`.

**Two boundaries the gate must never cross:** it only reverts a change it has **proven** meaningless, and
it only ever touches **LFB's own** files. A file LFB does not own, a **creation**, and a **deletion** always
keep their commit — an unknown file is never provably meaningless, and a vanished file is always news.

**A MERGE IS NEVER SUBJECT TO THE QUIET RULE (LOCKED, learned from a defect found while writing §6.6's
tests).** Mid-merge the commit being prepared is the **merge itself**, so the gate stands down entirely and
the merge commit is always made — **even when it staged nothing**.

> The defect: when §4.3.1's ladder resolves every conflicted path to **ours**, the index ends up identical
> to `HEAD`. The commit step tested "is anything staged?", saw nothing, and returned **without committing**
> — leaving `MERGE_HEAD` dangling. The repo is then **stuck mid-merge**: the next cycle's pull refuses to
> run (*"You have not concluded your merge"*), and that storage stops syncing until a human runs git by
> hand. This is a stuck-backbone fault of exactly the class §6.4 exists to prevent, and a device file
> resolved to "ours" is the **most common** resolution the ladder performs, so it is not an edge case.

The rule that falls out: **"nothing to say" and "nothing to finish" are different questions.** Quiet is
about whether this computer has news to author; concluding a merge is about leaving the repository in a
usable state. An unfinished merge is far worse than a redundant commit.

Always concluding an in-progress merge is implemented in code:
`~/repos/LargeFileBridge/code/packages/backend/src/modules/git/git.service.ts` — `GitBackbone.mergeInProgress()` (asked via `git rev-parse --git-path MERGE_HEAD`, never by joining `.git/`, so a linked worktree's gitlink file cannot hide it), consulted by both `dropVolatileOnlyChanges()` and the commit decision in `commitAndPushInner()`.

Not re-writing an unchanged document, canonically, is implemented in code:
`~/repos/LargeFileBridge/code/packages/backend/src/shared/store/yaml-store.ts` — `writeYamlIfChanged()` (which prepends `updated_at` to the caller's volatile list) and `canonicalize()`.

Declaring the device file's volatile network fields is done in code:
`~/repos/LargeFileBridge/code/packages/backend/src/modules/storage/devices.service.ts` — `writeSelfDevice()`, passing `volatile: ["device.hardware.primary_ip", "device.hardware.ip_addresses"]`.

Refusing a commit whose whole diff is volatile is implemented in code:
`~/repos/LargeFileBridge/code/packages/backend/src/modules/git/git.service.ts` — `GitBackbone.dropVolatileOnlyChanges()`, called from `commitAndPushInner()` immediately after `git add -A`, with the per-document volatile registry in `volatileYamlPathsFor()`.

**The "last checked" marker of §6.6.1 is `repo_storage.last_scan`**, and it is the volatile field with the
widest blast radius: every company/Personal SDL mirrors one `repos/<repoUid>/repo_storage.yaml` per tracked
repo, so a fleet of a hundred repos re-stamps a hundred files whenever a pass runs. The whole `last_scan`
block is volatile, not only its `at` — `on_device` and `headless` move with it every time a different
computer, or the background worker, takes the pass, so suppressing the timestamp alone would leave the churn
untouched. Both layers cover it, and layer 2 is the one that must hold: the writer-side scrub only runs on a
machine carrying that build, so a peer on an older one re-stamps the real value, the scrub blanks it again,
and the two ping-pong one commit per cycle until the whole fleet upgrades (§6.6.4).

Scrubbing the scan heartbeat out of the mirrored copy is implemented in code:
`~/repos/LargeFileBridge/code/packages/backend/src/modules/storage/tracking-sync.service.ts` — `scrubVolatileRepoStorage()`, called from `mirrorToSyncRepo()`; the receive side restores this machine's own stamp in `reconcileFromSyncRepo()` so a pull never blanks it and re-triggers a stale-scan re-scan.

Refusing a commit whose whole diff is the scan heartbeat is implemented in code:
`~/repos/LargeFileBridge/code/packages/backend/src/modules/git/git.service.ts` — `volatileYamlPathsFor()`, returning `["repo_storage.last_scan"]` for any `repo_storage.yaml` path (`isRepoStorageYamlPath()`, which matches the current `repos/<repoUid>/` mirror and the legacy `.lfbridge/` shape alike).

#### 6.6.3 Policing it — quiet is a health property, so measure it

Quiet is **easy to lose and silent when lost**: nothing breaks, no error is raised, and the only symptom is
a commit count nobody is looking at. It regressed twice in one day. So it is **measured**, not assumed.

* **The health signal is the commit rate on an idle computer.** On a computer where the user performed no
  substantive transaction, LFB's own commits over 24h must be **0**. A sustained rate above a handful per
  day with no matching user activity is a **defect**, and it is the first thing to check when a user reports
  the backbone misbehaving.
* **The diagnostic that finds it in one command** — for any tracking repo, the ratio of commits to
  substantive file touches:

  ```
  git log --since='24 hours ago' --format='%s' | sort | uniq -c | sort -rn
  git log --since='24 hours ago' --name-only --format='' | sort | uniq -c | sort -rn | head
  ```

  A single path dominating that list is churn until proven otherwise. Confirm by reading the diffs: if the
  changed lines are all one volatile key, it is churn by definition.
* **Regression tests own this permanently.** The idle-cycle test must run the **real** commit path over a
  **real** git repo across **repeated** passes and assert the commit count never moves —
  `~/repos/LargeFileBridge/code/packages/backend/src/modules/git/quiet-gate.spec.ts`, plus the
  convergence tests in `~/repos/LargeFileBridge/code/packages/backend/src/shared/store/yaml-store.spec.ts`.
  A single-comparison unit test is **not** sufficient evidence — it is exactly what passed while the live
  repo took 348 commits a day.

#### 6.6.4 A fix only counts once it is RUNNING on every computer

Both churn defects were fixed in the repo while the flood continued, because the machine doing the flooding
was running an **older build**. Live evidence on 2026-07-29: `bryan-mac-pro`'s device file carried the
volatile-hardware fields (new build) while `bryanstarbuck-macbook-pro`'s did not (old build) — and it was
the stale machine emitting a timestamp-only commit every ~16 minutes.

**So the fleet's build state is part of the diagnosis, not a footnote.** When churn is reported, identify
*which device file* is churning and confirm that computer is running a build that contains the fix, before
concluding anything about the code. A device file that is missing fields the current schema publishes is
the tell that its computer is stale.

### 6.7 A FIX THAT IS NOT RUNNING IS NOT A FIX — build staleness & self-update (LOCKED, learned from a defect)

**The rule.** LFB knows which build it is running, publishes it so the rest of the fleet can see it, keeps
its own checkout up to date, and **says out loud** when this computer or any of the user's other computers
is behind. A stale computer must never again be invisible.

**The incident (2026-07-29).** Both churn defects in §6.6 were found, fixed, committed and pushed — and the
flood continued at exactly its old rate, because the computer producing it was running an **older build**.
The tell was that its device file lacked fields the current schema publishes, which took reading two YAML
files side by side to notice. Nothing in the product could see the gap, and no amount of further work in
the repo could have closed it.

Three consequences, all of which the design now assumes:

* **"Fixed in the repo" and "fixed on the fleet" are different states**, and only the second one is worth
  anything to the user.
* **Churn diagnosis must start with the build.** Identify *which device file* is churning, then confirm
  what build that computer runs, **before** concluding anything about the code. Otherwise the next fix gets
  written against code that was never the problem.
* **A device file missing fields the current schema publishes is the tell** that its computer is stale.

#### 6.7.1 The build number is a deliberate integer, never the git sha (LOCKED)

Each computer publishes `device.app_build` (+ a short label) into its device file. It is a **monotonic
integer bumped by hand** when a change matters to other computers — a sync/churn fix, a schema field others
must publish, a protocol change.

> **It must NOT be the git HEAD sha.** This repo is continuously auto-committed, so the sha moves every few
> minutes; publishing it into a **synced** file would manufacture a commit per code commit — precisely the
> flood §6.6 exists to stop, re-created by the very feature meant to police it. The sha *is* used for the
> **local** "am I running older code than my own checkout?" check, where nothing is published and nothing
> can churn.

A peer that reports **`0`** is running a build too old to publish the field at all — which is itself the
answer, and the loudest one.

#### 6.7.2 What the app does about it

1. **Detect (local).** The HEAD sha captured **at boot** is the code actually running. If the checkout's
   HEAD has since moved, this process is running stale code.
2. **Upgrade (opt-out, `self_update.enabled`).** When the checkout is behind its remote, **fast-forward it**.
   Rails, each load-bearing: **fast-forward ONLY** (never a merge, rebase, or force — a diverged branch is
   reported, never reconciled by a background job); **a dirty tree is never touched**; `check_only` does the
   detection and writes nothing, for a machine whose source is managed elsewhere.
3. **Never restart the process itself.** The app runs under a source watcher (`just run` → `pnpm dev` →
   `tsx watch`), so a successful fast-forward **is** the restart. Calling `process.exit()` would be a bet
   that something brings us back, and in this deployment nothing would — `just run` starts a detached
   `nohup pnpm dev` with no supervisor. **A stale app is a bug; a dead app is an outage.** If the process is
   still on the old build after the source moved, that is *reported*, not acted on.
4. **Surface (always).** A peer behind this computer is named — the computer, its build, and what to do.
   *"Something is out of date"* is not actionable; **which computer** is the entire content.

**The report is THROTTLED, and that is the same rule as §6.6 applied to the log.** Its host ticks every 5
minutes; an unthrottled report would write ~288 WARN lines a day into `error.err` about a condition that
changes maybe twice a week, burying every other fault in the file. **Repeating a standing fact is not
reporting it.** So it is said when the **answer changes**, and otherwise at most **hourly** as a reminder
that it is still true; when the fleet catches up it goes silent, and the *next* problem is fresh news
again. A monitoring feature that manufactures noise has become the thing it was built to police.

The fetch is **throttled to hourly** even though its host (the watchdog) ticks every 5 minutes: a build does
not go stale on a 5-minute timescale, and 288 fetches a day would be exactly the pointless background
traffic §6.6 is about removing.

Knowing and publishing the build is implemented in code:
`~/repos/LargeFileBridge/code/packages/shared/src/build.ts` — `APP_BUILD` (bump it deliberately), written into the device file by `~/repos/LargeFileBridge/code/packages/backend/src/modules/storage/devices.service.ts` — `writeSelfDevice()`.

Detecting staleness, fast-forwarding the checkout, and naming stale peers is implemented in code:
`~/repos/LargeFileBridge/code/packages/backend/src/modules/schedule/self-update.service.ts` — `buildState()` / `runningStaleCode()` / `runSelfUpdate()` / `stalePeersAcrossStorages()` / `stalePeerMessage()`, driven from `~/repos/LargeFileBridge/code/packages/backend/src/modules/schedule/watchdog.service.ts` — `checkOwnBuild()` on the existing watchdog tick, and reported by `~/repos/LargeFileBridge/code/packages/backend/src/modules/health/health.router.ts` — `GET /api/health`.

### 6.8 The write switch — auto-commit can be turned OFF per computer

A setting (`git_backbone.auto_commit` in `config.yaml`, on the Settings page as "Git auto-commit",
default **on**) makes every backbone on this computer **read-only** when turned off. The cycle still
**fetches and fast-forwards**, so the other computers' edits keep landing here — but this machine may
not author anything: no checkpoint commit, no merge commit, no SDL write-back commit, no artifact
commit, **no push**. A remote that cannot be fast-forwarded is *surfaced as a problem*, never merged
(a merge is a commit). The `.gitattributes`/`.gitignore` heals are also skipped — a heal is a working-tree
write that would sit uncommitted in the repo. The switch is read **live** each cycle, so flipping it
needs no restart; the skip is logged, never silent.

**Read-only must still converge, and that takes one extra step.** With the switch off, the pre-merge
checkpoint of §4 is skipped — it is a commit — while everything that *writes* the tree carries on: the
device file, the manifest and the mirrored `repos/<repoUid>/` subtree are rewritten on every pass
(writing your own text locally is not a Git write). The tree is therefore permanently dirty with LFB's
own generated text, and a fast-forward that touches any of it aborts with *"Your local changes to the
following files would be overwritten by merge"* — the exact abort the checkpoint was invented to kill,
now on every cycle. So the read-only pull clears **its own** blockers the way a refused merge does
elsewhere: each path is quarantined under the state root, then an untracked one is deleted and a tracked
one restored from HEAD, and the fast-forward is retried. That authors nothing — index and working tree
only — and the incoming copy simply wins over a cache the next pass regenerates. A blocker LFB does
**not** own is never touched; it is named in the surfaced problem, and the fetch waits for the user.

**A blocker that could not be cleared is reported as what it is.** A clear can fail — a file another
process holds open, a directory the account may not write, both ordinary on Windows — and git then
refuses the retry naming the same paths. That is *not* a diverged branch, so it must not be reported as
one: telling the user their checkout diverged and needs a merge commit sends them to `git merge` for a
problem no merge can fix, and hides the file that is actually stuck. The surfaced problem names the stuck
files instead, and the next cycle retries. Divergence — this computer holding commits origin does not —
is the only state that earns the "reconciling would require a merge commit" wording.

Reading the switch and the read-only pull are implemented in code:
`~/repos/LargeFileBridge/code/packages/backend/src/modules/git/git.service.ts` — `gitAutoCommitEnabled()` / `GitBackbone.pullReadOnly()` (clearing its own blockers via `GitBackbone.clearBlockingOwnFiles()`, retrying with `GitBackbone.tryFastForward()`), gating `GitBackbone.commitAndPush()`; artifact delivery honors it in `~/repos/LargeFileBridge/code/packages/backend/src/modules/pin/repo-artifact-sync.service.ts` — `syncWorkingRepoArtifacts()` / `convergeWorkingRepoFromOrigin()`.

A commit or push is only ever as good as the worker that triggers it, so the switch's honest counterpart
is the OS scheduler honoring `<worker>_process.enabled` — see [scan.mdx §3.0](./scan.mdx).

## 7. Compliance boundary — the charter's no-relay posture, in Git terms (LOCKED)

The charter forbids LFB from becoming a gateway/relay for **other people's** content. The Git backbone
has the same shape of rule and the same default:

* LFB drives Git **only** on the repos the user **explicitly configured** as a storage's backbone. It
  never fetches, hosts, or serves a repo it merely discovered on disk, and it never proxies a third
  party's repo. The set of repos LFB will `push` to is exactly the set of storage backbones the user
  turned on — no wider.
* **Always look for out-of-compliance cases and flag/fix them**: any code path that would run a Git
  command against a repo the user did **not** configure as a backbone is a defect, exactly like a code
  path that would turn this machine into a public IPFS gateway. The only acceptable Git targets are the
  user's own configured storage backbones.
* **A `*_large_files_bridge` company/personal tracking repo counts as user-configured.** When such a
  storage's **own root is a git working tree**, LFB **auto-adopts that root** as its backbone
  ([devices.mdx §11.2.1](./devices.mdx#1121-a-company--personal-tracking-repo-auto-adopts-its-own-git-root--commit--push-first-write-and-every-update-locked-learned-from-a-defect))
  — this is **inside** the boundary, not a widening of it: a purpose-built tracking repo the user made
  for LFB is a repo the user *configured*, and LFB only ever pushes **our own** device registry into it.
  A plain **code** repo (storage type `repo`) is **never** adopted — its Category-B tracking state routes to
  **Local Storage** (+ the sync repo), never the code repo, so no git cycle ever runs against it. Its
  committed `.lfbridge/` holds only Category-A content and is **not** git-ignored
  ([git_ignore.mdx §5.3](./git_ignore.mdx)); it is simply excluded from every tracking-state git cycle.

* **LFB's OWN SOURCE CHECKOUT is the one git target that is not a storage backbone** (§6.7). Self-update
  runs `fetch` and a **fast-forward-only** `merge` against **the repository this very process is running
  from** — resolved from the running module's own path, never from a config value, a discovered repo, or
  anything a third party can point at. It is **inside** the boundary for the same reason a purpose-built
  tracking repo is: it is unambiguously the user's own, and there is exactly one of it. The rails are
  narrower than a backbone's — **never a non-FF merge, never a rebase, never a force, never a push** (LFB
  does not publish to its own source repo), and it is **opt-out** (`self_update.enabled`) with a
  `check_only` mode that writes nothing. Any code path that would run git against a source tree resolved
  from anywhere *other* than the running module's own location is a defect of the same class as pointing
  the backbone at a discovered repo.

Enforcing that Git operations only ever target a user-configured storage backbone (never a merely-discovered code repo) is handled in code:
`~/repos/LargeFileBridge/code/packages/backend/src/modules/storage/storage-settings.service.ts` — `getGitBackboneRemote()` returns a backbone **only** for an explicit dedicated-repo backing OR a company/personal storage whose own `<root>/.git` exists (a `repo`-type code repo returns null); `~/repos/LargeFileBridge/code/packages/backend/src/modules/git/git.service.ts` — `GitBackbone` is constructed only from that resolved remote, and there is no entry point that runs `push`/`fetch` on an arbitrary path.

## 8. Acceptance criteria

1. Turning on a storage's **Git backbone** ([storage_settings.mdx §4.1](./storage_settings.mdx#41-dedicated-git-repo-preferred-when-available))
   grants LFB permission to run **`git fetch`, `git merge` (automatic), `git add`/`commit`, and
   `git push`** against **that one repo** on **every pin pass** — and no Git command runs against a
   storage whose backbone is off (§1).
2. The Git library is **`simple-git`** driving the **system `git` binary**, so the **merge is done by
   real git** (ort strategy); `isomorphic-git` and `nodegit` are explicitly rejected (§2).
3. LFB accepts **two remote shapes**: a **local file path** to a checked-out working tree (used in
   place), and an **HTTP(S) URL** with **no** local checkout (cloned into a machine-local
   `pin/s/<id>/git/` cache and managed there). Both converge on one working copy the rest of the engine
   operates on (§3).
4. Concurrent edits from two of the user's computers **merge automatically**: self-owned per-device
   files never collide, append-mostly shared lists merge by **`merge=union`**, and only a **genuine**
   git conflict is surfaced — via **`merge --abort` + a UI problem**, never a clobber or a force-push
   (§4).
5. A **URL** remote authenticates through the **OS git credential helper** with `GIT_TERMINAL_PROMPT=0`;
   an auth failure is **surfaced** as a "re-authenticate" problem while IPFS pinning continues — LFB never
   prompts for or stores a plaintext password (§5).
6. The per-pass **cycle order is fixed**: resolve working copy → fetch → auto-merge → reconcile/pin to
   grafted paths → stage self-owned + commit → push, with a **fetch-merge-push retry** on a
   non-fast-forward reject; the cycle is idempotent (§6).
7. LFB drives Git **only** on user-configured storage backbones — never a merely-discovered or
   third-party repo, never a force-push — the Git analogue of the charter's no-public-relay rule (§1, §7).
8. **`merge=union` is the transport, not the reconciliation.** The union keeps both sides' lines so the
   file never conflicts; what LFB believes afterward comes from the **per-entry merge** of the pulled
   `repos/<repoUid>/` mirror in **step 4** of the cycle — union by `path`, union `pinned_by`, newer
   `modified_at` wins a CID conflict, absence never a delete — never a wholesale copy (§4.2, §6,
   [storage_company.mdx §8.4.3](./storage_company.mdx#843-receiving-is-a-merge-never-a-copy-locked)). The
   attribute patterns are **filename-matched**, so the mirror's remote-keyed rekey needs no
   `.gitattributes` change.
9. **A mirror write nudges its SDL's backbone on a debounce** rather than waiting for the next timer tick;
   the nudge coalesces to one commit + push per storage, runs the ordinary §6 cycle, and resolves the SDL
   by **ownership** (a working-repo path prefix resolves to nothing) — §6.2.
10. **Every conflicted path has an automatic resolution, applied PER FILE** (§4.3.1, authority
    [storage_company.mdx §11.1](./storage_company.mdx#111-a-conflict-is-always-resolved-never-surfaced-as-homework-locked)):
    **regenerate** for caches (`repo_storage.yaml`, `files.yaml`), **ours** for `devices/<self>.yaml`,
    **union** for append-only lists (manifest / decisions / owner_map / SyncList / sidecars / history), and
    **quarantine** for anything with no rule. A conflict in one file **never blocks** another; with nothing
    left over the merge is **finished and committed**, and `merge --abort` + surface (§4.3) is the **last
    resort**, not the first response — one unresolvable file must never freeze a storage's whole backbone.
11. **A Git-backed storage with no `origin` reports a loud, standing fault** and is never mistaken for a
    healthy repo with nothing to do (§4.3.2): committed-but-unpushed is a **reported state**, named on the
    storage's row and in the log, with "add a remote" as the one-click fix.
12. **A rejected push is retried three times with backoff** (`0s / 2s / 8s`), each attempt **re-pulling
    first** and **never** force-pushing (§6.3); every rejection's **cause is logged** with its attempt
    number, a later success clears the earlier problem, and exhausting the budget leaves the commit local
    for §6.1's ahead-count push on the next cycle.
13. **An idle computer is SILENT** (§6.6). With no substantive transaction — nothing pinned or un-pinned,
    no git-ignore decision, no transcript/AI description/OCR, no compression, no new/changed/deleted tracked
    file, no device-identity change, no user-initiated action — LFB makes **zero commits and zero pushes**,
    pass after pass, on **both** the personal and the company tracking repo. It still **pulls** every cycle,
    so another computer's work arrives normally; receiving is not authoring.
14. **A volatile field never becomes a commit** (§6.6.1). `updated_at`, `primary_ip`/`ip_addresses`, an
    mtime with unchanged content, a re-derived cache, and a pure key-reorder or schema-default fill-in are
    each **incapable** of producing a commit on their own — enforced both at the writer (canonical
    change-detection) and at the commit choke point (staged volatile-only modifications are reverted).
15. **The gate never swallows real news** (§6.6.2). A created file, a deleted file, a file LFB does not own,
    and any substantive change **always** keep their commit; volatile churn riding along on such a commit is
    free. The gate reverts only what it has **proven** meaningless.
16. **An in-progress merge is ALWAYS concluded** (§6.6.2). The merge commit is made even when the resolution
    staged nothing (every conflicted path resolved to "ours" leaves the index identical to `HEAD`), so
    `MERGE_HEAD` is never left dangling and the next cycle's pull is never refused with *"You have not
    concluded your merge"*. The quiet rule never applies to a merge.
17. **Every computer publishes which build it runs** (§6.7.1), as a deliberate monotonic integer — never
    the git sha, which would churn a synced file on every code commit. A peer reporting `0` is on a build
    too old to publish it, which is itself the answer.
18. **A stale computer is never invisible** (§6.7.2). LFB detects that this process is running older code
    than its own checkout, **fast-forwards** that checkout when it is behind (FF only; never a merge,
    rebase, force, or push; dirty tree untouched; opt-out + `check_only`), and **names** any of the user's
    other computers that are behind this one — with the computer, its build, and what to do.
19. **Self-update never restarts the process itself** (§6.7.2). The source watcher performs the restart; a
    build still stale after the source moved is *reported*, not acted on. A stale app is a bug, a dead app
    is an outage.
20. **Quiet is measured, not assumed** (§6.6.3). The idle-computer guarantee is covered by a regression test
    that drives the **real** commit path over a **real** git repo across **repeated** passes and asserts the
    commit count never moves, plus convergence tests proving a repeated identical write goes quiet and
    *stays* quiet. A commit rate above a handful per day with no matching user activity is a **defect**.
