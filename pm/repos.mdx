# LargeFileBridge — Repos

The **Repos** page is the landing view of LargeFileBridge and the screen users live in. It answers
one question at a glance: *for every repo on this computer, are my large files pinned across my
other machines?* It is a header over **one TanStack Table** — **one row per repo, for every git repo on
this computer** (LFB discovers and knows them all automatically — there is no "managed" opt-in;
[pin_process.mdx §1](./pin_process.mdx#1-lfb-knows-every-repo--there-is-no-lfb-managed-gate-locked)) —
with the standard search / filter / sort control row above it.

The left bar's **Repos** item (order 1, icon `FolderGit2`, route `/` — source of truth
`pm/left_bar.yaml`) lands here. Clicking any repo row opens that repo's per-file screen
([One repo](./one_repo.mdx)).

The Repos page is loaded and rendered as one TanStack table in code:
`~/BGit/Bryan_git/LargeFileBridge/code/packages/frontend/src/pages/repos/ReposPage.tsx` — `ReposPage` component

This spec builds on the siblings and does not repeat them:

* [README](../README.md) — the product charter: Git tracks the small files; LFBridge moves the big,
  git-ignored files peer-to-peer over IPFS.
* [Left bar](./left_bar.mdx) — the left navigation (data source of truth `pm/left_bar.yaml`); this
  document does not redefine it and only shows where it sits.
* [One repo](./one_repo.mdx) — the per-file screen a row click opens.
* [Repo tracking scheme](./repo_tracking_scheme.mdx) — the tracking state LFB keeps for a repo
  (`repo_storage.yaml`, per-file `<name>.yaml` sidecars, the per-computer history log) as these counts change.
  This state lives in **Local Storage** at `~/T/_large_files_bridge/repos/<repoKey>/`, never in the working
  repo ([artifact_placement_policy.mdx](./artifact_placement_policy.mdx)).
* [Special files](./special_files.mdx) — the classifier (large · already-pinned · video/image/audio) behind
  the per-repo counts on this table.

  tower and a Mac laptop, exercising every count, decision, and warning this table summarizes.

## 1. Vocabulary — Repo → Large file → Decision (LOCKED)

Three terms, used consistently across every spec and every screen:

| Term | Definition |
| --- | --- |
| **Repo** | **Any** git repository on this computer. LFBridge **discovers and knows every repo automatically** — a repo is never "unmanaged" ([pin_process.mdx §1](./pin_process.mdx#1-lfb-knows-every-repo--there-is-no-lfb-managed-gate-locked)); IPFS pinning of its bytes is the only opt-in. It has a local **path**, a **name** (the folder name), a git-ignore that excludes the big files, and a **manifest** (checked into git) listing the large files by path + IPFS CID. |
| **Large file** | A big, git-ignored file inside a repo (video, image, model weights, dataset, render output). LFBridge — not git — is responsible for moving its bytes between your computers. |
| **Decision** | Per large file, whether LFBridge should move it: **Add to IPFS (pin)** (stored decision value `sync`), **Ignore** (deliberately not pinned), or **Undecided** (LFBridge found it but the user has not yet chosen). Defined in full on the [One repo](./one_repo.mdx) screen; the Repos table only shows the **counts** per decision. |

```ts
// The per-repo summary the backend returns for each Repos-table row.
export interface RepoRow {
  repoId: string;        // stable id (hash of the absolute path)
  bookmarked: boolean;   // user favorite — persisted per-repo in config.yaml (§8); drives the leading ribbon toggle
  name: string;          // folder name
  path: string;          // absolute local path
  counts: {
    pinned: number;      // large files pinned (CID present + pinned locally) — INCLUDES files
                         //   that were already IPFS-pinned and got imported (ipfs.mdx §4)
    pending: number;     // decided "Add to IPFS (pin)" but not yet transferred (fetch/push queued)
    undecided: number;   // found by LFBridge, no pin/Ignore decision yet
    ignored: number;     // decided "Ignore" — deliberately not pinned
    pinnedForeign: number; // undecided, but their bytes are ALREADY pinned on this computer by another
                           //   IPFS tool (foreign_pin_discovery.mdx §6) — not a pin nag, but still files
  };
  peerCount: number;     // how many of your OTHER computers pin this repo — never this one (§4.3)
  notBackedUp: number;   // pinned files no OTHER computer holds — they live only on this machine
  missingHere: number;   // files a peer has that this computer does not have on disk at all
  bytes: { total: number; pinned: number }; // bytes of the files `counts` covers, and the pinned subset
  lastPinAt: string | null;  // ISO date-time of the last completed pin pass, or null
  lastScanAt: string | null; // when the census behind every count above was taken
  status: RepoStatus;    // rolled-up pin status (see §4.2)
}

export type RepoStatus =
  | "up_to_date"   // every "Add to IPFS (pin)" file present locally and on >=1 peer
  | "pinning"      // a transfer is in progress
  | "behind"       // pending > 0 (files owed in or out)
  | "needs_review" // undecided > 0 (user has decisions to make)
  | "error"        // last pin failed / IPFS node unreachable
  | "never";       // repo added, never pinned
```

The per-repo summary row (`RepoRow`) each table row shows is assembled by the backend in code:
`~/BGit/Bryan_git/LargeFileBridge/code/packages/backend/src/modules/store-model/units.service.ts` — `computeRepoRow`

### 3.1 Control row (above the table) — LOCKED

A single control row sits above the table, matching the standard toolbar:

* **Search box** (left) — a free-text input; substring match, case-insensitive, across **Repo name
  + path**. Filters the current data set live.
* **Facet rail** (directly under the control row, always visible) — the categorical filters live
  **here**, not in a dropdown: each facet is a labelled group of **value checkboxes, all checked by
  default** (all-checked = inactive), checkboxes within a facet OR and facets AND. The **owning spec is
  [tables.mdx §2](./tables.mdx#2-filtering--the-value-visibility-checkbox-model-locked)** — this page
  does not restate the model, it only names its facets (§3.2). **`☐ Bookmarked only`** is **promoted to
  the head of the rail** ([tables.mdx §2.7](./tables.mdx#27-the-promoted-bookmarked-only-filter-locked)).
  On this page the rail's one enum facet is **Status** (§3.2, col 9). Changing any facet resets to page 1.
* **Filter icon** (right, icon-only `⛛` funnel — **no text label, no button box**) — **no longer the
  place filters live.** It holds only the long tail
  ([tables.mdx §2.3](./tables.mdx#23-what-survives-in-the-filter--popover-locked)): the free-text
  **`contains`** filters (**Repo**, **Path**), the **numeric `≥` thresholds** for the count/size columns
  (Files / Pinned / Pending / Undecided / Ignored / Already pinned / Size / Missing here / Not backed up /
  Peers) and the **Last pin** + **Last scan** date bounds, plus any facet that
  **overflows** the rail at narrow widths. There is **no operator select + value input** row and **no
  `<select>`** anywhere in it. The icon stays **colored when any filter is active — rail facets
  included** (with an optional count), so it remains the single honest "something is filtered" mark.
* **Sort icon** (right, icon-only sort glyph — **no text label, no button box**) — opens a dropdown
  listing the sortable columns, each with asc/desc and the **1st/2nd/3rd** priority slots
  ([tables.mdx §3.1](./tables.mdx#31-the-sort-dropdown-ui-locked)); the icon is **colored** when a sort
  is active. The dropdown is the **discovery / Clear sort** surface, not the only way to read the sort:
  the **active sort renders as a live chip run** on the control row beside the icon
  (`Sort: [1 Bookmarked ↓] [2 Repo ↑]`) whose chips toggle direction, remove a key, and drag to
  re-rank, and **shift-clicking a header appends** that column as the next key instead of promoting it
  to primary ([tables.mdx §3.5](./tables.mdx#35-sorting-without-opening-the-dropdown--the-active-sort-chips-locked)).
  Chips, headers, and dropdown are **one** state.
* **Header-click sort (LOCKED).** In addition to the sort dropdown, **clicking a column header**
  sorts the table by that column. Clicking the **same** header again **toggles ascending ↔
  descending** (it does not cycle to "unsorted" — the header always leaves a sort applied; clear it
  from the dropdown's **Clear sort**). This adds **no new UI** — the header text *is* the control; the
  active sort column shows a small **caret** (`↑` asc / `↓` desc) beside its label, plus a pointer
  cursor / hover on sortable headers. Header click and the dropdown share **one** sort state, so a
  header-driven sort shows as active in the dropdown and vice-versa. **Only sortable columns respond**
  — every column the sort dropdown lists (including the leading **Bookmark**, whose header sorts
  bookmarked-first exactly like the dropdown) is clickable; a column with `sortable: false` and the
  **non-data** trailing chevron / kebab cells do nothing on header click.
`DataTable` toolbar (search left; icon-only sort/filter popovers right; rounded fills reserved for
the floating popovers, never the data surface).

`~/BGit/Bryan_git/LargeFileBridge/code/packages/frontend/src/components/table/DataTable.tsx` — `DataTable` component (the `showFilter` / `showSort` popovers).

### 3.2.1 Responsive column priority — drop the least-important column as the table narrows (LOCKED)

The table must **never wrap a cell onto a second line** to make everything fit. Instead, **every column
carries a priority**, and as the available width shrinks, the table **hides the lowest-priority visible
column first**, then the next, and so on — so what remains always fits on one line. As the window widens
again, hidden columns **reappear** in reverse order (highest priority first). This runs on the shared
`DataTable`, so every table inherits it.

**The trigger (plain-language).** If a cell would **wrap to two rows** because the row is too narrow,
that is the signal to **remove a column** — and if one isn't enough, remove **two or three** — until
every row is a single line again. In code we achieve this with a **per-column minimum width budget**:
the sum of the visible columns' minimum widths (plus the leading select + trailing chevron/kebab) must
fit the container; while it doesn't, the **lowest-priority** visible column is dropped and the budget
recomputed. Implemented in
`~/BGit/Bryan_git/LargeFileBridge/code/packages/frontend/src/components/table/DataTable.tsx` —
`useResponsiveColumns()` (measures the container with a `ResizeObserver`, drops lowest-priority columns
until the min-width budget fits), driven by the per-column `priority` + `minWidth` fields on
`~/BGit/Bryan_git/LargeFileBridge/code/packages/frontend/src/components/table/types.ts` — `LfbColumn`.

**Priority numbers — LOWER number = MORE important (kept longest); HIGHER number = dropped first.** The
master stack-rank below covers **every column that can appear** across LFB's repo-style/file tables (the
Repos list uses the subset it has; a files table that adds **Size** slots it in at the same rank). Two
special rules the user set: **Peers is the single lowest priority (dropped first)**, and **Size is
second-lowest (dropped next)**.

| Priority | Column | Pinned? | Drop behavior | Rationale |
| --- | --- | --- | --- | --- |
| **1** | **Repo / File (name)** | **Pinned — never drops** | never | The row's identity. Without it the row is meaningless. |
| **2** | **Status** | **Pinned — never drops** | never | The "am I OK?" verdict (§4.2) — the whole point of the screen. |
| **0** | **`▮` Bookmark** (leading toggle) | **Pinned — never drops** | never | A tiny fixed-width control; always fits, always useful. Rendered leftmost regardless. |
| **3** | **Undecided** | no | dropped 8th | Actionable — files that need a decision now. |
| **4** | **Last pin** | no | dropped 7th | "When did this last move?" — high-value reassurance/alarm. |
| **5** | **Pending** | no | dropped 6th | In-flight transfers. |
| **6** | **Pinned** | no | dropped 5th | Reassurance count of backed-up files. |
| **7** | **Path** | no | dropped 4th | Useful but long and already middle-truncated with a tooltip; the name carries identity. |
| **8** | **Ignored** | no | dropped 3rd | Least-actionable count. |
| **9** | **Size** | no | **dropped 2nd** *(of the original eight)* | Second-lowest per the rule. The Repos list now carries one (§3.2 col 9). |
| **10** | **Peers** | no | **dropped 1st** *(of the original eight)* | **Lowest of the original columns.** Redundancy detail; the Status verdict already flags "not backed up." |
| **11** | **Not backed up** | no | dropped 4th | The risk number — kept longest of the four detail columns, because it is the only one that says "you could lose these." |
| **12** | **Files** | no | dropped 3rd | Context for the counts, not a count you act on. |
| **13** | **Missing here** | no | dropped 2nd | Actionable, but the same files already show as Pending / Undecided. |
| **14** | **Already pinned** | no | dropped 1st | Reconciliation detail; zero on most machines. |
| **15** | **Last scan** | no | **dropped first of all** | Freshness, not state — reach for it when a number looks wrong, not while reading the table. |

**Two lowest, restated.** The user's rule — *Peers lowest, Size second-lowest* — is about the **original
eight** columns and still holds among them. The six columns added since (**9 Size** aside, which takes its
spec'd rank) are finer-grained still, so they rank **below** Peers and leave today's drop order intact
underneath them.

**Drop order as the Repos list narrows:** `Last scan` (15) → `Already pinned` (14) → `Missing here` (13)
→ `Files` (12) → `Not backed up` (11) → `Peers` (10) → `Size` (9) → `Ignored` (8) → `Path` (7) → `Pinned`
(6) → `Pending` (5) → `Last pin` (4) → `Undecided` (3). It **stops** before ever dropping the three pinned
columns (**Bookmark · Repo · Status**), which always remain so the table is never useless. The trailing
**› chevron** and **`⋮` kebab** control cell also always remain (they are not priority columns).

**Rules.**
* A column with **no `priority`** set is **treated as pinned** (never auto-hidden) — hiding is
  **opt-in** per table by assigning a priority; the Repos list assigns one to every column per the table
  above.
* **Pinned columns** (Bookmark, Repo, Status) never drop even at the narrowest width; if even those
  don't fit, the pinned set may scroll horizontally rather than wrap — pinned identity/verdict beats
  everything.
* **Sort & filter still reach hidden columns.** A column being responsively hidden from the body does
  **not** remove it from the **facet rail**, the **sort chip run**, or the `⛛` / sort dropdowns (§3.1)
  — the user can still filter by `Peers ≥ 1` even when the Peers column is hidden at the current width.
  (Hiding is presentation-only.) The rail obeys the same priority order when *it* runs out of width,
  overflowing its lowest-priority facets into the `⛛` popover
  ([tables.mdx §2.2](./tables.mdx#22-the-facet-rail--filtering-without-opening-a-dropdown-locked)).
* **Persistence.** Responsive hiding is derived from **live width**, not a saved preference — it is not
  written to `config.yaml`. The per-user sort/filter persistence ([tables.mdx §4](./tables.mdx)) is
  unaffected.
* **`minWidth`.** Each column declares a sensible `minWidth` (px) used for the budget; sensible defaults
  by kind — text ≈ 140, timestamp ≈ 96, enum ≈ 100, int ≈ 72, toggle ≈ 40 — overridable per column.

### 3.2.2 The Status facet — declared vocabulary (LOCKED)

Status is the **only enum facet** on this page, so it is the only column that earns a place on the
facet rail (§3.1). Per [tables.mdx §2.8](./tables.mdx#28-a-facets-values-must-be-declared--an-empty-facet-is-a-bug-locked)
it **must declare its complete value list** — a facet that ships without one renders as a label with no
chips and fails review. Its values are exactly the `RepoStatus` members (§1), **each a checkbox, all
checked by default**; all-checked is the resting, inactive state and there is **no `any` option**:

```
 Status   ☑ Up to date   ☑ Pinning   ☑ Behind   ☑ Needs review   ☑ Error   ☑ Never
```

| Checkbox label | `RepoStatus` value | Pill (§4.2) |
| --- | --- | --- |
| **Up to date** | `up_to_date` | green |

### 4.1a Every row adds up (LOCKED)

**`Files` (col 8) = `Pinned` + `Pending` + `Undecided` + `Ignored` + `Already pinned`.** The five buckets
are disjoint and exhaustive by construction — one pass assigns each counted file to exactly one of them —
so the identity is not a check the code performs, it is a property of how the counts are built, and the
client derives `Files` as that sum rather than receiving it. A row that does not add up is a bug in
`repoRowStats()`, not a rounding difference.

Two columns sit **outside** the sum on purpose, because they are the same files counted on a different
axis and adding them would double-count:

* **`Missing here`** — a file a peer has and this computer does not is already in `Pending` or
  `Undecided`, by its decision. This column says *where the bytes are*, not *what was decided*.
* **`Not backed up`** — those files are in `Pinned`. This column says *how many copies exist*.

**"Not backed up" requires the file to be pinned HERE (LOCKED).** The test is `transfer === "pinned"`
**and** no other computer claims it — not `decision === "sync" && cid != null`, which is what three
separate copies of this rule used to say. Those are different: a file with a CID that **nobody** claims
(a peer dropped its pin, or ours was never recorded) passed the old test while being **Pending** — we
want it and do not have it. So a file this computer does not hold was counted as "lives only on this
computer", offered the one remedy that cannot work for it ("open Large File Bridge on another computer
so it can pull them" — there is nothing to pull), and pushed the count **above `Pinned`**, breaking the
subset relation above.

*Defined once in:* `~/BGit/Bryan_git/LargeFileBridge/code/packages/backend/src/modules/store-model/units.service.ts` — `isSingleCopy()`, used by `repoRowStats()` (the column), `computeTaskMetrics()` (the One-repo tile) and `export-repo-recommendations.ts` (the CLI export).

**Why `Already pinned` had to become a column.** `counts.pinnedForeign` has always been computed and
never shown. A file whose bytes another IPFS tool already pinned on this node is deliberately kept out of
`Undecided` (re-asking "pin this?" about a pinned file was the 4th bug in the "CLI says pinned, app says
not" saga), so before this column existed it was subtracted from Undecided and added to **nothing** — the
visible columns silently stopped summing to the repo's file count, with no cell to explain the gap.

*Composed in:* `~/BGit/Bryan_git/LargeFileBridge/code/packages/backend/src/modules/store-model/units.service.ts` — `repoRowStats()`; *summed in:* `~/BGit/Bryan_git/LargeFileBridge/code/packages/frontend/src/pages/repos/ReposPage.tsx` — `totalFiles()`.
*Guarded in:* `~/BGit/Bryan_git/LargeFileBridge/code/packages/backend/src/modules/store-model/repo-row-stats.spec.ts` — every aggregate is asserted against the same aggregate recomputed from `computeRepoDetail`'s fully-composed rows.

### 4.2 Status pill colors (LOCKED)

| `status` | Meaning | Pill |
| --- | --- | --- |
| `up_to_date` | Every "Add to IPFS (pin)" file present locally and on ≥1 peer. | green |
| `pinning` | A transfer is in progress right now. | blue (accent), animated |
| `behind` | `pending > 0` — files owed in or out. | amber |
| `needs_review` | `undecided > 0` — the user has decisions to make. | accent outline |
| `error` | Last pin failed, or the IPFS node is unreachable. | red |
| `never` | Repo added but never pinned. | grey |

Precedence when several could apply: `error` > `pinning` > `behind` > `needs_review` > `up_to_date`
> `never`.

**`never` is the LAST verdict, not a short-circuit (LOCKED).** It means *nothing has ever been pinned
here* — `counts.pinned === 0` **and** no `lastPinAt` stamp. It must **not** be returned merely because
the stamp is missing: bytes reach a computer by import, by a pull, or by a pass whose stamp predates the
current state root, and testing `!lastPinAt` ahead of `up_to_date` put a grey **never** pill on rows
reading *114 Pinned / 0 Pending / 0 Undecided* — the healthiest state the product has, labelled as the
emptiest. A repo with **nothing to pin** (no large files at all) is `never` too: there is no work and no
verdict, and a green "Up to date" tick over an empty census would be a claim the scan never made. Read it
together with **Files** (col 8) and **Last scan** (col 14), which say whether the census is empty or stale.

*Rolled up in:* `~/BGit/Bryan_git/LargeFileBridge/code/packages/backend/src/modules/store-model/units.service.ts` — `rollupStatus()` (one function, used by both the Repos row and the One-repo detail, so the list and the page it opens can never disagree).

### 4.3 `Peers` counts your OTHER computers (LOCKED)

`peerCount` is **how many of your other computers hold at least one of this repo's files**. **This
computer is never one of them.**

The manifest's `pinned_by` list includes our own label — pin truth is a self-claim
([ipfs.mdx §1.1](./ipfs.mdx)) — so counting it made **every repo this machine had pinned read at least
1**, and the LOCKED "**Peers = 0** means nothing is backing this repo up" alarm (§4.1) could never fire
for the one situation it exists to catch: files that live on this machine and nowhere else. The file-level
twin (`TaskMetrics.notBackedUp`) always excluded self; this is the repo-level number brought in line with
it, and **`Not backed up`** (col 12) is the same test surfaced as a count.

*Counted in:* `~/BGit/Bryan_git/LargeFileBridge/code/packages/backend/src/modules/store-model/units.service.ts` — `repoRowStats()` (cheap path) and `peerCountForFiles()` (composed path); both skip `computerLabel()`.

## 7. Empty & loading states

* **No repos:** the table is replaced by a dashed card — "No repos yet. Add your first repo →"
  (opens the Add-repo dialog).
* **Loading:** skeleton rows sized to the columns, so there is no layout shift.
* **Loading PROGRESSIVELY (performance.mdx P-37).** The rows are STREAMED: the server composes them in
  batches and the table starts filling in tens of milliseconds rather than after the last repo on the
  machine. Every reader shares ONE walk, so N tabs — or a burst of live-refresh bumps — still cost one pass
  over the disk.
* **Refetch:** existing rows stay visible until new data replaces them; a repo mid-pin shows the
  animated `pinning` pill without blocking interaction. This is why progressive filling applies to the
  FIRST load only — replacing a finished table with a growing one on every bump would be a blink, not
  progress.

The streamed list endpoint (one shared walk, multicast to every reader) is in code:
`~/BGit/Bryan_git/LargeFileBridge/code/packages/backend/src/modules/repos/repos.router.ts` — the `GET /api/repos/stream` handler + `startRepoRowsFeed()`

`~/BGit/Bryan_git/LargeFileBridge/code/packages/frontend/src/api/streamQueries.ts` — `streamRepoRows()`

* **A BACKGROUND PASS MAKES EVERY NUMBER IN THIS TABLE PROVISIONAL (performance.mdx P-38, LOCKED).** The
  per-repo counts here — peers, pinned, undecided — are recomputed by the same `scan` / `pin` passes that

### 8.4 Sort & filter — the shared model ([tables.mdx](./tables.mdx))

The bookmark's sort/filter behavior is the **cross-cutting** one defined once in
[tables.mdx](./tables.mdx) (bookmarks, promoted filter, multi-level sort, per-user persistence) — Repos
is its **reference implementation**. In short:

* **Sort is multi-level** (primary / secondary / tertiary — [tables.mdx §3](./tables.mdx#3-multi-level-sort--primary--secondary--tertiary-locked)).
  The **default** here is **Bookmarked descending first, then repo name** — favorites float to the top
  of a 100-repo list. The sort dropdown's **1st/2nd/3rd** priority slots let the user re-rank; the
  choice is **saved per user for this page** and restored next visit.
* **Filter** — **`☐ Bookmarked only` is a single promoted checkbox at the head of the facet rail**
  ([tables.mdx §2.7](./tables.mdx#27-the-promoted-bookmarked-only-filter-locked)) — on = only
  bookmarked repos, off = no bookmark constraint. It ANDs with the Status facet (§3.2.2), resets to
  page 1, and colors the filter icon.
  * **It is the only bookmark filter.** There is **no** per-column *Bookmarked: yes / no* facet
    alongside it — the two-value form would cost a chip and buy nothing over the checkbox's obvious
    off state. Bookmarked-only is the **one documented exception** to the value-checkbox facet model
    ([tables.mdx §2.1](./tables.mdx#21-a-facet-is-its-values-each-with-a-checkbox-all-checked-by-default-locked)),
    and this page must not reintroduce the retired `yes / no` select.
  * **Filter and sort are independent** (§3.4 of tables.mdx): the sort floats bookmarks to the top of
    the *full* list; this checkbox hides everything *except* bookmarks. Either, both, or neither.
* Bookmark state is **independent** of `status` — a bookmarked repo still shows its true status pill.
* **Persistence** — this page's sort + filter are saved in `users/<email>/config.yaml` `tables.views`
  ([tables.mdx §4](./tables.mdx#4-persistence--sort--filter-saved-per-user-per-page-locked)).
