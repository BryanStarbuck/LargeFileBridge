# The Database

Large File Bridge keeps its machine-local state in **PostgreSQL**, and keeps every
byte that crosses between the user's computers in **YAML files on disk**. This spec
is the single source of truth for that split: which data moves, which deliberately
does not, the schema, the indexes, and the fence that stops the two halves leaking
into each other.

It replaces the "there is no database" sentence in
[storage_local.mdx](./storage_local.mdx) §0 — see §1.3 for exactly what that
sentence meant, why it was right when it was written, and what changed.

Companion specs:

* [database_migration.mdx](./database_migration.mdx) — the migration engine, the
  `migration_state.yaml` ledger, the YAML→Postgres backfill, and rollback.
* [performance.mdx](./performance.mdx) — the measured problems this work exists to
  fix. Its **Ninth pass** section is the entry point.
* [syncable_data_location.mdx](./syncable_data_location.mdx) — the travelling half,
  which this spec must never own.
* [storage_local.mdx](./storage_local.mdx) — the state root, which this spec
  re-homes into Postgres one document class at a time.

## 1. Why a database, and why only for half the data

### 1.1 The problem, measured

Every number below was measured on this machine on 2026-08-24, against the live
state root. None of it is estimated.

| Store | On disk | Records | Access shape |
|---|---|---|---|
| `repos/<slug>-<key>/files/**/*.yaml` (sidecars) | 23.1 MB in **~119 MB** of 4 KiB blocks | 29,138 | read-modify-write whole file |
| `pin/r/<repo>/status.yaml` | 5.17 MB | **30,762** candidates | read-modify-write whole file |
| `repos/<slug>-<key>/decisions.yaml` | 4.97 MB | 18,234 events | full-scan fold, no cache |
| `foreign-pin-cache.json` + `foreign-pins.json` | 8.47 MB | 38,870 | whole-file rewrite |
| `repos/<slug>-<key>/manifest.yaml` | 1.68 MB | 4,184 | read-modify-write whole file |

The shape is the problem, not the size. 8 MB is nothing for a database and brutal
for a document that must be parsed, mutated in memory, re-serialized and re-fsynced
to change one field.

Four consequences are already in the record:

* **`YAML.parse` owned ~40% of `GET /api/repos`** — measured with a JIT-resolved CPU
  profile, and written into the code that fixed it
  (`shared/store/yaml-store.ts:15-19`).
* **The sidecar mirror re-merged 20,059 unchanged files every pass.** A profile
  attributed **7.9 s of 17 s** non-idle time to `readYamlDoc` plus 1.65 s to
  serialize; `loop-watch` reported `EVENT LOOP BLOCKED … up to 13858ms`
  (performance.mdx P-40). On any given pass **99.98%** of those sidecars are
  byte-identical.
* **The decision fold has no cache.** `charlie-kirk`'s 11,423 events fold to 2,189
  distinct paths — a 5.2× write amplification on a log that is re-parsed and
  re-folded *in memory* on every read, once per repo while composing the Repos list
  (`units.service.ts:970`) and again per decision request
  (`repos.router.ts:831`).
* **A whole-file rewrite of the foreign-pin cache caused a 4 GB RSS incident**
  on 2026-07-20.

Live today, in `error.err`: `storage.reconcile.yielding (yielded) 9139ms/105 calls,
worst 2143ms` and `storage.mirror 3639ms/101 calls, worst 1567ms`.

### 1.2 The fix is a storage engine, not another cache

Every one of those symptoms is the same disease: **we hold a whole document in
order to read or change one record.** Caching the parse (which we did, and which
helped) reduces the constant. It cannot change the shape.

Postgres changes the shape. A decision becomes a row, a pin claim becomes a row, a
candidate becomes a row — and "which files in this repo are big, undecided, and not
yet pinned" becomes an indexed query instead of a fold over 11,423 events.

### 1.3 What "there is no database" meant, and what changed

`storage_local.mdx` opens by saying LFB has no database and that Local Storage is
*"effectively LFBridge's database replacement."* That was the right call and it is
still the right call **for the travelling half**. What it was protecting against is
real and permanent:

> A database that is the only copy of something a second computer needs is a
> database that has silently become the sync protocol.

So the sentence is narrowed, not reversed:

* **Local Storage is now backed by Postgres.** It was always described as the thing
  that *"if you wiped it and re-scanned, it would rebuild"* — that is a cache with
  extra steps, and a cache belongs in a database.
* **The Syncable Data Locations stay YAML, forever.** They are the sync protocol.
  Postgres may feed their serializers values; it may never be in their write path.

The seam that makes this safe already exists in the code, and it is the single most
important fact in this document:

> Category-B tracking state **already** lives in Local Storage as its always-home,
> and is only **additionally** mirrored to the sync repo.
> — `modules/storage/tracking-root.service.ts:5-11`

So moving Local Storage into Postgres requires **no change to the sync contract at
all**. The mirror keeps copying files; it just stops walking 29,614 of them to
discover that 20,059 did not change.

## 2. The boundary (LOCKED)

Three categories. Every store in the app is exactly one of them, and the category
decides where it lives.

| Category | Where it lives | Postgres role |
|---|---|---|
| **LOCAL_ONLY** — this computer's own bookkeeping, rebuildable by re-scanning | Postgres | **source of truth** |
| **MIRRORED_BOTH** — Category-B tracking state: local always-home + additive SDL mirror | Postgres (working copy) **and** the YAML file | source of truth for the working copy; **feeds** the file's serializer |
| **SDL_TRAVELS** — bytes another computer will read | YAML under an SDL | **never** in the write path |

### 2.1 The four documents that escape today

Verified in code, not inferred. `LOCAL_ONLY` is `{".sync-repo", ".durable-artifact"}`
(`tracking-sync.service.ts:50`); `MERGED_NEVER_COPIED` is the three names at `:61`;
and `copyTreeGen` applies **both sets only at `rel === ""`** (`:196`), falling through
to `fs.copyFileSync` for everything deeper.

Therefore these four travel today as plain last-writer-wins copies. They are **live
data-loss bugs**, found by this analysis and fixed in slice 3 *before* any Postgres
write lands:

| Document | What is lost | Fix |
|---|---|---|
| `decisions_policy.yaml` | shared user intent — whose default-decision mode wins | field-wise merge (newest `set_at`, ties by `set_by`) |
| `decisions.conflicted.yaml` | this machine's failed-merge quarantine, overwritten by a peer's | add to `LOCAL_ONLY` |
| `manifest.conflicted.yaml` | same | add to `LOCAL_ONLY` |
| `files.yaml` | machine-local content in a mirrored path — two computers with different subsets overwrite each other every cycle | add to `LOCAL_ONLY`; content becomes `lfb.file` |

That last one is the exact ping-pong the `repo_storage.yaml` `counts:` scrub was
written to stop (`tracking-sync.service.ts:386-390`).

### 2.2 The fence, as an enforceable rule

> A byte that will be read by another of the user's computers must be produced by a
> **designated serializer** writing a file under a Syncable Data Location, and
> Postgres must appear nowhere in that write's causal chain except as the source of
> the values the serializer is handed.

**One serializer per travelling document, and it does not change.** Postgres feeds
these functions their arguments; it never emits YAML itself, and this work creates
no new YAML writer:

| Document | Serializer | Module |
|---|---|---|
| `decisions.yaml` | `serializeLedger` | `modules/storage/ledger-merge.ts` |
| `manifest.yaml` | `serializeManifest` | `modules/storage/manifest-merge.ts` |
| `repo_storage.yaml` | `YAML.stringify {sortMapEntries:true}` | `modules/storage/repo-storage.service.ts` |
| `files/<rel>.yaml` | `YAML.stringify {sortMapEntries:true}` | `modules/storage/file-sidecar.service.ts` |
| `history/<device>.txt` | `appendHistory` | `modules/storage/history-log.service.ts` |
| `decisions_policy.yaml` | `writeDecisionPolicy` | `modules/storage/decisions.service.ts` |
| `analysis/**/compression.yaml` | `writeLedger` | `modules/compress/compress-ledger.ts` |
| `<sdl>/devices/<self>.yaml` | `writeSelfDevice` | `modules/storage/devices.service.ts` |

**The wire-format rules survive intact and may not be re-implemented in SQL:**

* `projectRepoStorageToMirror` scrubs `last_scan` and `counts` on the way out
  (`tracking-sync.service.ts:447`, `MACHINE_LOCAL_REPO_STORAGE` at `:432`).
* `mergeManifests` strips our own `pinned_by` claim from arriving entries and passes
  every peer's through unchanged (`manifest-merge.ts:123-128,157`). `pin_claim.origin`
  plus the `lfb_pin_claim_guard` trigger mirror this **inside** Postgres so the two
  cannot diverge.
* `serializeLedger` compacts. Nothing else compacts.
* The tie-break for two CIDs at the same `modified_at` is a total order on the value
  with plain `<`, never `localeCompare` — two computers must not disagree because of
  collation.

### 2.2b The column that two writers wanted to mean two things

The render equality gate (§2.3) came back **red at full corpus scope** on its first real run —
15,868 of 29,447 sidecar documents did not render byte-identical — and the cause was not the
renderer. `lfb.file.modified_at` and `lfb.file.size_bytes` had **two writers with two different
meanings, and both were right**:

* the **scan census** writes the **live stat**, because `size_bytes` drives `is_big`, the compression
  rollups and every "large files only" tab, and a stale size there is a wrong answer on a
  user-visible surface;
* the **sidecar** stores the size and mtime **as of the last time Large File Bridge touched the
  file** — not a staler measurement but a **different fact**, and the one the document is required to
  state when it is re-serialized.

One column cannot hold both. Migration **0017** gives the sidecar its own `sidecar_size_bytes` and
`sidecar_modified_at`, written only by the sidecar plane and read only by `renderSidecar`. Both are
**nullable with no `>= 0` CHECK**, because `FileSidecarSchema` declares `size: z.number().nullable()`
and `modified: iso.optional()` — a document that says `size: null` must render as `size: null`, and
NULL here means "the document said so", never "we do not know yet".

Result: **15,868 → 0** differing documents.

Two things this cost, both worth remembering:

* Adding the columns to the INSERT list but **not** to the `ON CONFLICT DO UPDATE SET` clause made it
  **worse** (15,868 → 28,451): every row already existed, so the update fired and left both NULL. A
  sidecar-owned column is assigned **outright** — "preserve what is there" is only correct for a
  column another writer also owns.
* The re-run was armed by bumping the area's **logic version**, not by clearing state. This is
  exactly what `applied_version < version` is for: the watermark alone would have declared every
  scope up-to-date and migrated nothing.

### 2.3 How we detect a violation

**The render equality gate.** For every `(unit, doc)` row in `lfb.doc_render`, render
the document from Postgres through its designated serializer and compare `sha256`
against the bytes on disk. **Zero diffs, or the cutover does not happen.**

**Scope is the LOCAL Category-B copies — 29,447 documents — and that is a correction to
this paragraph's first draft**, which said "the two SDL trees plus the local copies".
`doc_render`'s primary key is `(unit_id, doc, doc_key)` with no SDL dimension, and there is
a reason it cannot have one: an SDL copy is not the same document as the local one. The
SDL's `manifest.yaml` is the MERGE of ours with every peer's claims, and its
`repo_storage.yaml` is deliberately scrubbed of `last_scan`/`counts`. Rendering either from
our rows and calling a difference a defect would fail the gate on documents that are
correct. The SDL side is covered by `ingested_sha256` instead — what last came in — which is
the honest question to ask of a copy we do not author.

This is the right test because `tracking-sync.service.ts:225-234` records that 58 of
the last 60 device commits were a lone `updated_at` line. A renderer that is one byte
off turns every mirror pass into a commit, and two computers into a re-render loop.

The gate runs in CI, blocks the cutover, and then runs nightly.

**Current result** (2026-08-24, real corpus): **29,447 documents examined, 29,339 byte-identical,
0 different — the gate PASSES.**

**Three are classified `healed`, and counted apart from failures.** Their sidecars sit at a healed
location on disk while their own `path:` field still carries the pre-heal Windows spelling —
`sidecar-heal.ts` fixed where the file lives and did not rewrite what it says. Postgres files them
under the POSIX spelling because `rel_posix` is the generated primary key, which is precisely what
makes the stray-path fork *structurally impossible instead of healed by hand* (§3). **Postgres is
right and the document is stale**, so no renderer change can or should reproduce it.

Counting those as failures would leave the gate permanently red for something nobody intends to fix
— which is how a gate stops being read, the same failure the 0015 "DO NOT APPLY" comment had. Counting
them as matches would hide them. So they get their own bucket, are printed by name, and the
classifier (`isStrayPathHeal`) is pinned **narrow** by eight tests: a different path, a different key,
a truncated delta, or backslashes on the *Postgres* side are all real diffs.

Rendering each Category-B document from Postgres through its designated serializer,
comparing `sha256` against the bytes on disk and writing **only on a change** is done in
code:
`~/BGit/Bryan_git/LargeFileBridge/code/packages/backend/src/modules/storage/doc-render.service.ts`
→ `runRenderGate` (the gate) and `syncFenceBeforeMirror` (the pre-mirror pass), with one
renderer per document class (`renderDecisions`, `renderManifest`, `renderRepoStorage`,
`renderSidecar`, `renderDecisionPolicy`). It is the **only** module in the app that imports
both the pool and a serializer; that exclusivity is itself a test —
`modules/storage/doc-render.import-guard.spec.ts`. Running the gate from a terminal is
`just db-render-gate` (`shared/persistence/render-gate-cli.ts`); running it as a test is
`modules/storage/render-gate.spec.ts`, which needs `LFB_GATE_STATE_DIR` and
`LFB_GATE_DATABASE_URL` for the same reason `decision-fold-gate.spec.ts` does.

### 2.3.1 The first full run — measured 2026-08-24, and it does NOT pass

29,447 documents examined against a fully backfilled database — 309 whole-unit documents
(3 per repo) plus 29,138 sidecars. **13,474 byte-identical, 15,868 different, 105 not
covered.** The Postgres-fed write is therefore **OFF**
(`renderWritesArmed()`, `LFB_DOC_RENDER_WRITE`), which is what §2.3's "zero diffs, or the
cutover does not happen" means in practice.

| Document class | On disk | Identical | Different |
|---|---|---|---|
| `decisions.yaml` (18,234 events) → `serializeLedger` | 103 | **103** | 0 |
| `manifest.yaml` (4,184 entries) → `serializeManifest` | 103 | **103** | 0 |
| `files/<rel>.yaml` → `YAML.stringify {sortMapEntries:true}` | 29,136 | 13,268 | **15,868** |
| `repo_storage.yaml`, **scrubbed mirror projection** | 103 | **103** | 0 |
| `repo_storage.yaml`, local copy (live `counts:`) | 103 | — | not covered |
| `history/<device>.txt` · `analysis/**/compression.yaml` · `decisions_policy.yaml` | 18 · 37 · 0 | — | outside the target list |

**All 309 whole-unit documents render byte-for-byte, for every repo.** That is the result
this slice exists to establish: `serializeLedger`'s compaction, its total order,
`serializeManifest`'s `pinned_by` sort, `MACHINE_LOCAL_REPO_STORAGE`'s scrub and the
`to_char` spelling of every timestamp all survive the round trip through rows.

**The 15,868 sidecar failures are ONE finding, not 15,868.** Classified structurally, every
one of them is `modified` and/or `size`: 15,171 `modified`, 412 `modified`+`size`, 282
`size`, 3 `modified`+`path`. `lfb.file.size_bytes` and `lfb.file.modified_at` hold the
**live scan census** — area 3 writes them from a fresh `stat` — while a sidecar's `size:`
and `modified:` are **historical**, the values as of the last time the sidecar itself was
written. Verified on one row end to end: the file's real mtime, `pin/r/<folder>/status.yaml`
and `lfb.file.modified_at` all read `2026-04-29T01:16:20.558Z`, and the sidecar reads
`2026-04-28T00:26:13.508Z`. `upsertSidecarFiles` (R5,
`modules/store-model/file-detail.repo.ts`) correctly declines to overwrite the census, so
the column holds the census's fact and the render says so. **One column, two facts, two
owners** — a schema question, not a renderer bug. Resolving it needs either a second pair
of columns for the sidecar's as-recorded values, or a decision that the sidecar's identity
block is derived from the census on write.

The 3 `modified`+`path` failures are the same shape one level up: `lfb.file.rel_path` is
documented as "byte-exact as the sidecar recorded it", but four areas write `lfb.file` and
`rel_path` belongs to whichever inserted first — so a Windows peer's `_mix\rotten\27k.csv`
is lost when the census created the row with the healed spelling.

**`repo_storage.yaml` splits in two, and the half that TRAVELS is the half that renders.**
`RepoStorageCountsSchema` is nine counters — special / large / ipfs_pinned / videos / images
/ audio / compressible / transcribable / transcribed — and `lfb.unit_rollup` (0003) names
the UI's nine, which overlap in one; so the LOCAL file, which carries this computer's live
counts and `last_scan`, is not renderable. The MIRROR copy is, and 103 of 103 render
byte-identical, because `projectRepoStorageToMirror` resets exactly `counts` and `last_scan`
to their schema defaults on the way out — **the two blocks Postgres cannot source are
precisely the two the wire does not carry** (`renderRepoStorage(unitId, { scrub: true })`).
That is not a coincidence; it is `MACHINE_LOCAL_REPO_STORAGE` and this schema agreeing about
which fields are about a computer rather than about a repo.

`history/<device>.txt` is **structurally** outside the gate: its designated serializer,
`appendHistory`, is append-only and stamps `new Date()` at call time, so there is no
argument that reproduces a file. Re-rendering one would require a second writer, which §2.2
forbids. `history_entry` (0010) therefore stays a read index over a file this work never
writes.

**One defect found in the specs while doing this:** `decisions_policy.yaml` has TWO
spellings today — `writeDecisionPolicy` (decisions.service.ts) uses a plain
`YAML.stringify(doc)`, and `mergePolicyInto` (tracking-sync.service.ts) uses
`YAML.stringify(winner, { sortMapEntries: true })`. §2.2 names the former as the designated
serializer. It is latent — there are zero `decisions_policy.yaml` files on this machine —
but it is precisely the churn shape §6 describes, and it should be reconciled before any
policy document exists.

### 2.3.2 What the fence costs, and what it does not yet save

`syncFenceBeforeMirror` runs before `mirrorToSyncRepo`'s tree walk
(`tracking-sync.service.ts` `mirrorGen`) and records `doc_render`; the reconcile leg records
`doc_render.ingested_sha256` and `lfb.sdl_ingest` (`recordSdlIngestForRepo`). Both are
fire-and-forget, because that call chain is synchronous top to bottom.

**The skip is the mechanic.** A document whose on-disk `sha256` already equals
`rendered_sha256` is not re-rendered at all. Measured on this machine, per unit per pass:

| Repo | Cold (renders both documents) | Warm (1 SELECT + 4 `statSync`) |
|---|---|---|
| `charlie-kirk` (3.1 MB ledger, 894 KB manifest) | **239.9 ms** | **0.8 ms** |
| `all` | 173.1 ms | 0.5 ms |
| `act3_Marketing_NextGen` | 4.8 ms | 0.5 ms |

Without that skip the fence re-rendered every pass and cost 233 ms per unit — more than the
mirror it precedes. `storage.mirror` runs ~101 times a minute here, so an unconditional
render would have put a minute of CPU into every minute of wall clock.

**`storage.mirror` itself is UNCHANGED, and no more should be claimed.** Measured over 15
mirror passes across three repos: **1161 ms with the fence off, 1112 ms with it on** —
noise. That is the correct outcome while the gate is non-zero: the fence records and
reports, and writes nothing. The mirror's cost falls only when `renderWritesArmed()` is on,
and that waits on the two column-ownership questions above.

`doc_render_dirty` works end to end and is already useful: after one mirror plus one
reconcile of a repo, three rows exist and **one** is dirty — `repo_storage.yaml`, whose
mirror copy is scrubbed of `last_scan`/`counts` and therefore legitimately differs from the
local copy forever. The other two converge to identical, which is what a settled document
looks like.

## 3. The naming law

This resolves every place two subsystems invented different keys for the same thing.
Implemented in `code/packages/backend/src/shared/persistence/migrations/0003_unit.sql`
and the data-access layer `modules/store-model/unit.repo.ts`.

**One unit identity.** `lfb.unit.unit_id bigint` is the only FK target. The five
spellings the code already uses are **columns on that one row**, so no caller changes
its vocabulary:

| Column | Value | Source |
|---|---|---|
| `abs_path` | the natural key (UNIQUE); everything derives from it | — |
| `repo_key` | `sha1(resolve(abs_path))[0:12]` | `tracking-root.service.ts:26` |
| `repo_id` | `sha1(resolve(abs_path))[0:16]` | `units.service.ts:69` |
| `storage_sid` | `repo_key` for a repo; `'personal'`; or the community id | `storage.service.ts:75` |
| `pin_folder` | the `pin/r/<folder>` directory name | — |
| `repo_uid` | `sha1(lower(host/owner/repo))[0:12]`, NULL when no remote | `repo-identity.ts` `repoUidFor` |

`repo_key`, `repo_id` and `storage_sid` are the same sha1 at different lengths. They
are **stored, not recomputed** — Postgres cannot reproduce the TypeScript hash and
must never disagree with it.

**One file identity.** `(unit_id, rel_posix)`.

* `rel_path` is the **byte-exact** spelling last seen on disk, required to re-render
  YAML.
* `rel_posix` is a **STORED GENERATED** column, `replace(rel_path,'\','/')`, and it is
  the primary-key component.

Verified on 16.15: a PK over a stored generated column works, and it collapses
`a\b.mp4` and `a/b.mp4` into one row — which makes the stray-path fork
(`file-sidecar.service.ts` `sidecarPath`) **structurally impossible** instead of
healed by hand. It reproduces `foldLedger`'s `healWindowsPath` key exactly
(`decisions.service.ts:145-157`).

**One CID identity.** `cid_canon` (canonical CIDv1 base32) is the join key; `cid_text`
is the verbatim value as the fleet recorded it and is **never** locally rewritten.
Postgres cannot compute `canonicalCid` (`ipfs.service.ts:757` is a base58→base32
rewrap in TS), so the app supplies it and a CHECK forbids NULL.

**One device identity.** `lfb.device.device_id smallint`. `pinned_by` labels and
`history/<device>.txt` filenames are **different spellings of one computer**
(`history-log.service.ts` sanitizes; `pinned_by` does not) — both are columns.

### 4.1 The decisions that are not obvious

**`file_decision` is a maintained fold, not a view.** `decision_event` is the
append-only truth; a trigger (`lfb.fold_decision`) maintains one current-state row per
`(unit_id, rel_posix)`. This is what turns the 96 ms per-unit fold into a 0.23 ms
lookup. `readLedger`/`foldLedger` keep working unchanged and become the **verification
oracle** — CI asserts `file_decision` equals `foldLedger(readLedger(root))` for every
unit, after every mirror-in.

Appending an event beside the unchanged `decisions.yaml` write, and letting the trigger
fold, is done in code:

Measured on this machine after the migration ran (105 units, 18,234 events, 4,242 folded
paths, zero mismatches): the TypeScript fold of the largest ledger — charlie-kirk,
3.1 MB, 11,423 events → 2,189 paths — takes **458–481 ms**, and reading the maintained
fold for the same unit takes **7.3–8.5 ms end to end** (2.7 ms server-side). A SQL
`DISTINCT ON` over the raw log for that unit measures **77–87 ms**, which is what the
0.23 ms figure above is being compared against — it is the *view* this table replaces,
not the TypeScript path. Whole-computer: **749 ms** of TypeScript folds versus **1.2 ms**
for one `count(*)` over `file_decision`.

**`pin_claim.origin` encodes the merge asymmetry.** `manifest-merge.ts:123-128` strips
our own claim from arriving entries and passes peers' through. An `origin` enum
(`'local' | 'wire'`) plus the `lfb_pin_claim_guard` trigger makes that asymmetry a
database invariant, so the SQL path and the YAML path cannot drift. This is the exact
correctness area the foreign-pin work keeps reopening: **"pinned" means pinned on THIS
computer by ANY local software; a peer's claim is never pinned-here.**

**`manifest_entry.stage` preserves the two-manifest split.** `pin/r/<repo>/manifest.yaml`
and `repos/<key>/manifest.yaml` are **not** twins to be collapsed — they are two stages
of a pipeline, and the tracking copy is written only when `publish_manifest` is on
(`pin.service.ts:793`). Collapsing them would start publishing manifests for repos the
user opted out of.

**`file_event` uses `UNIQUE NULLS NOT DISTINCT`.** 18 of 29,138 sidecars carry
`by: null`; a default `NULLS DISTINCT` constraint would re-insert them forever.

**`compression_sample` carries a UNIQUE idempotency key.** Without it a backfill re-run
doubles every sample and moves the mean — which would silently corrupt the charter's
learned baseline.

Index choices are justified by a named UI surface, not by intuition. Full

| One-Repo tabs Compress / Transcribe / Describe / OCR | per-tab partial index | **3 ms** |

## 6. What deliberately does NOT move

These are not leftovers. Each is on disk because moving it would make the product
worse, and each reason is a mechanism.

1. **The three Syncable Data Locations, in full** — 125 MB / 10,049 files (personal),
   137 MB / 19,696 files (act3), plus every working repo's `.lfbridge/`. The
   disqualifying constraint, and it is absolute.

2. **The local copy of every Category-B document.** Postgres becomes the authoritative
   *working* copy, but the file keeps being written by its designated serializer,
   because `mirrorToSyncRepo` copies **the file**, not a query result. Putting Postgres
   in the mirror's read path would mean a database bug ships corrupted state to the
   user's other computers over git — a class of failure that does not exist today.

3. **`.sync-repo` and `.durable-artifact`** — 105 markers and 105 latches, read by
   `tracking-root.service.ts`, a deliberate **leaf module** (fs + path + crypto only)
   that exists to break an import cycle. Giving it a database client recreates exactly
   the cycle it was written to avoid. `.sync-repo`'s first line is also an absolute
   path on **this** computer.

4. **All 35 MB of logs.** Three sufficient reasons: `error.err` is written
   **synchronously so it survives a crash-exit** (a fault trail that needs a working
   database is unavailable precisely when the database is what broke); `launcher.log`
   is the **only** place a V8 out-of-memory abort appears, because `abort(3)` runs no
   JavaScript; and we do not own the file descriptors for `launcher.log` or the
   ipfs/launchd logs. A queryable *index* over `transactions.log` is a good idea and is
   an open question (§8) — the files stay regardless.

5. **`config.yaml` and the small app-level YAML.** 3,539 bytes behind two caches; a
   cache-hit read is a single `statSync` at ~0.7 µs against a ~0.25 ms loopback round
   trip — **340× worse** in Postgres, and `effectiveFlags()` is called *per file*. More
   importantly `config.yaml` carries the `access:` block, which `security.service.ts:86-97`
   reads live and **fails closed** on every auth decision. Behind Postgres, an
   unreachable database is not "settings unavailable" — it is every user locked out of
   sign-in, on a product whose charter is *"runs locally first."*

6. **`.auth_session_secret` and the session store.** The 64-byte secret is the
   bootstrap root of trust and must be readable **before** any authenticated surface
   exists. A session store you cannot reach means signed out — and the sister app's
   2026-08-15 incident (19 admin logouts when batch work consumed every pooled
   connection) is exactly this failure.

7. **The job queue.** `queue/queue.jsonl` stays. Its stated payoff for moving — letting
   the launchd worker claim work directly — **is unreachable**: the three launchd
   workers are `scan`, `pin` and `device` (`internal.router.ts:27-41`), none of which
   executes a job-queue task, and `single-instance.ts` forbids a second backend.
   Worse, the naive `FOR UPDATE SKIP LOCKED` claim with a snapshot `COUNT` cap
   **provably oversubscribes**: run against this server with `cap=4` in two concurrent
   transactions, it yielded **8 rows running**. Moving it would trade a working
   fsync'd commit-point design for a broken concurrency one.

8. **`worker-misses.json`** — written by `code/deploy/launchd/run-worker.mjs`, a
   different, dependency-free process, in exactly the case where the backend is
   **down**. A Postgres write there is impossible and pointless.

9. **`mirror-memo.json` — the `src` half.** The `dst` half becomes `lfb.doc_render`.
   The `src` half must stay: `pairSettled` means "this job ran to completion and
   *neither* file has moved" (`tracking-sync.service.ts:666-670`), and the SDL side's
   `ino/size/mtimeNs` is the identity of a file Postgres must never own.

10. **`merge-quarantine/`** — its entire value is being the **exact bytes** that were
    about to be lost. Re-encoding a byte-preserving forensic copy into rows destroys
    the only property it has.

11. **The 3.25-million-file filesystem index — not built.** Measured under `$HOME`:
    **726,503 directories vs 3,254,966 files**, of which only 6,647 are ≥100 MB. A full
    file index is ~629 MB for data the product has no opinion about.

12. **`_do_batches/` and `_batches/` as sources.** `_do_batches` is explicitly
    disposable and recalculate-and-replace. `_batches` is O(1)-append by deliberate
    design (chosen to avoid O(n²) on the exact 1,440-file batch it was built for), and
    its meaning lives in the **absence** of a terminal record. Postgres indexes
    `_batches` read-only; it never writes it.

    Re-reading a manifest only when its `(size, mtime_ms)` no longer matches the stored
    token — and stamping that token from the stat taken **before** the read, so a
    manifest that grew mid-parse re-ingests next pass rather than claiming freshness for
    bytes nobody saw — happens in code:
    `code/packages/backend/src/modules/jobqueue/batch-index.service.ts` —
    `manifestIsIndexed()` / `syncBatchIndex()`. Measured: 5 manifests / 1,834 items
    ingest in **288 ms**; a second pass with no source change skips every scope.

## 7. Runtime

Implemented in `code/packages/backend/src/shared/persistence/pool.ts`.

### 7.1 The loopback posture is a compliance rule

The charter forbids this machine becoming a public gateway or relay. Postgres gets the
equivalent posture, and it is **asserted at boot**, mirroring the existing
`ipfs.public_gateway=false` check:

> In `server.mode='local'`, `SELECT current_setting('listen_addresses')` and WARN
> loudly if it is anything but `localhost` / `127.0.0.1` / `::1`.

Verified on this machine today: `listen_addresses=localhost`, `ssl=off`, bound only to
`127.0.0.1:5432` and `[::1]:5432`. **Compliant.**

`isLoopbackDatabaseUrl` is **parsed, not pattern-matched, and fails closed** — the
sister app's regex searched the whole string and returned a false positive on a remote
URL whose *password* contained `@localhost`.

The boot stage that connects the pool, runs the compliance probe, applies the schema
migrations, reads the epoch and adopts the five legacy sentinels — best-effort under
`auto`, a hard boot failure under `required` — is
`code/packages/backend/src/shared/persistence/boot.ts`, `bootDatabase()`, called from
`code/packages/backend/src/main.ts` immediately after `bootstrapState()`. The pool is
handed back on a clean stop by `closePool()`, from `main.ts`'s own `shutdown()`.

The database section of `GET /api/health` (and `GET /api/health/database`, which
`just db-status` reads) reports mode, reachability, server version, `listen_addresses`,
the §7.1 loopback verdict, the schema ledger head and the data-migration ledger's
done/pending/failed counts — in
`code/packages/backend/src/shared/persistence/boot.ts`, `databaseHealth()`.

### 7.2 First run types nothing

`just db-up` provisions role, database and extensions. `DB_MODE=auto` means a user who
has never heard of Postgres gets the YAML path and a WARN, not an error. Recipes:
`db-up`, `db-down`, `db-reset`, `db-psql`, `db-status`, `db-migrate`.

`just db-status` reports three distinct states: nothing on `:5432` / listening but
unprovisioned / provisioned with N migrations applied.

All six recipes are one portable `node` line each, per the justfile's own rules; the
provisioning, the three-state probe and the scoped disconnect live in
`scripts/dev/db.mjs`. `db-migrate` applies the schema through the runner rather than
`psql -f`, so the ledger, the checksum and the advisory lock all apply —
`code/packages/backend/src/shared/persistence/migrate-cli.ts`.

**`db-down` never stops the server and never drops anything.** The cluster on `:5432`
is shared — this machine has fifteen other databases on it — so `db-down` terminates
only the backends attached to `largefilebridge`. That scoping is not free: the obvious
`… WHERE datname = 'largefilebridge' AND pid <> pg_backend_pid() AND pg_terminate_backend(pid)`
puts a volatile, side-effecting function beside the predicates meant to restrict it,
and SQL guarantees no evaluation order between them. Measured on 16.15 against a
database with **zero** connections, it killed this session and both idle pool
connections of an unrelated app. The filter is therefore fenced behind an `OFFSET 0`
subquery — `scripts/dev/db.mjs`, `terminateSql()`.

> benchmark run behind this spec, and should be dropped.

## 8. Open questions

These are decisions, not gaps. Each is written down because getting it wrong quietly
is worse than deciding it late.

1. **RESOLVED (slice 12): the filesystem rollup (`fs_dir`, migration 0015) is
   DELETED.** The measurement the question asked for was taken, and it went against
   the table on both counts.

   **Warm `listDirectory('~')` is 2.6-3.0 ms** — median of 12 calls, reproduced across
   three separate processes (3.0 / 3.0 / 2.8 / 2.6 ms). That is inside the 3-6 ms band
   this question named as the delete threshold, so the rule as written decides it.

   **And the one cost `fs_dir` could have removed is 0.5% of the page.** On a full
   recompute (listing cache expired) the call is **147.8 ms**; running the identical
   listing with the subtree-interest answers already cached gives **146.9 ms**. The
   interest walk — the only one of `listDirectory`'s four costs a directory rollup
   could serve — is **0.8 ms of 147.8 ms**. The other 147 ms is `readdir`, the
   per-entry `statSync`, `computeBadges`, and the one `git check-ignore --stdin`, and
   **Postgres removes none of those**. A 726,503-row table with per-file write
   amplification, bought for 0.8 ms, is not a trade this app makes. Measured by
   alternating the two arms in one process with the OS page cache pre-warmed
   (`clearListingCache()` / `clearInterestCache()`).

   The two numbers that had already failed still fail: `GET /api/repos` measures 0 ms
   of synchronous handler time, and the Full Paths walk truncates on
   `FLAT_ITER_BUDGET` alone.

   **The gate is a mechanism, not a comment — and this is what it was for.** 0015
   first shipped as a `DO NOT APPLY` banner inside the SQL, and the runner applied the
   file anyway; a gate that does not gate is worse than none, because it reads as a
   decision that was enforced. Moving it to `shared/persistence/migrations/gated/` —
   which `loadMigrations()` cannot reach, since it reads the top level only — is what
   made "decide by measuring" a real option instead of a comment nobody could act on.
   The `gated/` directory went with the file (it held nothing else), but the
   **mechanism** stays: `reportGated` treats a missing `gated/` as the normal case, so
   the next migration that needs deciding rather than applying is gated by one `mkdir`
   and one `git mv`, and is logged on every boot from then on — nothing can be parked
   and forgotten. Implemented in
   `code/packages/backend/src/shared/persistence/migrate.ts`, `loadMigrations()` /
   `reportGated()`. Verified: the applied set is **15**, and
   `to_regclass('lfb.fs_dir')` is NULL.

2. **Sub-3-character search has no index.** `pg_trgm` cannot serve a term shorter than
   3 characters (verified: 2-char ILIKE fell back to a bitmap scan + filter at 5.6 ms
   against 0.41 ms at 5 chars). Proposed: the API refuses a <3-char term and the client
   filters the fetched page. That is right for a page and **wrong for a repo with 2,743
   candidates where the match is on page 6.** Decide: accept it, add a prefix btree on
   `base_name`, or require 3 characters in the UI.

3. **Nobody has scheduled the git-ignore axis.** The source is `git check-ignore`, which
   `units.service.ts:519-520` measures at **2.3 s for 1,875 paths** — git's own
   evaluation, not process startup. That cost **survives the migration in full**. Options:
   fill on the scan pass (+2.3 s per repo per scan), fill lazily per page with a stale-row
   refresh (renders UNDETERMINED until git answers — the current behaviour, and honest),
   or a low-priority background sweep. **This is the largest unaddressed cost on the
   One-Repo page and it is not a Postgres problem.**

4. **`decisions_policy.yaml` — merge or hold out?** It is *shared user intent*. Adding it
   to `MERGED_NEVER_COPIED` stops the loss but means two computers' policies never
   reconcile. A field-wise merge needs a conflict rule — probably newest `set_at` wins,
   ties by `set_by` lexical, matching `foldLedger` — but **that is a product decision
   about whose policy wins**, not a technical one.

5. **`pin_claim`'s inline CHECK is a placeholder.** Enforcement lives in the
   `lfb_pin_claim_guard` trigger because a CHECK cannot read another table. Decide: drop
   the inline CHECK (cleaner; intent stops being visible in `\d`) or denormalize
   `device.is_self` onto `pin_claim` as a generated column so a real CHECK can enforce it.

6. **A derived index over `transactions.log` and `error.err`.** Both stay on disk
   unconditionally. But `transactions.log` is 8,823 lines of BEGIN/END pairs (4,090 each)
   and the questions it exists to answer are aggregates grep cannot express: which BEGINs
   never got an END, p95 ms by op, heap trend across the heartbeats preceding a gap.
   Cheap and high-value. The blocker: the tailer must key on **inode, not path**, because
   `rollChain` renames the file underneath it, and a fast 5 MiB burst inside one poll
   interval can still lose lines — **which must be recorded as a gap, not papered over**.

7. **The compression baseline starts below its own confidence floor — MEASURED, and worse
   than the estimate.** Seeding was expected to yield "~110 samples" from "37 local + 37
   in the act3 SDL". Those are the **same 37 records**: the act3 SDL's
   `repos/charlie-kirk-83e62afc2c80/analysis/**` is the byte-for-byte mirror of the local

   The classifier — log-normal fit on bits-per-pixel-per-second, ±1-bucket widening, the

   Seeding the samples from the compression records (one ffprobe per file, measured 27 ms

   `~/BGit/Bryan_git/LargeFileBridge/code/packages/backend/src/modules/compress/baseline-backfill.ts`,

## 9. Implementation order

Twelve slices, each independently shippable. Slice 3 **must** land before any Postgres
write, because it is the fence.

| # | Slice | Independent value |
|---|---|---|
| 1 | Runtime: pool, mode, provisioning, just recipes | zero readers, zero writers, zero behaviour change |
| 2 | Migration engine + `migration_state.yaml` | adopts the 5 sentinels + 105 latches, keeps the files |
| 3 | **Close the four sync-boundary escapes** | fixes 4 live data-loss bugs; no Postgres at all |
| 4 | Units, devices, people | kills `folderForRepoId`'s 105-config scan |
| 5 | The file plane — census, tabs, search | One-Repo page 1 becomes an index-only scan |
| 6 | Decisions — the maintained fold | **96 ms → 0.23 ms** per unit; 135 ms → 0.37 ms fleet-wide |
| 7 | Manifests and pin claims | the merge asymmetry becomes a database invariant |
| 8 | Foreign pins | retires 8.47 MB resident JSON + the 40,000-entry eviction cap |
| 9 | Sidecars, artifacts, git-ignore | deletes 29,138 inodes of read amplification |
| 10 | The sync fence + the render gate | attacks `storage.mirror`, the genuinely blocking section |
| 11 | Rollups, history, compression baseline | first time the charter's learned baseline exists at all; **Repos list 1,076 ms → 34 ms measured** (105 rows, 105/105 identical to the oracle) |
| 12 | Derived projections; the watcher's write amplification | `_batches` indexed read-only; one dropped video costs **0.068 ms** instead of a **53.9 s** scan; `fs_dir` deleted on the measurement |

Cutover discipline, applied to every data slice:

* **Dual-write first.** Every existing YAML writer is untouched; a Postgres upsert is
  added behind it.
* **Reads cut over one surface at a time**, behind the tab or endpoint id, so a
  regression is scoped to one tab.
* **The old function becomes the oracle.** `foldLedger`, `readLedger` and friends keep
  working and are asserted equal to the SQL result in CI.
* **No slice claims more than it does.** Slice 10 expects roughly *half* of
  `storage.mirror` to survive, because `reconcileGen` still parses arriving SDL YAML by
  the fence.
