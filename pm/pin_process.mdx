description: The authoritative spec for what happens when LargeFileBridge pins — the "pin pass," the every-15-minute pass that adds files to IPFS and pins them. A pin pass is ALWAYS a full pass over every unit LFB knows on this computer (every git repo it has discovered, plus the computer unit), never one repo in isolation. However it is triggered — the 15-minute scheduleTask, the 48-hour session catch-up, or a manual "Pin now" on a single repo — it runs the full pass; a repo-scoped trigger only sets PRIORITY (that repo pins first, then the pass continues over the rest). # LargeFileBridge — The Pin Pass (add to IPFS)

This is the **primary, authoritative** spec for the act of pinning — adding files to IPFS and pinning
them. Three neighbors describe *pieces* of it and defer here for the process itself:

* [storage_local.mdx](./storage_local.mdx) — where pin state lives on disk (per-unit `config.yaml` +
  `manifest.yaml`) and the **background pin process** transparency contract (§13). The *mechanics of
  a pass* are here; storage owns the *state a pass reads and writes*.
* [scan.mdx](./scan.mdx) — the two **scheduleTasks** (4-hour discovery + 15-minute pinset) that
  *trigger* work. A **scan** discovers; a **pin pass** (this file) moves bytes.
* [one_repo.mdx](./one_repo.mdx) — the **Pin now** button on a repo page. The button is one *trigger*
  of the pass defined here.
* [sync_list.mdx](./sync_list.mdx) — the **trust & reconciliation** rules (§5 there) a pass applies
  when it reads any incoming list. The pass never *trusts*; it *reconciles*.

The pin pass runs LFB's own TypeScript-on-Node worker (never raw shell/`curl`), identically on a
laptop and on a server; only the resolved state root changes.

## 1. LFB knows every repo — there is no "LFB-managed" gate (LOCKED)

**Retire the idea of an "LFB-managed" repo.** A repo does **not** have to be added to, adopted by, or
turned on in LFB before LFB knows about it. LFB **discovers and understands every git repository on
the filesystem automatically** ([storage_local.mdx §7](./storage_local.mdx#7-the-scanner--discovering-repos-and-the-mask),
[scan.mdx](./scan.mdx)). Knowing a repo, tracking its large files, computing its counts, showing it in
the UI, and **reconciling it during a pin pass** all require **zero** user action.

Two distinct concepts — keep them separate everywhere:

| Concept | Who triggers it | What it means |
| --- | --- | --- |
| **Known / understood** | **Automatic** — the scanner | LFB has discovered this repo (or the computer unit), tracks its big files, reflects it in the UI, and **visits it every pin pass**. Every repo on disk is known. There is no opt-in to be known. |
| **IPFS-enabled (opted in to pin)** | **Explicit user action** — a confirmed choice | LFB may **add bytes to IPFS, pin them, and fetch them from peers** for this unit. This is the **only** thing that is opt-in. It is `pinned: true` in the unit's `config.yaml` (storage_local.mdx §6.2). |

So the per-unit **`pinned`** flag does **not** mean "managed vs. unmanaged." It means **"the user has
opted this unit into IPFS pinning/adding."** A `pinned: false` repo is **not** invisible or ignored —
it is fully known and fully visited by the pass; LFB simply does not add/pin/fetch its bytes until the
user opts in. This matches the charter: LFB never turns a computer into a pinner of content without an
explicit, user-confirmed action, and it never quietly mutates a repo.

> **Why this matters (charter alignment).** IPFS pinning is the one action with an outward, hard-to-
> reverse footprint (it makes this machine store and serve content). The charter requires it be
> **user-confirmed**. *Understanding* a repo has no such footprint, so it needs no gate. Conflating
> the two produced the "managed" mental model, which made a fresh repo look like it "wasn't in LFB"
> when in fact LFB knew it perfectly well and was merely not pinning it yet.

Discovering and registering every git working tree with no user action (identity + `pinned` seeded off, i.e. pinning-not-yet-opted-in) is handled in code:
`~/BGit/Bryan_git/LargeFileBridge/code/packages/backend/src/modules/store-model/units.service.ts` — `registerRepo`

Wording rule for all specs and UI copy: prefer **"every repo on this computer"** / **"known repo"** /
**"opted in to IPFS pinning"** over **"managed repo."** "Managed" survives only where it plainly means
"the row in our list," never as an opt-in gate.

## 2. Every pin pass is a FULL PASS (LOCKED)

A **pin pass** is one traversal of **every unit LFB knows on this computer** — every discovered repo
(`pin/r/<repo_name>/`) **plus** the computer unit (`pin/computer/`,
[storage_local.mdx §8](./storage_local.mdx#8-pincomputer--the-whole-computer-pin-unit)). One pass = the whole
machine, always.

**No trigger reduces the scope to a single unit.** The three triggers differ only in *when* and *what
runs first*, never in *what gets covered*:

| Trigger | Source | Scope | Order |
| --- | --- | --- | --- |
| **Scheduled** — 15-min scheduleTask | launchd/cron ([storage_local.mdx §13](./storage_local.mdx#13-the-background-pin-process--the-transparency-contract)) | Full pass | Natural order |
| **Session catch-up** — > 48h stale | a returning web session ([sessions.mdx §3](./sessions.mdx)) | Full pass | Natural order |
| **Manual — "Pin now" on a repo** | the repo page / row kebab / bulk ([one_repo.mdx §3.1](./one_repo.mdx#31-header--two-rows-and-neither-of-them-wraps-locked)) | **Full pass** | **That repo first (priority §3)**, then the rest |

The load-bearing rule the button must honor: **a manual Pin now on one repo prioritizes that repo but
still runs the full pass.** It does the user's repo first (so their result is immediate) and then keeps
going across every other known unit. It must **never** pin one repo and stop.

**A fourth, implicit trigger: the in-process watchdog backstop.** The three triggers above are all
*external* to the running app — a launchd fire, a returning session, a button. If the **launchd trigger
itself dies** (a stale trampoline path, an unloaded job), none of them fire and the flow stops silently.
So the always-on web app **watches its own workers**: any installed + enabled worker that has not run
within twice its interval is **run in-process** and its OS job is **repaired**, so a dead OS trigger can
never silently halt the pass while the app is up. This backstop — and the full taxonomy of ways the flow
can stall and how each self-heals or is surfaced — is specified in
[backbone_resilience.mdx](./backbone_resilience.mdx) (§3 the watchdog, §7 the overdue signal), implemented in
`~/BGit/Bryan_git/LargeFileBridge/code/packages/backend/src/modules/schedule/watchdog.service.ts` —
`startWatchdog()`.

The full pass over **every repo plus the computer unit**, and a manual Pin now that pins the clicked repo first (as the priority unit) then runs the pass over the remaining units in the background, are implemented in code:
`~/BGit/Bryan_git/LargeFileBridge/code/packages/backend/src/modules/pin/pin.service.ts` — `pinAll({ priorityDone })` (repos fan out via `runPool`, then `pinComputerUnit()`; both repo and computer share one generic `runUnitPin` core), invoked after the priority repo by `~/BGit/Bryan_git/LargeFileBridge/code/packages/backend/src/modules/repos/repos.router.ts` — `POST /api/repos/:repoId/pin`

## 3. Prioritization — order, never scope

When a pass is triggered from a specific repo, that repo's unit is the **priority unit**:

* It is pinned **first and awaited**, so the UI can return that repo's fresh detail immediately and the
  button feels instant.
* The rest of the pass then runs, in the **background**, so the response is never blocked by a long
  fan-out over 100+ repos.
* Priority changes **order only**. The remaining units are still all covered.

A paths-scoped manual pin (bulk **Pin now (selected)**, [one_repo.mdx §4.4](./one_repo.mdx#44-bulk-actions))
prioritizes this repo restricted to the selected files, then the full pass follows for the rest.

**Every "Pin now" affordance is selection-aware, and they all speak REPO-RELATIVE paths.** Checked rows pin
exactly those files; nothing checked pins the whole repo. Both halves of this were once broken and neither
failed loudly: the action row's **Pin now** always sent `undefined` (so checking three rows and picking it
pinned the ENTIRE repo), while the bulk menu sent the table's `fileId` keys (`<repoId>:<relPath>`) to a route
that matches on repo-relative paths, so `onlyPaths` matched nothing and the run reported "nothing to pin".
The selection Set is keyed by `fileId`, never by path — mapping it is mandatory, and a selection-aware action
must also **show its count on the label** so its scope is legible before the click.

Mapping the checked set to the path form each route speaks is implemented in code:
`~/BGit/Bryan_git/LargeFileBridge/code/packages/frontend/src/pages/repos/selection.ts` — `selectedRelPaths()` (pin + decisions) / `selectedAbsPaths()` (compress + the producing trio).

**THE SCOPE BINDS EVERY HALF OF THE PASS, and it binds what the pass WRITES BACK.** A paths-scoped run is
one the user asked for over specific files — the bulk **Pin now (selected)**, and the targeted pin every
decision click fires. Three rules, each learned from a real break:

* **Add** honors the scope (`onlyPaths`) — it always did.
* **Fetch-missing** must honor it too. It did not, so a "Pin now (5)" quietly pulled down every missing
  file in the repo and reported `fetched`/`failed` counts for files the user never checked.
* **Status write-back** must MERGE, never replace. A scoped run only classified the paths it was handed,
  so writing its orphan map wholesale erased every other file's `first_seen_at`. With a decision click or
  two a day the 24h grace never lapsed, and a file deleted here was never staled back to Undecided
  ([decisions.mdx §12](./decisions.mdx)). `mergeOrphans()` (`code/packages/backend/src/modules/pin/orphans.service.ts`)
  carries the untouched records forward; inside the scope this run's verdict wins.

And the selection is an **intersection**: a pin moves bytes for `sync`-decided files only, so a selection
of undecided rows is eligible for nothing. That is a UI obligation, not a silent server no-op — the button
asks to decide them first ([one_repo.mdx §4.4](./one_repo.mdx#44-bulk-actions)).

**Overlap guard.** Passes are idempotent, but overlapping passes waste work, so a single in-flight
guard collapses a second pass that starts while one is running (rapid Pin-now clicks, or a
scheduleTask that fires mid-pass). The **priority unit is always pinned by its own trigger** and is
never dropped by the guard — only the shared *remainder* fan-out is de-duplicated.

Answering with the priority repo's detail immediately, then running the remainder pass in the background under the in-flight guard, is handled in code:
`~/BGit/Bryan_git/LargeFileBridge/code/packages/backend/src/modules/pin/pin.service.ts` — `pinAll` (`passInFlight` guard) + `repos.router.ts` `POST /:repoId/pin` (`void pinAll({ priorityDone })`)

## 4. Parallelism — many cores, bounded concurrency (LOCKED design)

Modern machines have **20–30 cores**; pinning units one-at-a-time wastes almost all of them. A pin
pass is **concurrent by default**:

* **One global budget for all TRANSFERS, and it is a HARD 8 — not the core count (LOCKED, corrected).**
  Every add/pin/fetch is drawn through a **single limiter**, so total in-flight IPFS operations stay
  bounded **no matter how units × files multiply**. Concurrent state writes are safe because every write
  goes through the store layer's **per-file mutex + atomic temp-then-rename**
  ([storage_local.mdx §15](./storage_local.mdx#15-the-store-layer-how-code-touches-disk)).

  This limiter was sized `cores − 2`, which asked the wrong question of the wrong resource. Cores say how
  much **work** a box can do at once; a fetch is bounded by **one uplink shared by every transfer on it**,
  so scaling fan-out with cores makes a fast machine **starve itself faster than a slow one**. Measured on a
  20-core machine (⇒ 18 in flight) behind carrier-grade NAT at ~262 KB/s aggregate — a ceiling that does not
  move whatever the concurrency:

  | in flight | behaviour |
  | --- | --- |
  | 1 | 188 progress records in 170s, longest gap **5s** |
  | 8 | **six of eight** got one record then nothing for **99 of 100s**; the two that moved went **54s** and **80s** between records |

  §10.8.12 C allows 120s of silence and two attempts, so a starved file exhausts both and reports "the
  transfer never started" — for bytes that were live on IPFS the whole time and fetch in ~2s given the pipe
  to themselves. **70 files in one repo sat unpullable** there while every one of them was available.
  The cap costs nothing real: the uplink, not the fan-out, sets total throughput, so eight
  streams that finish beat eighteen that time out. `LFB_IPFS_TRANSFER_CONCURRENCY` widens it for a link
  that can take it.
* **Across units.** Units pin concurrently.
* **Within a unit.** A unit's independent per-file operations (add + pin new/changed files, fetch
  missing CIDs) **fan out in parallel** through the same global limiter — not a strict file-by-file
  loop. Ordering within a unit does not matter; each file owns a distinct manifest-row key, so the
  shared in-memory manifest/pinset maps are mutated without collision.
* **The priority unit** starts immediately; the remainder fan out behind it.

Sequential pinning is a **defect to fix**, not an acceptable baseline. Any place that still loops
`for … await` over units or files across a pass should be flagged and converted to the pool/limiter.

**Two budgets, because there are two resources.** The **unit** fan-out is CPU-shaped and keeps the canonical
**RESPONSIVE budget** (`cores − 2`) defined in [parallelization.mdx §1](./parallelization.mdx) and exposed as
`responsiveBudget()` in `~/BGit/Bryan_git/LargeFileBridge/code/packages/backend/src/shared/concurrency.ts`:
the pin pass is its **reference consumer** — work that runs *alongside* interactive use, leaving 2 cores for
the web app + IPFS node rather than running hot at ~90% like the mass-compute budget the job queue draws
([performance.mdx P-26](./performance.mdx)). The **transfer** ceiling is the hard 8 above and is deliberately
**not** drawn from that helper. Unifying them was the mistake: one definition is right only when there is one
resource, and "how many cores" can never answer "how many streams fit down this link."

The two-level fan-out — a `cores − 2` pool across units and one shared **hard-8** limiter that caps ALL
per-file add/pin/fetch work — is implemented in code:
`~/BGit/Bryan_git/LargeFileBridge/code/packages/backend/src/modules/pin/pin.service.ts` — `runPool` + `PIN_CONCURRENCY` (units) and `ipfsLimiter` + `IPFS_TRANSFER_CONCURRENCY` (per-file `Promise.all` through the limiter)

## 4a. One file, one transfer — the four pull entry points (LOCKED, learned from a defect)

A pin pass holds the repo **unit lock** (§2), so two passes never overlap on one repo. A **pull** holds
nothing, and it has **four** entry points that all reach the same repo:

* the repo page's **Pull down** button (`POST /:repoId/pull`);
* the **To Do** apply (`todo.router.ts`, fire-and-forget);
* **auto-sync-in**, hourly ([storage_company.mdx §14.3](./storage_company.mdx));
* **pull-retry**, 3-hourly ([warnings.mdx §10.8.12 C.3](./warnings.mdx)).

Two of them landing on one repo is **ordinary, not exotic** — a person clicks Pull down and the sweep that
has been re-arming for hours fires underneath it. Observed on `charlie-kirk`: **two dock cards pulling the
same 3.0 GB video**, one reading ≈2.3 GB and the other ≈2.2 GB. Each ran its own DAG walk and its own full
write to disk, and between them they held **two of the eight** transfer slots (§4) for bytes that only have
to arrive once — so the rest of the batch waited on duplicated work.

**A whole-pass lock is the wrong fix.** Serializing pulls the way §2 serializes pin passes would park the
user's click behind a three-hour background sweep, with a spinner and no explanation. The rules are:

* **Dedupe per FILE, not per pass.** The second caller for a file **joins** the first one's transfer and
  reports its outcome as its own — so every card still answers for every file it was asked about, its
  bar still reaches its total, and a failure carries the real reason rather than a fresh guess. The
  waiter does **not** hold a transfer slot.
* **A pull never blocks a pull.** Different files in the same repo keep running concurrently.
* **The background sweeps stand down; user actions never do.** auto-sync-in and pull-retry skip a repo
  that is already being pulled — a second pass would only re-derive the same list and paint a second
  card. Neither advances its cursor past the repo it skipped, so the next cycle finishes the job.
* **The byte reading is PER FILE, and the line must say so.** Up to eight files transfer at once and the
  note names the oldest, so the reading changes subject when that file settles: the total went **16 MB →
  85 MB** as the line handed over to a file already half-transferred, with the file count unmoved in the
  same glance. Per-file is the wanted behaviour — what was missing is the context. The `+N more` marker
  therefore sits with the FILENAME rather than at the end of the line, because the end is what a 360px card
  truncates first, and it is the only thing on the line saying the reading covers one of several transfers.
* **A pull writes back only what it CORRECTED.** Healed wrapper-directory CIDs are applied by
  **re-reading** the manifest and setting those paths — never by writing back the whole snapshot the pass
  opened with, which for an hours-long pull silently drops every entry a pin pass, the reconciler (§6b) or
  another pull wrote meanwhile. That short read-modify-write is the one moment a pull takes the unit lock.

*Implemented in:*
`~/BGit/Bryan_git/LargeFileBridge/code/packages/backend/src/modules/pin/pin.service.ts` — `fetchesInFlight` +
`inFlightKey` (per-file single flight), `repoPullInFlight(repoRoot)` (what the sweeps ask), and the
`healedCids` re-read at the end of `pullMissingInner`. The note's composition is
`~/BGit/Bryan_git/LargeFileBridge/code/packages/backend/src/modules/progress/work-note.ts` — `WorkNote.compose()`.

## 5. What a pass does per unit — and what the opt-in gates

For **every** known unit the pass visits, it always **reconciles** (no opt-in required):

1. **Rescan light** — pick up new/changed/deleted big files the last scan recorded ([scan.mdx](./scan.mdx)).
2. **Reconcile the pinset** — read the local IPFS pinset (`ipfs pin ls`) and refresh the unit's
   `pinned_by` claims against ground truth: confirm real pins, **drop** stale self-claims for pins that
   were lost, and surface pinned-but-untracked CIDs as **import** candidates
   ([storage_local.mdx §9.5](./storage_local.mdx#95-the-ipfs-pinset-is-the-source-of-truth--pinned_by-is-a-stale-cache),
   [scan.mdx §2.1](./scan.mdx#21-the-15-minute-scheduletask-reads-the-ipfs-pinset-import-already-pinned)).
   **The pinset compare is CANONICAL, and re-adds adopt an existing foreign-profile pin instead of
   duplicating it.** One file's bytes can be pinned under several different CID strings (CIDv0 `Qm…` vs our
   CIDv1 `bafy…`, and different `--raw-leaves`/`--cid-version` DAG profiles), and `ipfs pin ls` is
   base-sensitive — so a raw string compare goes blind to a pin whose encoding differs from ours (the "CLI
   says pinned, app says off" defect). Every pinset membership test canonicalizes to CIDv1 base32 first, and
   when an already-tracked file looks unpinned the pass re-hashes it once to see whether the bytes are
   already pinned under another profile and **adopts that CID** rather than re-adding a duplicate. Full rules
   and the honest boundary (why we do NOT auto-hash undecided files on the hot path) live in
   [knowledge/ipfs.mdx §5.1](../knowledge/ipfs.mdx#51-the-same-file-can-have-several-different-cids--never-compare-cid-strings-raw-locked-learned-from-a-defect).
   Implemented in `~/BGit/Bryan_git/LargeFileBridge/code/packages/backend/src/modules/ipfs/ipfs.service.ts` —
   `canonicalCid()` / `canonicalPinnedSet()` / `contentPinnedCid()`; applied at the reconcile seams in
   `~/BGit/Bryan_git/LargeFileBridge/code/packages/backend/src/modules/pin/pin.service.ts` — `runUnitPin()`.
3. **Reconcile any incoming Sync List** — never trusted, always reconciled per
   [sync_list.mdx §5](./sync_list.mdx#5-trust--reconciliation-the-load-bearing-rule).
4. **Write `status.yaml`** — last pin time, counts, errors — so the UI reflects the visit.

Only the **byte work** is gated by the `pinned` opt-in (§1):

* If the unit is **opted in** (`pinned: true`): add new/changed files marked **Add to IPFS (pin)** (the
  `sync` decision value — frozen on disk, rendered in the UI as "Add to IPFS (pin)") to IPFS, pin
  locally, fetch missing manifest CIDs from peers, and (if `publish_manifest`) write the committed
  in-repo manifest so git carries the list.
* If the unit is **not opted in** (`pinned: false`): the pass still visits and reconciles it (steps
  1–4) but adds/pins/fetches **nothing** — until the user opts in.

**Step 2 is NOT optional on a not-opted-in unit, and this is the rule that was missing in code.** Its text
still travels: the receive half of the mirror runs every pass, and the scan path publishes the unit's
manifest onward to the user's other computers. So a **self-claim on a `pinned: false` unit has no writer
that can ever correct it** — `runUnitPin`, the only place the claim was re-derived from the real pinset,
never runs for that unit. Measured on charlie-kirk (`pinned: false`, `last_pin_at: null`) on 2026-08-11:
**173 entries advertised this computer as holding CIDs that `ipfs pin ls` did not have**, published to the
fleet on every scan. The verification is now unconditional for both repos and storages, and it stays
free: the pinset is read **only when a claim of ours actually exists**, and the manifest is written **only
when a claim is genuinely unbacked**, so a healthy unit never pays for `pin ls` and never manufactures a
commit for the backbone to push. A **failed** `pin ls` leaves every claim untouched — a dead daemon is not
an empty pinset, and dropping our claims on it would tell the user's other computers this machine had lost
the bytes.
Self-claim verification for units whose pin pass does not run, in code:
`~/BGit/Bryan_git/LargeFileBridge/code/packages/backend/src/modules/pin/pin.service.ts` —
`healSelfPinClaims()`, called from `pinRepoFolderInner()` and `pinStorageUnitInner()` on the
`pinned: false` branch. The paired rule that stops new ones arriving lives at the merge:
`~/BGit/Bryan_git/LargeFileBridge/code/packages/backend/src/modules/storage/manifest-merge.ts` —
`mergeManifests(local, incoming, selfLabel)`.

**Device write-back is explicitly NOT gated by `pinned`.** Writing **this computer's own**
`devices/<self>.yaml` into a Git-backed storage — and running that storage's **git backbone cycle** to
carry it — is the "understand", not the "pin", side of §1: it puts your own identity text into your own
configured repo, with **no** outward footprint. So a Git-backed storage runs its **git backbone pass
(pull → write self device → commit → push) every pass regardless of `pinned`**; only the byte reconcile
above waits on the opt-in. This is the
guarantee the [every-10-minute device-registration worker](./devices.mdx#11-the-device-registration-write-back--every-10-minutes-locked)
is built around, and it is applied to this pin pass too — implemented in
`~/BGit/Bryan_git/LargeFileBridge/code/packages/backend/src/modules/pin/pin.service.ts` —
`pinStorageUnit(id)` (git backbone cycle + `writeSelfDevice` outside the `pinned` gate; only `runUnitPin` inside it).

**A manual Pin now is itself the opt-in.** Clicking Pin now on a not-yet-opted-in repo is an explicit
user action, so it flips that repo to `pinned: true` and does the byte work, then the every-15-min
scheduleTask keeps it fresh. (This is the exact bug §6 records: the manual path used to be gated by the
same `pinned:false` guard as the background scheduler and silently did nothing.)

The manual-vs-background gating — the background scheduler respects `pinned:false`, a manual Pin now moves bytes and flips the unit's opt-in on — is handled in code:
`~/BGit/Bryan_git/LargeFileBridge/code/packages/backend/src/modules/pin/pin.service.ts` — `pinRepoFolder(folder, onlyPaths, { manual })`

## 6. Never a silent no-op — report truthfully (LOCKED, learned from a defect)

This invariant exists because it was violated in production. The defect and the rule:

> **The defect.** `pinRepoFolder()` bailed at the top with `if (!cfg.pinned) return`, and that guard
> fired for the **manual** Pin now too — not just the background scheduler. A fresh repo defaults to
> `pinned: false` ([storage_local.mdx §6.2](./storage_local.mdx#62-pinrrepo_nameconfigyaml)), so clicking **Pin
> now** returned instantly, pinned nothing, wrote no manifest — **yet the UI still toasted "Pin
> complete."** A user could mark files and click Pin forever and nothing would ever pin. The status
> popped up and vanished because the backend genuinely did nothing.

The rules this locks in:

* **A user-initiated pin must do real work.** The manual path is the repo's *primary* action; it may
  never be short-circuited by the background-only `pinned` gate (§5).
* **Report what actually happened, not a fixed string.** A pin result carries **counts** — added,
  pinned, fetched, skipped, failed, **missing, orphaned, staled** — and the UI reflects them. If a run was
  genuinely a no-op (nothing eligible), say so explicitly ("Nothing to pin — no files marked Add-to-IPFS
  (pin)"), never a blanket "complete."
* **Every eligible file lands in exactly one bucket.** A file that is marked Pin but has no bytes on this
  computer used to fall out of the tally entirely, so a run over 12 deleted files reported `eligible: 12`
  with every other count at 0 — which the UI read as *"nothing to pin — no files marked Pin"*, a plain
  contradiction of the number beside it. Absence is a RESULT and is now split by cause: `missing` (never
  here — the pull-down offer) vs `orphaned` (deleted from a computer that held it,
  [decisions.mdx §12](./decisions.mdx)) and `staled` (whose grace period lapsed this run).
  `eligible === added + fetched + skipped + failed + missing + orphaned` is the shape to hold.
* **Success ≠ "the call returned."** A green toast requires the work to have occurred (or an honest
  "nothing to do"), and a failure must surface, not be swallowed.
* **A run that never STARTED is not a no-op.** A dead daemon, a failed `pin ls`, a repo that is gone —
  each returns the same all-zero tally as a healthy nothing-to-do, and the UI printed the same benign
  "Nothing to pin — no files marked Pin" for all four. The counts therefore carry `error`, and the toast
  says the real reason ("Pin didn't run — IPFS node unreachable"). Same rule as the bucket split above:
  distinct situations must never share one sentence. And an offer that cannot work is withdrawn, not
  quietly attempted — with the node unreachable, `Pin now` is disabled and its tooltip says why.
* **A no-op must name its SCOPE.** "Nothing to pin — no files marked Pin" is false comfort after a click
  on `Pin now (5)`; a scoped run says "none of the selected files is set to Add to IPFS."
* **Long work must be VISIBLE while it runs, not only summarized after.** Every pin — the manual one, the
  decision-triggered one, and the every-15-minute full pass — registers in the progress registry and
  reports **per-file** (`n / N files`) or **per-unit** (`n / N units`) counts, so the dock shows a moving
  bar rather than a bare spinner. A pass moving bytes for minutes while the app looks idle is
  indistinguishable, from the user's chair, from a sync that has stopped. A repo-scoped card also names its
  SCOPE ("`<repo>` (3 selected)"), because a selective pin and a whole-repo pin are different work.
* **A COUNT IS NOT ENOUGH — the pass must also name the STEP it is on** ([webapp.mdx §12a](./webapp.mdx)).
  Counts only move when a *file* settles, and the longest stretches of a pass settle no files at all: the
  sync-repo reconcile re-parses and rewrites the ledger, the pinset read enumerates every pin on the
  computer, a storage's git cycle fetches and merges over the network, and a single 4 GB video occupies one
  slot for minutes. Every one of those rendered as `working` with a still bar — which is also what a wedged
  pass looks like. So each step reports a `note` in the user's language, a big file reports its **bytes**
  inside that line, and a run **queued behind another pass on the same repo says it is waiting** rather
  than spinning silently. Reported before the step, and — where the step is synchronous — with a
  `yieldToLoop()` so the progress poll is actually served while it runs.

This is a **design smell to hunt for everywhere**: any action whose success UI is decoupled from
whether it did anything. Flag and fix such silent no-ops on sight.

## 6b. The reconciler — the three records must AGREE, and one pass owns saying so

A tracked file is described in three independent places, and until this pass existed nothing compared them
as a set:

1. the **manifest's `pinned_by`** — which computers claim to hold the bytes;
2. the **IPFS pinset** — what this node actually holds;
3. the **working tree** — what is actually on disk.

Each existing pass tends one edge of that triangle and only for the units it visits, so a file could sit
indefinitely in a state every downstream surface then reported as fact — `Pull down`, the three-state pin
icon, and `Not backed up` all read these records and cannot tell a stale one from a true one. The observed
shapes: a claim on bytes this computer no longer held (so a teammate was told a second copy existed), a file
sitting on disk the node had never pinned (so it was NOT a second copy and no peer could fetch it), and a
recorded CID that is a wrapper **directory** rather than a file (§5.1 Layer 0) — which no computer in the
fleet can ever `cat`, so the file is unreachable for everyone until someone who holds the bytes re-adds it.

**It validates RECORDS; it does not move bytes.** Nothing here adds a file to IPFS, fetches one, or writes
one back to the working tree. Those already have owners — `runUnitPin`'s add/fetch-missing (§5), the
pull-retry pass (warnings.mdx §10.8.12 C.3) and auto-sync-in (storage_company.mdx §14.3) — and a second
mover would race them for the same files under a different set of rules. The one outward call it makes is
`ipfs add --only-hash`, which computes what a local file's CID *would* be without storing a block or
creating a pin: a read, used to recognise bytes we already hold under a CID no string comparison can reach.
A disagreement it cannot settle by editing a record is therefore **reported**, not acted on.

**What it checks, per manifest entry.** Deciding the verdict from `onDisk` × `heldHere` × `claimed` and
correcting the record is implemented in code:
`~/BGit/Bryan_git/LargeFileBridge/code/packages/backend/src/modules/pin/reconciler.service.ts` — function
`reconcileEntry()`; the per-repo pass that folds both manifests, writes them back and bumps the repo's
topics is `reconcileRepo()` / `reconcileRepoInner()` in the same file.

| Situation | What the record must say | Action |
|---|---|---|
| we claim it, the pinset does not hold it | not ours | drop **our** claim |
| the pinset holds it, we never claimed it | ours | add our claim |
| our dropped claim was the last one, and no copy is on disk | nothing at all | remove the entry |
| on disk, looks unpinned, recorded CID is a **file** | maybe pinned under another add profile | `--only-hash` probe; a hit is recorded as a CID **equivalence** |
| on disk, looks unpinned, recorded CID is a **directory** | the CID of the bytes we actually hold | replace the recorded CID — see below |
| recorded CID is a **directory**, unwrappable, not on disk | the file inside it | replace the recorded CID |
| recorded CID is a **directory**, interior gone | unknown — do not guess | report: it needs re-adding where the bytes are |

**Equivalence or replacement is decided by which record is wrong.** A differing FILE CID is a legitimate
second add profile: the fleet's record stays exactly as the fleet wrote it and the pair is remembered
locally (§5.1 Layer 3). A DIRECTORY CID is not a spelling of the file at all — nobody can `cat` it — so an
equivalence there would repair only the machine that computed it while every peer kept a CID it can never
use. On the one computer that still holds the bytes, **replacing** the recorded CID is the single repair
that travels to the others, and it is the only way a wrapper-CID file becomes pullable again once the
original wrapper's interior nodes have been collected.

`pinned_by` means "these bytes are pinned on this computer" and nothing else — not "the file is here", not
"we intend to". A claim we cannot back tells a teammate a second copy exists when it does not; a pin we hold
but never claimed tells them the opposite. This is the rule `runUnitPin` already applies to the units it
visits, extended to every unit and enforced in **both** directions.

**The other record on a repo.** The machine-local frozen `decisions:` enum is a projection of the shared
ledger, and every read path trusts the projection rather than re-folding it, so drift there is the same
class of defect as a stale pin claim. The pass re-projects rather than re-deriving its own answer.
Implemented in code:
`~/BGit/Bryan_git/LargeFileBridge/code/packages/backend/src/modules/storage/decisions.service.ts` —
`reconcile()`, called per repo from `reconcileRepoInner()`.

**Two invariants outrank "make the records agree", and the pass yields to both.**

* **A peer's claim is not ours to edit.** We can verify exactly one computer's bytes — this one. Every write
  touches our own label only, and an entry disappears only when the last claim on it was ours and we just
  disproved it. Union merge makes that safe: a peer that still holds the file re-contributes the entry on
  its next mirror, which is precisely the confirmation we lacked.
* **A delete must still mean something** (decisions.mdx §12). "Pinned here but not on disk" is also the
  signature of a user deleting a synced file. This is the sharpest reason the pass writes no bytes: putting
  that file back from our own pin is exactly the surprise re-pinning §12 forbids. `orphans.service.ts` owns
  that judgement and its grace period, and the reconciler neither restores the file nor pre-empts the
  verdict — it only records that we do, in fact, still hold the bytes.

**A pass that cannot see does nothing.** An unreachable node answers "unknown", never "nothing is pinned"
(§5.1). Read as empty, every rule above fires the wrong way at once and a single pass could strip a repo's
whole manifest, so the pass declines to run instead of guessing. Implemented in code:
`~/BGit/Bryan_git/LargeFileBridge/code/packages/backend/src/modules/pin/pin.service.ts` — `pinnedCidSet()`
returning `null`, checked at the top of `reconcileRepoInner()`.

**Concurrency and cost.** It takes the SAME per-repo unit lock the pin pass takes — both write the manifest
wholesale from a snapshot taken at entry, so running them together would silently drop the loser's repairs
(`unit-lock.ts`). Entries are checked serially, so at most one probe is ever in flight and no second
concurrency budget exists beside §4's. Probes are capped per repo per pass (`LFB_RECONCILE_CID_PROBES`,
default 25): an `--only-hash` re-hash reads the whole file, and a wrapper unwrap is a network round trip
that re-proves the same thing.

**Scheduling — periodic, in-process, nothing to install.** Every 6 hours (`LFB_RECONCILE_MS`), first run no
sooner than 5 minutes after boot (`LFB_RECONCILE_BOOT_MS`) because the daemon it interrogates is usually
still coming up. There is no launchd/schtasks/systemd job and nothing for the user to enable — it is a
re-arming timer inside the running server, armed once at boot. The due time is persisted for the reason
pull-retry persists its own: a restart must RESUME the remaining wait, not reset it, or a long-interval pass
never runs on a machine that restarts often. Implemented in code:
`~/BGit/Bryan_git/LargeFileBridge/code/packages/backend/src/modules/pin/reconciler.service.ts` —
`startReconciler()` and `nextReconcileDelayMs()`; armed from `code/packages/backend/src/main.ts`.

**Asking for it now.** A user who does not want to wait for the next tick can run one repo's repair on
demand; the response carries the refreshed detail so the metric tiles show corrected numbers without a
second round trip. Implemented in code:
`~/BGit/Bryan_git/LargeFileBridge/code/packages/backend/src/modules/repos/repos.router.ts` —
`POST /api/repos/:repoId/reconcile`.

Locked tests: `code/packages/backend/src/modules/pin/reconciler.spec.ts`.

## 7. Acceptance criteria

1. **Every repo is known automatically** with no user action; the pass **visits and reconciles every
   known unit** (all repos + the computer unit) regardless of opt-in (§1, §2, §5). No spec or UI copy
   frames a repo as needing to be "added"/"managed" before LFB knows it.
2. The per-unit **`pinned` flag means "opted in to IPFS pinning,"** not "managed." A `pinned: false`
   unit is still fully known, visited, and reconciled; only byte work (add/pin/fetch) is withheld (§1,
   §5).
3. **A pin pass is always a full pass.** No trigger — scheduled, session catch-up, or manual
   Pin now — reduces scope to one unit (§2).
4. A **manual Pin now on one repo prioritizes that repo (pinned first, awaited) and then runs the full
   pass over the remaining units** in the background; it never pins one repo and stops (§2, §3).
5. The pass runs with **bounded concurrency** across units (`cores − 2`) and fans out per-file work
   within a unit through the **hard-8 transfer limiter**; sequential `for…await` over a whole pass is
   treated as a defect (§4).
6. A **manual Pin now is the explicit opt-in** for its repo (flips `pinned: true` and moves bytes),
   while the **background scheduler still respects `pinned: false`** (§5).
7. **No silent no-ops.** A user-initiated pin does real work or reports an honest "nothing to pin,"
   with truthful counts; a green success toast is never shown for a run that did nothing, and failures
   surface (§6).
8. Overlapping passes are **collapsed by a single in-flight guard**; the priority unit is always pinned
   by its trigger and never dropped by the guard (§3).
