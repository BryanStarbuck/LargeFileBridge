# LargeFileBridge — The MCP server (`lfb`)

## About Large File Bridge

Large File Bridge is a local-first web app (TypeScript on Node; UI at http://localhost:2222/, REST backend
at http://localhost:8787/) that keeps the **big, git-ignored files** in a person's repos and folders —
videos, large images, audio and other large binaries — **in sync across their own computers by pinning them
on IPFS**, while git carries the small text files and the record of what exists. It scans repos and
directories for large files, nudges the ones that should be git-ignored (never ignoring anything on its
own), tracks each file with a content hash and per-file metadata, and pins and fetches those files so every
computer holds the same copy; a 15-minute `launchd` job keeps that going in the background. Around that
core it helps people take care of the media itself: it finds files that are needlessly uncompressed and
compresses them only when asked, writes transcripts, AI visual descriptions and OCR text beside them, and
— the subject of this spec family — **recognizes when two files are the same content** even after a
resize, re-compression, re-encode or format change. Everything runs on the user's own machine: sign-in is
Google through OpenAuthFederated for allow-listed accounts only, the computer never acts as a public IPFS
gateway or relay, and the fingerprint features never touch the network.

The MCP server lets **Claude Code** use Large File Bridge from a chat. For example: *"get the perceptual
fingerprints for everything in ~/Videos/2026 as a CSV"*, *"is this clip part of that longer video?"*, or
*"which of these photos are the same picture?"*. It runs on the same computer as the web app, talks only
to it, and computes nothing itself.

The API it calls and the engine behind that API are described in the next section. The sibling thin
client is the `lfb` CLI ([cli.mdx](./cli.mdx)).

## The three fingerprint specs, and how they work together

Perceptual fingerprints are specified in three files. Each one owns one layer, and each layer talks only to
the layer below it. **You are reading mcp.mdx, the Claude Code layer at the top.**

```
  Claude Code (chat)              Web app (browser)                Terminal
        │ stdio, JSON-RPC               │ signed-in session              │
        ▼                               │                                ▼
  lfb MCP server ── mcp.mdx             │                     lfb CLI ── cli.mdx
        │ X-LFB-Api-Key, loopback only  │                                │ X-LFB-Api-Key
        └───────────────────┬───────────┴────────────────────────────────┘
                            ▼
  REST API  /api/fingerprints/*  ── apis.mdx
  local API key · hybrid 200/202 jobs · lookup · compare · CSV export
                            │
                            ▼
  Fingerprint engine  ── perceptual_fingerprint.mdx §FD
  fingerprint.service → lfb-pdq Go sidecar (PDQ) + the user's own ffmpeg for video frames
                            │
                            ▼
  Postgres lfb.perceptual_fp + memory tier · CSVs in ~/T/_large_files_bridge/fingerprints/exports/
```

The CLI shares the same key and base URL, but today it calls `/api/files/list`, not the fingerprint routes.

| Spec | The question it answers | What it owns | What it leaves to the others |
| --- | --- | --- | --- |
| [perceptual_fingerprint.mdx](./perceptual_fingerprint.mdx) | *What is a fingerprint, and what computes it?* | The research and the algorithm choice (PDQ for images, PDQ per frame for video); the match thresholds, quality floor and the video duplicate / subset rule; storage and the validity rule; the no-network guarantee. | How programs reach it (apis.mdx) and how Claude Code presents it (mcp.mdx). |
| [apis.mdx](./apis.mdx) | *How does any program ask for one?* | The local API key and machine-channel security; the endpoints; the hybrid sync/async job contract and its wait budgets; the error codes; the measured timings that justify the contract. | What a fingerprint means and when two match (perceptual_fingerprint.mdx); the Claude Code tools (mcp.mdx). |
| [mcp.mdx](./mcp.mdx) ◀ **this spec** | *How does Claude Code ask for one?* | The eleven `lfb_` tools; the stdio transport; reply shaping (summaries, byte cap, pointer to the CSV); the playbook `ai/lfb_mcp.md`; registration with Claude Code. | Every answer (computed by the backend, apis.mdx) and creating the key (apis.mdx §3.2). |

**One request, end to end.** The user asks Claude Code: *"is clip.mp4 part of long.mp4?"*

1. Claude calls `lfb_fingerprint_compare` (mcp.mdx §5).
2. The MCP server re-reads the key from `~/.credentials/large_files_bridge.json` and sends
   `POST /api/fingerprints/compare` to `127.0.0.1:8787` (mcp.mdx §4).
3. The backend honors the key only from a loopback peer with a loopback Host header (apis.mdx §3.5).
4. For each file it reuses the stored fingerprint if the size, modification time and engine version are
   unchanged, or computes a new one through the `lfb-pdq` sidecar (perceptual_fingerprint.mdx §FD.3–§FD.4).
5. It compares the two frame lists. A shared fraction ≥ 0.8 is a **duplicate**; otherwise a longest matching
   run covering ≥ 0.7 of the shorter video is a **subset**, returned with its time range
   (perceptual_fingerprint.mdx §4, apis.mdx §7.8).
6. The MCP server wraps the answer in its JSON envelope (mcp.mdx §6), and Claude reports it as a
   **signal**. Nothing is deleted or moved because of a match.

**Where a change starts.**

* **A different algorithm, threshold or storage rule** → perceptual_fingerprint.mdx first. The API and the
  MCP server only carry the new values through.
* **A new capability for callers** → a backend endpoint in apis.mdx first, then an MCP tool that wraps it.
  The MCP server holds wrapper code only (mcp.mdx §1), so a tool can never be the first place something is
  computed.
* **How Claude Code behaves** (tool wording, reply size, what to do on an error) → mcp.mdx and
  `ai/lfb_mcp.md` only.

**A number used in more than one spec has one owner.** The others cite it; if they ever disagree, the
owner wins and the others are corrected.

| Number | Value | Owner |
| --- | --- | --- |
| Image match threshold (normal / strict) | Hamming ≤ 32 / ≤ 24 of 256 bits | perceptual_fingerprint.mdx §4 |
| PDQ quality floor | 50 (of 100) | perceptual_fingerprint.mdx §4 |
| Video duplicate / subset | shared fraction ≥ 0.8 / longest-run coverage ≥ 0.7 | perceptual_fingerprint.mdx §4 |
| When a stored value is still valid | same size, modification time and engine version | perceptual_fingerprint.mdx §FD.4 |
| Server wait budget (`wait_ms`) | default 20 s, maximum 55 s | apis.mdx §6.2 |
| MCP wait cap / MCP HTTP timeout | 50 s / 75 s | mcp.mdx §6 |
| MCP reply byte cap | 200 KB (up to 2 MB) | mcp.mdx §6 |

The shared threshold constants, in code:
`~/repos/LargeFileBridge/code/packages/shared/src/fingerprints.ts` — `PDQ_MATCH_THRESHOLD`, `PDQ_MATCH_THRESHOLD_STRICT`, `PDQ_QUALITY_FLOOR`.

## 1. Placement (charter amendment)

```
LargeFileBridge/
├── ai/lfb_mcp.md   # the MCP playbook — served to Claude Code as the server's instructions
├── mcp/            # the MCP server — a peer of pm/ and cli/
│   ├── justfile    # build / run / register
│   └── code/       # ALL implementation: src/, scripts/, package.json, tsup.config.ts
├── cli/            # the CLI (cli.mdx)
├── code/           # the web app — still owns ALL functionality
│   └── sidecars/pdq/   # the Go PDQ fingerprint engine (perceptual_fingerprint.mdx §FD.3)
└── pm/
```

* **`mcp/code/` is the third sanctioned code location**, after `code/` and `cli/code/`. It follows the same
  rule as the CLI: it may hold **MCP wrapper code only** (tool schemas, HTTP calls, result shaping, the stdio
  lifecycle). Anything that computes an answer about files belongs in the backend as a REST endpoint first.
* **`ai/`** holds prompt files an AI reads. `ai/lfb_mcp.md` is the source of truth for the server's
  instructions.

## 2. Registering it with Claude Code

* **Build:** `just build-mcp` (root justfile), or `just build` in `mcp/`. The output is **one** bundled,
  executable file, `mcp/code/dist/index.js`, with the MCP SDK inside it. Claude Code spawns the server by
  absolute path from an unrelated working directory, so nothing may depend on resolving `node_modules`.
* **Register:** `just mcp-register` prints the line, and `just mcp-register apply` runs it:

```
claude mcp add --scope user lfb -- node ~/repos/LargeFileBridge/mcp/code/dist/index.js serve
```

* **Checks:** `claude mcp list` should show `lfb … ✓ Connected`. In a session, `lfb_whoami` confirms the
  backend, the key and the engine.
* **Hand probe (no Claude Code needed):** `node mcp/code/scripts/probe.mjs [dir] [fileA] [fileB]`. It spawns
  the built server over stdio exactly as Claude Code does, and runs whoami, files, compare, a directory job,
  the CSV export and two error cases.

## 3. Transport and lifecycle

* **stdio only.** There is no HTTP listener, so no DNS-rebinding surface of its own
  ([apis.mdx §3.6](./apis.mdx)).
* **Nothing is ever written to stdout except JSON-RPC.** A single stray line desynchronizes the transport
  and Claude Code just shows a dead server. All logging goes to stderr and `error.err` (§7).
* **Startup makes no network call.** `tools/list` answers with the backend down; a server that probed first
  would look "failed to start" whenever the web app is merely stopped.
* **Argv:** the only command is `serve`. Anything else prints usage to stderr and exits 1.
* **Shutdown** on SIGINT, SIGTERM or stdin EOF: in-flight calls get up to 8 s to finish, then the process
  exits.

The entry point, in code:
`~/repos/LargeFileBridge/mcp/code/src/index.ts` — `main()`.

## 4. Authentication

* The server reads `large_files_bridge.api.secret_key` from `~/.credentials/large_files_bridge.json`
  (`LFB_CREDENTIALS_FILE` overrides). It re-reads the file **on every call**, so a rotation in the web app
  takes effect immediately.
* It **never creates** the key. Creating it is the web app's job (backend boot, or Settings → Local API key),
  and the server says so when the key is missing.
* It **refuses** a credentials file that other users can read (`credentials_mode`, fix: `chmod 600`).
* Each call carries `X-LFB-Api-Key` and `X-LFB-Client: mcp` to `http://127.0.0.1:<BE_PORT|8787>/api`. The
  host is fixed to loopback, and there is no setting to change it.
* The key is never logged or returned; `lfb_whoami` shows only `sha256:xxxxxxxx`.
* The full threat model (another computer, DNS rebinding, another OS user, a leaked key, an AI asked to
  print the key) is in [apis.mdx §3.7](./apis.mdx). This server adds no attack surface of its own: it opens
  no listener and has no setting that points it anywhere but loopback.

The key reader, in code:
`~/repos/LargeFileBridge/mcp/code/src/credentials.ts` — `readApiKey()`, `keyFingerprint()`.

The HTTP client and its error codes, in code:
`~/repos/LargeFileBridge/mcp/code/src/http.ts` — `api()`, `ApiError`.

## 5. Tools

Every tool name starts with `lfb_`, so it cannot be confused with another server's tools. Input schemas are
zod, published as JSON Schema. Relative paths resolve against the directory Claude Code was started in, and
`~` is home.

| Tool | Calls | Use it when |
| --- | --- | --- |
| `lfb_whoami` | reads the key file, then `GET /fingerprints/info` | First, whenever anything fails. Reports the backend up or down, whether the key is present and authenticated, the engine built or missing, and whether Postgres is storing results. |
| `lfb_fingerprint_files` | `POST /fingerprints/compute` | The user names files (up to 5,000). |
| `lfb_fingerprint_directory_csv` | `POST /fingerprints/directory-csv` | **The fast default for a folder, a repo, or several locations**, and for any "fingerprint this folder as a CSV" request. One native process fingerprints the whole tree on ~80% of the cores, filtered by `extensions`; the answer is `csv_path`. **One call at a time:** for several directories, call it for one, wait for that job to finish, then call it for the next. Never call it in parallel or from several agents (apis.mdx §7.9). |
| `lfb_fingerprint_directory` | `POST /fingerprints/scan` | The older per-file directory walk (about 5 files/s). Only when results are wanted paged inline rather than as a CSV. |
| `lfb_fingerprint_job` | `GET /fingerprints/jobs/:id` | A result came back `pending`. `wait_seconds` (≤ 50) long-polls; `offset` and `limit` page the results. |
| `lfb_fingerprint_export_csv` | `GET /fingerprints/jobs/:id/csv?save=true` or `GET /fingerprints/lookup?dir=…&format=csv&save=true` | Any CSV or spreadsheet request, or more than ~50 files. Returns `csv_path` in the state root. |
| `lfb_fingerprint_lookup` | `GET /fingerprints/lookup` | "What is already stored?" Never computes, and reports whether each stored value is still valid. |
| `lfb_fingerprint_compare` | `POST /fingerprints/compare` | "Are these the same?" For videos it also says duplicate vs subset, and the time range. |
| `lfb_fingerprint_cancel` | `POST /fingerprints/jobs/:id/cancel` | Stop a running job. |
| `lfb_list_jobs` | `GET /fingerprints/jobs` | Find a job after a timeout, before starting it again. |
| `lfb_files_list` | `GET /files/list` | The CLI's task-category listing (compressible, gitignore, transcribable, …). |

The tool definitions, in code:
`~/repos/LargeFileBridge/mcp/code/src/tools/fingerprints.ts` — `fingerprintFiles`, `fingerprintDirectory`, `fingerprintDirectoryCsv`, `fingerprintJob`, `exportCsv`, `lookup`, `compare`, `cancel`, `listJobs`.

The diagnostics and the file list, in code:
`~/repos/LargeFileBridge/mcp/code/src/tools/orientation.ts` — `whoami`, `filesList`.

**Job-shaped replies** (files, directory, job) are condensed for the model:

* `job_id`, `pending`, `status`;
* `progress`: done, total, discovering, eta_seconds;
* `summary`: counts per outcome, such as `ok_image`, `ok_video_cached` and `failed_decode_failed`;
* `next`: one sentence saying what to call next;
* `csv_path`: the job's CSV once it has finished (every finished job writes one);
* then the results. `lfb_fingerprint_directory_csv` returns none inline; its CSV is the answer. It also
  returns `engine` (workers, cores, waiting_for_slot).

### 5.1 Typical flows

* **A few files** — *"fingerprint these three photos."* One call to `lfb_fingerprint_files` comes back with
  `pending: false` and every value. Done in one round trip.
* **A big folder** — *"fingerprint everything in ~/Videos/2026 as a CSV."*
  1. `lfb_fingerprint_directory_csv` (with `extensions` if the user named file types) returns
     `pending: true`, a `job_id`, progress, and `next`.
  2. `lfb_fingerprint_job` with `wait_seconds: 50` and `limit: 1`, repeated until `pending: false`. Each
     call blocks on the server, so this is a handful of calls, not a spin.
  3. The finished job's `csv_path` is the CSV. Claude Code reads that file directly instead of pulling
     thousands of rows through the chat.
* **Several locations** — *"fingerprint my mirror, Dropbox and the repo."* Run the big-folder flow for the
  first location, wait until its job finishes, then start the next. Each job already uses about 80% of the
  cores, so running them in parallel or through agents is never faster. The server also queues a
  second bulk scan until the first ends.
* **Same or not** — *"is this clip part of that longer video?"* One `lfb_fingerprint_compare`. The reply's
  `note` says duplicate, subset (with `longest_run` giving the time range) or different. The model reports
  it; it never deletes or moves anything because of it.
* **A tool timed out or the chat was interrupted** — `lfb_list_jobs` first, then resume the existing job
  with `lfb_fingerprint_job`. Starting the request again would start a second job over the same files.
* **Anything fails** — `lfb_whoami` first. It separates "the web app is not running", "the key is missing or
  wrong", and "the PDQ engine is not built" in one call.

## 6. Response contract

* **One text block per call, holding JSON.**
  * Success: `{"ok":true,"data":…}`.
  * Failure: `{"ok":false,"code","message","hint"}` with `isError: true`.
  * A failure the user can act on is a **result**, never a thrown protocol error. A thrown error reads to
    the model as "the tool is broken"; a result reads as "here is what to do".
* **Error codes the playbook teaches:** `backend_down`, `unauthorized`, `credentials_missing`,
  `credentials_mode`, `credentials_invalid`, `timeout`, `bad_request` / `bad_arguments`, `not_found`,
  `http_error`, `unknown_tool` and `internal`. Per-file codes are listed in apis.mdx §2.
* **Byte cap:** a reply over 200 KB (`LFB_MCP_MAX_BYTES`, up to 2 MB) drops trailing results and says so,
  with `truncated: { shown, of, hint }` pointing at the CSV export. The model never receives a
  context-flooding reply.
* **No automatic retries.** Every fingerprint request is a job, so a blind retry would start a second job.
* **The timeout comes from the environment, never from a tool argument.** `LFB_MCP_TIMEOUT_MS` defaults to
  75 s, which is more than the longest server-side wait (50 s), so the backend decides when to hand back a
  job. A tool argument that could stretch a timeout or redirect the URL would be an injection surface.

The envelope, argument validation and bug logging, in code:
`~/repos/LargeFileBridge/mcp/code/src/server.ts` — `McpServerHost.call()`.

The byte cap and the summaries, in code:
`~/repos/LargeFileBridge/mcp/code/src/tools/shape.ts` — `capResults()`, `summarize()`, `resolveUserPath()`.

## 7. Errors and logs

* **WARN and ERROR** go to stderr, which Claude Code keeps in its MCP log, **and** are appended to the app's
  fault trail `~/T/_large_files_bridge/error.err`, in the backend's line format, tagged `[mcp:<context>]`.
  There is **one place** to look for every Large File Bridge failure. Rotation stays the backend's job; the
  MCP server only appends whole lines.
* **Uncaught exceptions and unhandled rejections** are logged to `error.err` as well; neither takes the
  server down.
* **Values are sanitized.** Control characters are stripped from logged values (file names, server
  messages), so nothing can forge a log line.

The logger, in code:
`~/repos/LargeFileBridge/mcp/code/src/logger.ts` — `log`, `logError()`.

## 8. The playbook (server instructions)

* **Source:** `ai/lfb_mcp.md`.
* **Contents:**
  1. what the server is;
  2. every tool and when to use it;
  3. the sync-then-job behavior and "never re-issue on pending";
  4. reading results (thresholds, quality, strategy, failure codes; a match is a signal only);
  5. the CSV workflow;
  6. what to do per error code;
  7. a NEVER list (never print or ask for the key, never act on a match, never scan `/` or home without
     confirming).
* **Build.** `mcp/code/scripts/build-instructions.mjs` substitutes the `{API_BASE}`, `{CREDENTIALS_FILE}`,
  `{EXPORTS_DIR}` and `{ERROR_LOG}` variables, **fails the build on an unknown variable** or an empty file,
  and writes `src/instructions.ts`. That file is generated; edit the `.md` and rebuild.

## 9. Acceptance criteria

1. `just build-mcp` produces one executable bundle. `claude mcp add … serve` registers it, and
   `tools/list` works with the backend down.
2. With the web app running, `lfb_whoami` reports the backend up, the key authenticated, and the PDQ
   engine present.
3. Fingerprinting files and a directory works end to end:
   * small work returns synchronously;
   * large work returns a job that `lfb_fingerprint_job` long-polls to completion;
   * `lfb_fingerprint_export_csv` returns a CSV path that exists;
   * `lfb_fingerprint_directory_csv` on a folder returns a job whose finished `csv_path` has one row per
     matching file (path + 64-hex value), filtered by `extensions`.
4. The key is never printed; a loose credentials file is refused with the `chmod` fix; a rotated key works
   on the next call without a restart.
5. Every failure is an `isError` result with a stable code, and every WARN/ERROR is also in `error.err`.
6. Nothing but JSON-RPC ever reaches stdout.
